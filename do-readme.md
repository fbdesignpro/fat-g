# Running fat-g on Windows: the `do-` batch files

Double-click one in Explorer, or run it from a terminal in this folder. Each finds npm by itself and stops with a message if Node.js or the dependencies are missing (`npm install` once, first).

| File | What it does | Data folder |
|---|---|---|
| [`do-check.bat`](do-check.bat) | Targeted checks by changed files or area; `list` previews the selection, `full` runs pre-push checks, and `smoke new-chat`, `smoke session-search`, `smoke avatar-family` or the two-launch `smoke data-reset` runs one Electron scenario. See [testing](docs/testing.md). | Checks use no app data; smoke scenarios use `fatg-smoke-new-chat` or `fatg-smoke-session-search` or `fatg-smoke-avatar-family` or `fatg-smoke-data-reset` in `%TEMP%`, separate from full smoke |
| [`do-record-baselines.bat`](do-record-baselines.bat) | Records the stored formats' baselines this build has none of into `tests/fixtures/baselines/` ([decision 0014](docs/decisions/0014-format-compatibility-starts-at-first-release.md#baselines-091)), replacing none: synthetic documents written under a fixed clock, nothing of anyone's data. Run it after a format's version is raised, then `do-check.bat focused --area baselines`. | None; scratch folders in `%TEMP%`, removed; writes `tests/fixtures/baselines/` in this checkout |

| [`do-dev-screenshot-save.bat`](do-dev-screenshot-save.bat) | Double-click to freeze a closed window's setup. Choose Screenshot window or Everyday dev when both exist; the same dialog confirms replacement of an existing snapshot. | [`do-dev-screenshot-run.bat`](do-dev-screenshot-run.bat) | Double-click for each take: restores a fresh copy of the default screenshot setup and starts dev with `--window-size=1920x1080`. Close it between takes. | `%APPDATA%\fat-g-dev-setups\runs\screenshots` |

| [`do-run-stream.bat`](do-run-stream.bat) | The development build in the demo source's stream form: one project and one session, with a long fixture conversation in its chat, and two empty chats beside it, **Second chat** and **Third chat**, for a plan several chats share — each turn with the group of twenty things it did — and three fixture answers that stream into it, one for each prompt sent. The prompt `states` plays M105's synthetic parallel tools, Thinking gaps, parent work beside children, child waits and an anonymous wait; `states held` ends its parent early and `states lost` supplies an unreported interruption. Stop interrupts these scripts. The prompts `tools` and `worker` play a turn of work instead: twenty tools run into the full window, the second with a sub-agent whose answer streams into its own tab. The prompt `question` plays a turn that asks: a card the turn waits on, with two numbered options, Something else as a third row, Decline and Submit — answered, a message follows whose own question is a second card that waits for nothing; declined, the fixture says it went on without an answer (M21, M100b). A word after it plays a card no CLI shows on request: `question form` asks four at once — one option to choose, then several to choose among, a text alone, a secret — and confirms nothing once answered; `question worker` has a sub-agent ask, in its own tab; `question withdrawn` takes its question back after five seconds and goes on; `question lost` ends after five seconds as a session whose process was lost. The prompt `approval` plays a turn that asks leave for an action (M22): a card with the whole action and Approve once, Deny and Stop; the session has two modes for it, Read only and Ask first, in the menu above the black line at the chat's right, and starts under Ask first. A word after it chooses the card, or a state no CLI shows on request: `approval command`, which the word alone plays too, asks to run one command; `approval file` asks to change two files, one outside the project's folders, with an edit of every matching passage and a change long enough to be drawn only once opened; `approval grant` asks to run a command the session's grant can cover — approved for the session, the same prompt then runs with no card, until the process is closed; `approval denied` shows an action a rule of the configuration declined, with no card; `approval worker` has a sub-agent ask, in its own tab. Two words ask nothing and arm the sandbox setup's dialog, reached from the mode menu: after `approval setup` Ask first needs a setup whose first try fails and whose second completes; after `approval unknown` the first try waits until Stop waiting, and its outcome is unknown. Under Read only each asking word is refused, as a real request is. With **Plan** pressed in the prompt-type bar, a prompt plays a plan turn (M22b): the plan is written into its tab a piece at a time, then whole, as Codex writes one, and its panel stands in the input's place once the turn has ended — Execute plan plays a short answer, after which the plan is implemented and deleted and the chat says so in a line above its input; Discard plan sends nothing and deletes the plan; Leave plan mode, keep plan takes the chat out and keeps the plan for Review existing plan; and feedback plans the next version; a prompt that begins with `request` proposes its plan in a request instead, as Claude does, the turn waiting on the panel. The word `long` in the prompt plans a text of about 330,000 characters, written over some seven seconds and drawn by sections in its tab — Stop while it is written, and it stays unfinished. Read only takes no plan turn, as on Claude, and the toggle says why. **Review** → **Review existing plan** brings any plan the folder holds back into the chat: plans stay between starts, until they are implemented or discarded. **Several chats on one plan:** bring the plan into **Second chat** and **Third chat** with **Review existing plan**: every chat shares it — a review, a revision or an implementation started in one shows in the others in the input's place or in a line above it, each with a button that selects the chat that holds it, and in their capsules — Plan ready in each while the plan is ready, and while another chat or the reviewer holds it an orange Waiting on plan review, revision or implementation — and a newer version moves every chat's panel to it; Execute in a chat that did not write the newest version sends its whole text; and a `request` plan in the first chat has its request closed, its turn stopped, when another chat's version replaces it. On a plan's panel, **Review by model** → **Start review** makes a second session, named after the plan, that reviews it (M22e): its answer is written a piece at a time and brings five findings over three tiers, the first pointing at a passage of the plan; **Send notes** with a note written brings the review again with one finding moved to another tier under a new id, its mark carried, and a note holding the word `ask` brings a line of prose above the review sent again unchanged, and one holding `garble` brings it with two findings unreadable — T1.2, which stands as before with its mark, and a new one with no id, left out — each said under the appraisal; once every finding is decided, **Integrate** into the plan's own chat — or any chat of the plan, or a new one — plans its next version, the reviewer is marked Done, and the review reads stale. The review is a hard stop: until it is integrated, **Cancel review** in the reviewer or in any chat of the plan closes it, and where its findings are all refused **Take me back to the plan** concludes it. The session keeps two hundred side questions from its start, about its newest hundred answers, and once a prompt was sent a new one — **Explain this** on a passage, or **Side question** in the prompt-type bar above the input — plays its answer into its own tab: written as it arrives, or, for a question that begins with the word `whole`, all at once after two seconds. Its conversation ends with a message of two images, the two-colour fixtures of `tests/fixtures/attachments/`, drawn from fat-g's images' folder as a pasted one is (M23). Beside the mode control stands the context meter (decision 0033): its reading comes at the session's first prompt, a little fuller after each turn, in a window of 200,000 that compacts at 167,000; the prompt `context` brings it near that line, to show the red cells filling, and its tooltip holds the parts, the messages and the last call. It is what the recorded performance runs are made with (M19, V17; M20a, V11; M20b, V17): this window and the page's console show the page's long tasks and frames, one line for what came before each stream and one for the stream alone. It starts no CLI and spends no turn. `do-run-stream.bat packaged` builds the smoke flavor (`npm run package:smoke`) and runs the same in it. | `fatg-stream` in `%TEMP%`, made anew at each start |
| [`do-package.bat`](do-package.bat) | Builds the release package (`npm run package`) into `release\release\`: the installer and the unpacked app. Add `--output candidate-0.9.0` to use `release\candidate-0.9.0\` while the default packaged copy is running; audit with `node scripts/verify-package.mjs release --output candidate-0.9.0`. Starts nothing, installs nothing. | none |
| [`do-package-and-run.bat`](do-package-and-run.bat) | Builds the unpacked app alone (`npm run package:dir`, faster: no installer) and starts it. This is "the packaged app" a milestone's acceptance asks for. | `%APPDATA%\fat-g` |
| [`do-run-packaged.bat`](do-run-packaged.bat) | Starts the unpacked app already built, without building again: for a second launch of the same build, such as a check that a chat is still there after a quit. | `%APPDATA%\fat-g` |
| [`do-open-data.bat`](do-open-data.bat) | Opens the two data folders in Explorer. | both |

To open the Main window at a particular size, run `do-run-dev.bat --window-size=1920x1080` or `do-run-packaged.bat --window-size=1920x1080`. `do-package-and-run.bat` accepts the same option. Close the app first. The option overrides the saved size and maximized state; normal window placement continues to be remembered. Dimensions describe the whole window in logical pixels (DIPs), subject to the minimum size and the display's usable work area. Installed apps accept `--window-size=1920x1080` directly too. Malformed sizes are ignored.

Every build replaces its selected output folder: after `do-package-and-run.bat`, `release\release\` holds no installer until `do-package.bat` runs again. `do-package.bat --output NAME` replaces only `release\NAME\`, leaving the default packaged copy alone. Package builds share compilation and notice staging; run them one at a time.

## The data folders

fat-g writes only into its data folder; [PRIVACY.md](PRIVACY.md) lists every file in it.

| Folder | Used by |
|---|---|
| `%APPDATA%\fat-g` | The packaged app, whether started from `release\release\win-unpacked\` or installed. They are the same program and share this folder. |
| `%APPDATA%\fat-g-dev` | Development runs (`do-run-dev.bat`, `do-run-demo.bat`), so they never touch the packaged app's files. |
| `%APPDATA%\fat-g-dev-setups` | Frozen setups and their separate working copies (`do-dev-setup.bat`); restoring or running a setup never changes everyday dev or packaged data. |
| `fatg-smoke` in `%TEMP%` | The automated smoke runs (`npm run smoke`) alone. |
| `fatg-stream` in `%TEMP%` | The stream form (`do-run-stream.bat`, with `packaged` or without) alone. Its records and its chat are replaced at each start, its plans kept, and neither of the two folders above is opened. |

`%APPDATA%` is usually `C:\Users\<you>\AppData\Roaming`. A link cannot hold it, so to open a folder run [`do-open-data.bat`](do-open-data.bat), or paste the path into Explorer's address bar or the Win+R box.

What a development run saved is not in the packaged app, and the reverse: each has its own preferences, projects, sessions and chats. The CLIs' own logins and histories are theirs and are shared by both.

## What "install" would do

Nothing here installs fat-g. Installing is a separate step you take yourself, by running `release\release\fat-g-<version>-x64-setup.exe` after `do-package.bat`. It is not needed to run or to accept a milestone: the unpacked app is the same program.

Running the installer:

- **Asks once through SmartScreen,** because the installer is unsigned: *More info → Run anyway*.
- **Installs for your user alone,** without administrator rights and without questions, into `%LOCALAPPDATA%\Programs\fat-g`.
- **Adds a Start-menu shortcut,** named fat-g, and no desktop shortcut.
- **Uses `%APPDATA%\fat-g`,** the folder the unpacked app uses: an installed fat-g opens with the same projects and chats.
- **Never updates itself.** A newer version is installed by building and running a newer installer, over the old one.

Uninstalling (Windows Settings → Apps) removes the program and keeps `%APPDATA%\fat-g`; delete that folder too if you want the data gone.

The settings behind this are in [`electron-builder.yml`](electron-builder.yml); the development guide's [Build a package](docs/development.md#build-a-package) section covers packaging and the audit of what a package contains.

## Other systems

These files are for Windows. On macOS and Linux, run the npm scripts they wrap: `npm run dev`, `npm run package`, `npm run package:dir`. The data folders are named in [PRIVACY.md](PRIVACY.md#the-data-folder).
