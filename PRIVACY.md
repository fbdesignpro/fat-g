# Privacy: what fat-g keeps, and where

fat-g is a desktop window around the AI CLIs you already installed. This page lists every file fat-g writes, what each one holds and never holds, and how to delete it. fat-g itself never changes this page; it is part of the source code.

Settings → About displays bundled author, version and license information. It reads no account or project data and saves nothing. Installers include `LICENSE.fat-g.txt` and `THIRD_PARTY_NOTICES.txt` with the program resources; on macOS they also include `LICENSE.electron.txt` and `LICENSES.chromium.html` there. These static notices contain no user data.

CLI discovery checks executable metadata in PATH and known installation folders, including declared desktop runtime locations on Windows and macOS. For versioned runtimes it lists at most 128 immediate entries in the runtime folder and, where a layout keeps one build folder inside each version, in those version folders, without further recursion or directory links. It does not inspect surrounding desktop application data, account settings or credentials, import a desktop login, or save an executable's discovered version path. Finding a file is separate from the CLI's own sign-in and compatibility checks.

## The data folder

fat-g keeps its data in its own data folder:

| System | Folder |
|---|---|
| Windows | `%APPDATA%\fat-g\` |
| macOS | `~/Library/Application Support/fat-g/` |
| Linux | `~/.config/fat-g/` |

- **Development runs** (`npm run dev`) use `fat-g-dev` beside it, so they never touch an installed fat-g's files. A development run also treats the checkout's own `assets/avatars/` as fat-g's families' source: it writes a family's `family.json` there, as it does in your `avatars/` folder, when one is missing or when you save that family ([decision 0031](docs/decisions/0031-avatars.md)). An installed fat-g never writes beside its program.
- **Smoke runs** (`npm run smoke`, the automated checks) use `fatg-smoke` in the system's temporary folder. The targeted `new-chat` and `session-search` checks use `fatg-smoke-new-chat` and `fatg-smoke-session-search` there, separate from full smoke and normal app data.
- **Windows application icons:** when loading a bundled ICO from the program archive, Electron briefly
  writes `image.ico` in a unique system temporary directory, then removes it after Windows loads the
  icon. These files contain only fat-g's bundled artwork, with no user or session information.
- **The stream form** (`do-run-stream.bat`, a development tool that plays generated text into a chat to measure the page) uses `fatg-stream` in the system's temporary folder, replaces its records and its chat at each start, and opens neither of the folders above.
- **Screenshot setups** ([`do-dev-setup.bat`](do/do-dev-setup.bat), [instructions](docs/dev-setups.md)) live in `fat-g-dev-setups` beside the normal data folders, outside the repository. An explicit `save` copies the preferences, records, conversation database and its recovery files, optional catalog, plans, attachments and user media from the closed source you choose into `snapshots/<name>/`. When a screenshot working copy exists, Save asks you to choose Screenshot window or Everyday dev; choosing a source also confirms replacement of an existing snapshot. Before a working copy exists, the source is everyday dev. These contain the same private chats, paths and settings as the originals. `run` explicitly replaces the disposable copy in `runs/<name>/` and starts dev there; everyday dev and installed data stay untouched. Project/CLI folders, credentials, logs and caches are never copied, and links are refused. Snapshots remain until manually deleted or replaced by a save you confirm, including sessions since removed from the app. Temporary `.saving-*` or `.restoring-*` copies are removed on success and can remain after a crash. Replacing working data unlinks old files without overwriting bytes. Nothing is uploaded. The windowless helper reserves `.worker/` for Electron runtime files.

## What fat-g writes there

A sent user message also keeps whether it came from the queue, in `conversations.sqlite` alone, so its header can say “(from queue)” after a restart.

Pasted images keep a display label such as “Pasted image 1” with their use in `conversations.sqlite`, numbered within the session. The clipboard's placeholder filename is ignored. Dropped images keep their filenames as before; the image files in `attachments/` are still named by the hash of their bytes.

Never creates, writes, renames or deletes it — so a file it cannot use stays exactly as you left it. |
| `avatars/` | Yours to fill, if you want avatars of your own: a folder for each family, a folder for each avatar in it holding its `portrait.png` or `portrait.webp` and, if you like, a `small` one, and a family's `family.json` and `LICENSE.txt` ([how](docs/avatars.md)). | Creates it when you choose **Show avatars folder** or **Make a copy** in Settings → Avatars, or create a family from an image, and it is missing. Reads, at start and when you choose **Rescan**, its folders' and files' names, each image's size and the header at its start — and a whole PNG whose header leaves its animation unsaid — and each `family.json`, and reads an image whole each time a window draws it. Follows no link in it and opens no folder whose name starts with a dot. The family editor writes a family's `family.json` ([decision 0031](docs/decisions/0031-avatars.md)): with fat-g's defaults — its avatars' folder names, provider scope (Any provider by default) and the default look — at start and at **Rescan**, in a family folder that holds an avatar and has none; and with your changes when you choose **Save family** in the family editor, keeping whatever else the file holds. Each is written beside it as `family.json.tmp`, then renamed over it. A `family.json` fat-g cannot read, or a link, it leaves as it is. **Make a copy** creates a new **Copy of ...** family in this folder from a built-in family, copying its validated portrait and small images, manifest and optional licence without changing their bytes. An existing name is numbered instead of overwritten; links and unrelated files are never copied. A failed copy removes only its own new folder. **Create family**, after dropping or choosing an image under **Avatar families**, creates a new family folder with a `Default` avatar and its prepared `portrait.png` and `small.png`, plus `family.json`. If you give matches, it also creates a named avatar with the same images and those matches. It never overwrites an existing name (in any case); a failed creation removes only its own newly reserved folder. **Add avatar** in the family editor creates a new avatar's folder in that family, with a `portrait.png` and a `small.png` the window made from the image you dropped or chose — scaled to 512 px and 64 px, never larger than the image — and adds its entry, with the matches you gave it, to `family.json` ([decision 0036](docs/decisions/0036-adding-avatars.md)). An image you drop onto, or choose for, an avatar's **Main image** or **Small version** in the family editor replaces it the same way — a main image with its small version — as `portrait.png` and `small.png`; the files it replaces are moved to your system's Recycle Bin or Trash, from where you can restore them. The image you dropped or chose is kept nowhere else; an existing folder or file is never overwritten, and a failed add removes only its own new folder. **Browse** opens your system's file chooser at the folder your last image came from — chosen there or dropped from it — which fat-g remembers in memory until it quits, never in a file or a log; it reads only the image you choose. The data folder also holds the browser engine's own working files (Electron's Chromium): folders such as `Cache`, `Code Cache`, `GPUCache`, `Local Storage`, `Session Storage` and `Network`, and files such as `Local State` and `Preferences` (Chromium's, not fat-g's). fat-g's pages store nothing in them. The things of fat-g's that Chromium keeps there are the Main window's zoom, a number in `Preferences` that fat-g sets when you zoom, so that the window opens at that size next time, and the avatars a window drew: an avatar's image, built-in or from your `avatars/` folder, may be kept in `Cache` under the id fat-g gave it, so that it is not read again ([decision 0031](docs/decisions/0031-avatars.md)). An image you pasted into a chat is never kept there, nor an image an agent read or an answer names. fat-g makes no network calls of its own.

## Reset everything and quit

**Settings > Diagnostics > Reset all data...** shows this run's exact data folder and asks two separate questions, each defaulting to Cancel. The second confirmation explicitly removes everything in that folder: settings and account entries, presets and recent selections, the project/session list, chats and queued drafts, plans, attachments, custom avatars and sounds, `catalog.json`, saved backups and browser caches. Only after the request file above has been written and flushed does fat-g quit, through its normal shutdown that stops running work and closes its stores. There is no third quit question.

Deletion takes place on the next launch, synchronously after taking the single-instance lock and before Electron opens its old browser profile or fat-g opens a store or starts a provider. The data directory itself and the current process's runtime lock entries stay in place. Directories and files are checked inside the admitted data root; symbolic links and junctions are unlinked rather than followed. Conversation database files and sidecars are overwritten before unlinking, unless another hard link exists, in which case only the data-folder entry is unlinked so an outside file is not modified. The reset request is removed last. A failed or interrupted reset retains that request and any remaining files, stops startup, and retries on the next launch. An invalid or incompatible request is preserved and nothing is deleted.

There is no reset backup. Your actual project folders and CLI logins, settings and history remain untouched. Other fat-g installations or development profiles, saved screenshot setups and backups outside the displayed folder remain. The next successful launch uses defaults and shows automatic provider detection again. Windows installations normally use `%APPDATA%\fat-g\`; macOS uses `~/Library/Application Support/fat-g/`; development uses `fat-g-dev` beside them.

## How to delete it

Quit fat-g first, then:

- **Everything:** delete the data folder. The next start is a first run.
- **Your projects and sessions only:** delete `records.json`. fat-g forgets your projects, and their sessions go with them. Nothing in their folders, and nothing in the providers' history, is touched: the conversations stay where each CLI keeps them. The chats fat-g saved are **not** deleted with it: each stays in `conversations.sqlite`, shown at the foot of the project list as a chat without a session, until you remove it there.
- **Your saved chats only:** delete `conversations.sqlite` and, if they are there, `conversations.sqlite-wal` and `conversations.sqlite-shm`. Your projects and sessions stay; their chats start empty. A session with Codex shows again what Codex itself still has; a session with Claude does not, since fat-g never reads Claude's own history, though the model still remembers the conversation.
- **One session, with its chat:** choose **Remove** in its `…` menu. fat-g forgets the session and deletes the chat it saved for it; the provider's history is untouched. Removing a project does the same for each of its sessions.
- **A plan:** fat-g deletes it by itself once it is implemented, or when you press **Discard plan**. Otherwise choose **Remove** in its tab's menu, once you confirm it; the decision of each chat taking part in it is settled first, and the confirmation says how many there are. **All plans:** Settings → Storage removes them all once you confirm it, or delete the `plans` folder. Removing a session leaves its plans; removing a project removes its plans with it.
- **A chat without a session:** the row "n chats without a session" at the foot of the project list, or Settings → Storage, removes one or all of them once you confirm it.
- **A conversation store set aside:** Settings → Storage lists each with its size and removes it once you confirm it, or delete the files yourself.
- **Your settings only:** delete `preferences.json`. The defaults return, every provider's switch is on, and your default modes are gone: a new chat then takes its project's default, or Ask first. A chat that exists keeps its mode. Your chat username returns to “You”. The avatars you assigned and the families you chose are gone with the file, and every model shows what fat-g's own families give it. Your families' `family.json` files stay in your `avatars/` folder.
- **Your model adjustments:** delete `catalog.json`, then choose **Reload** at the top of Settings → Providers, or restart. The lists go back to what the CLIs report.
- **A set-aside copy:** delete it whenever you no longer need it. fat-g never reads it again.

Uninstalling fat-g removes the program and keeps the data folder; delete it too if you want it gone. Removing a project in the app removes its record from `records.json`, its sessions' records with it, the chats fat-g saved for those sessions, and the project's plans in `plans/`, and nothing else.

**What Remove does to a saved chat, and what it cannot do.** The chat's content is overwritten inside fat-g's files, not only marked as free, and the file is made smaller by what was removed: after a removal the text is in none of the store's three files. fat-g cannot answer for copies outside its own files: a backup, a file-history or snapshot feature of your system, or blocks a drive keeps spare. And nothing in the provider is deleted: the conversation stays in the CLI's own history until you delete it there.

A session entry left in `records.json` without a project — after a hand edit, for instance — is shown nowhere else, so fat-g counts such entries in a row at the foot of the project list, "n sessions without a project", whose **Remove** deletes them, and the chats saved for them, once you confirm it.

A saved chat whose session is no longer listed — its record was deleted by hand, or `records.json` was set aside — is kept as it is and never deleted by itself. fat-g counts such chats in a second row there, "n chats without a session". Each can be opened and read, takes no prompt, and asks nothing of a provider; it is removed only when you choose **Remove**. If the session's record comes back, the chat is that session's again.

## Sessions

In this version a session can run with Codex or with Claude. Whichever it runs with, when you send a prompt:

- **Your prompt goes to the provider through your own CLI.** fat-g starts the CLI you installed, in the session's folder, and hands it your prompt over the CLI's own input, never on a command line. The CLI sends it to the provider under your account, together with whatever the agent reads to answer it. fat-g makes no network call itself.
- **Only in a folder you trusted.** A session starts, and is resumed, only in a project folder you answered "Trust this folder?" with yes, and only while that folder is there.
- **What a session may do is its chat's mode, and your CLI enforces it.** Each provider has five modes, named in fat-g's own words and listed under [With Codex](#with-codex) and [With Claude](#with-claude): from one that only reads to one that asks nothing. A chat's mode is shown in its header and changed there, and nowhere else: there is no mode for one prompt alone. A new chat takes the project's default for its provider if you set one, else your own default from Settings, else **Ask first**; a mode that acts without asking is never chosen for you. fat-g tells the CLI the mode each time it starts the session's process, and checks what the CLI reports before your prompt is sent: if the CLI reports another policy, nothing is sent, the chat says so with what the CLI reported, and you choose a mode again. A mode this account cannot use is never swapped for another: the chat says why, and waits for your choice. Some changes of mode close the session's process, which is started again at your next prompt; the menu says which, before you choose.
- **Under a mode that asks, a request to act is a card, and nothing runs until you decide.** When the CLI asks leave to run a command, change a file or use a tool, the chat shows a card at that place: who asks, the whole command, or the whole change with the text it would write, the paths it names and whether one lies outside the project's folders, and the model's own reason, marked as the model's. You choose **Approve once**, **Deny** or **Stop**. Nothing is chosen for you, there is no timeout and no default, and closing the card or pressing Escape approves nothing. Your decision is saved before it is sent, and never sent twice. fat-g reads no file to draw a change: what the card shows is what the CLI sent. A request too large to show whole is refused, and the chat says how large it was; it is never shown cut for you to approve.
- **Approve for this session is the CLI's own grant, and it ends with the session's process.** The choice is on a card only where the CLI itself offers one. fat-g sends back what the CLI offered, for this session and no further, and the card says what it covers before you choose. fat-g never sends a rule the CLI would save: Claude would write one into your project's folder, and Codex would apply one to every project of the account, and neither lists such a rule or takes it out. The session shows a list of the grants fat-g sent, each said live or ended; it is fat-g's own record, and no reading of the CLI, which lists none. A grant ends when the session's process ends: a change of mode that closes it, five idle minutes, a crash, or quitting fat-g. Nothing sends it again afterwards. There is no button that ends a grant: to end one, change the chat's mode, or let the session stand idle.
- **fat-g keeps no permission rules of its own.** It matches no request against anything, answers no request you did not answer, and builds no reviewer and no sandbox. What runs without a card runs because the CLI's own policy lets it: the mode you chose, a grant you gave, or your own CLI configuration.
- **Your own CLI configuration acts under every mode, with no card.** A rule in your Claude or Codex settings that allows a command, an MCP tool your settings allow, and a hook of yours run as that configuration lets them, and fat-g is never asked. No mode's description promises a card before every action, and each list of modes says so in one line. fat-g does not read your configuration and cannot list the CLI's own rules: Claude's CLI does not list them in the version fat-g was checked against, and Codex lists its permission profiles and not its rules.
- **A question the model asks you is shown as a card, and your answer is sent only when you press Submit.** Nothing is chosen for you, and fat-g answers nothing by itself: there is no timeout and no default. Your answer goes to the CLI through its own input, as a prompt does, and on to the provider with the conversation. It approves nothing: an answer is the reply to a question, and a request to act is another card, with its own decision. The question, its options and your answer are kept in `conversations.sqlite` with the chat, until you remove it. Where the CLI marks a question as secret, the field hides what you type, your answer is sent, and fat-g does not save it: the chat keeps only that an answer was given. A question that was waiting when its session's process ended, or when fat-g closed, is not answered later: its card says so ([decision 0026](docs/decisions/0026-questions.md)).
- **A plan is made only when you ask for one, and acted on only when you decide.** With **Plan** pressed, your prompt is sent as a plan turn, in the CLI's own plan mode, and the chat's mode stays as it is. The plan the provider proposes is kept in `plans/` in fat-g's data folder, whole, until it is implemented, you discard it or you remove it; nothing of it goes into your project. Every chat that made the plan, brought it or received its integration shares one state of it and decides on its newest version: **Execute plan**, **Discard plan**, **Leave plan mode, keep plan** and your feedback are sent only when you press them, one at a time across those chats, and a prompt cannot be sent while a plan waits for your decision or is under review. Where another chat carries the plan out or a newer version replaces it, a chat's pending Claude request on it is answered as Cancel answers it, which ends that chat's waiting turn and sends the model nothing else; that chat's next decision then sends the newest version's whole text to its own account. **Review existing plan** brings one of the project's plans into another chat, and sends its whole text to that chat's account in your next decision's prompt — another provider or another account, if that chat is one. A plan's text and title never reach a log, the app state or the mini window, which shows that a plan is ready and nothing else. **Review by model** sends the plan's whole text, a fixed instruction and your project folder's path to a new session on the account, model, effort and speed you choose — the chat's own to start with, or any account the project is set up for — under its provider's reading mode, when you press **Start review**; **Send notes** sends that session your notes and marks, and **Integrate** sends the findings you accepted and your notes — and, for a plan turn, the plan's whole text — to the chat you choose, on its account, which may be another. Each is a turn that spends that account's usage, and none runs by itself: no finding is marked but by you, and nothing is sent again. A review's findings, your marks and notes stay in `plans/` and the prompts and answers in `conversations.sqlite`; none reaches a log, the app state or the mini window. The reviewer's name holds the plan's title, and so does the name of a chat that had none when you brought the plan into it; both are kept and shown as any session's name, and stay when the plan is deleted, until you rename or remove the session ([decision 0029](docs/decisions/0029-plans.md), items 8 and 12–17).
- **The provider keeps the conversation.** Each CLI stores it in its own history on this machine, where that provider's other apps show it too. Removing a session in fat-g deletes fat-g's own copy and its reference; the CLI's copy stays.
- **fat-g keeps a copy of the chat, until you remove it.** What you and the model say in a session is written to `conversations.sqlite` in fat-g's data folder as it happens — your prompt before it is sent — so the chat is there after a restart, whatever the provider can give back. **What the session did is kept with it:** each command it ran with its command line and output, each file it read with its path and what was read, each search, each reported edit, each tool call with its input and result, and each sub-agent's own work and words, as the CLI reported them at the time. A long output is kept as its first and last parts, and the chat says how much was left out. This is the text of your files and the output of commands, in clear, in fat-g's data folder. It is kept until you remove the session, its project, or the chat itself; nothing is deleted by age, and nothing is sent anywhere. `records.json` still holds, of a conversation, only the session's name: the first line of your first prompt, a short title the session's own account wrote from it, or a name you typed.
- **A question beside a session is kept with it.** **Explain this**, on a passage you select in an answer, in what an action printed or in a file you opened, and **Side question**, above the input, ask the provider a question beside the session: its answer is not part of the conversation the agent works in, and the session's own turn neither waits for it nor is interrupted by it. fat-g sends the provider your question and, for Explain this, the passage you selected with where it came from; nothing else of your files is read for it. The question, the passage and the answers are saved in `conversations.sqlite` as a chat of their own beside the session's, until you explicitly close its tab or remove its session or its project. Side question opens a fresh tab directly. Closing a side question's tab with X, middle click or Delete stops its running answer and permanently removes its saved content and source marker, without another confirmation; a failed removal keeps the tab open. Quitting removes nothing: saved questions reopen as tabs when you return to their session after a restart, with no model call. Unsent text in a side question's field lasts only for the app's run. There is no separate Remove button in the tab. A side question spends your subscription's usage as a prompt does; fat-g is told nothing of what one cost, and shows nothing of it ([decision 0025](docs/decisions/0025-asides.md)).
- **A new session's title is asked of its own account, and only the title is kept.** At a session's first prompt — unless you switched **Name sessions automatically** off in Settings, or the prompt is a bare CLI command or skill — fat-g sends the first 2,000 characters of that prompt a second time, with a fixed instruction, to the same account through its own CLI, in a short process of its own started in fat-g's `probe-cwd` folder and never in your project. With Claude, that process loads none of your settings, hooks or MCP servers, is offered no tool, does not think, and saves no session; with Codex, it runs one thread that Codex does not save, read-only, asked for no approval and told to act on nothing, with Codex's web search, apps, plugins, hooks and sub-agents switched off for that thread alone, while your own Codex MCP servers stay as you configured them. Nothing is written to your Codex configuration. Anything the CLI asks of it is refused. The reply becomes the session's name, of at most 160 grapheme clusters, in `records.json`; nothing else of the exchange is kept, logged or shown. A name you typed — **Rename** in a session's menu — is never replaced. It spends a little of your plan's usage, as a short prompt does. Settings says which model writes the titles: by default, **Latest small model** selects the newest available Haiku or Luna from that account's CLI model list, refreshed at startup and as the list changes; if none is available, it uses the session's model. You can also choose the session's model explicitly or a fixed model your CLI lists ([decision 0028](docs/decisions/0028-secretary.md)).
- **A session you have typed in but not sent is described by its own account, once you leave it.** A session you start and never prompt is provisional: it has no capsule in the list while nothing is typed in it, and leaving it for another session makes fat-g forget it — nothing of it was ever sent. If you have typed something into it and then go elsewhere, fat-g sends the first 2,000 characters of that unsent text, with a fixed instruction, to the session's own account, in the same kind of short process the title uses, so the capsule can read "New session: setting things up" rather than "New session". **This is the only text fat-g sends that you have not pressed Send on.** It is sent once for a given text, never while **Name sessions automatically** is off, never for a session you have named yourself or that has already run a turn, and never for a bare `/` command or skill; a command or skill followed by text is eligible, and the command and text are sent together. Only the few words of the answer are kept, as the session's name in `records.json`: the text you typed is not written to `conversations.sqlite`, since a prompt is recorded when it is sent, and it is not kept, logged or shown anywhere else. The session's first turn asks for a proper title, which replaces it ([decision 0028](docs/decisions/0028-secretary.md)).
- **An image goes with your prompt only when you send it.** An image you paste or drop is kept in `attachments/` in fat-g's data folder as soon as it is in the composer, and goes to the provider, through your CLI, with the message you send it in — at once, into a running turn, or from the queue. How each CLI takes it is under [With Codex](#with-codex) and [With Claude](#with-claude). fat-g checks only that it is a PNG, JPEG, GIF or WebP image within its size: it does not open, convert or describe it.
- **Your draft and your queue are kept until they are sent or removed.** What you type is kept as you type, a few seconds behind, so that a restart shows it again; a queued message is sent once its session is idle, after a restart too, without asking again: you sent it when you queued it. Completing a session drops its queue and keeps its draft; removing a session deletes both, with their images.
- **A message sent into a running turn is said under it.** With **Send now**, your message goes to the CLI while its turn runs, and the chat says what became of it — taken into the turn, sent as the next prompt where the turn had just ended, not sent, not confirmed, or cancelled by Stop. fat-g never sends one again by itself. Where the turn cannot take a message at that moment, your message waits first in the session's queue, kept as a queued message is, and goes as soon as the turn takes one, or as the next prompt once the session is idle.
- **A prompt is never sent twice.** If fat-g is closed or crashes around a Send, the chat says that the provider did not confirm the message, or that the turn's end did not arrive. fat-g does not send it again by itself.
- **Quitting stops what runs.** fat-g stops each running turn and ends the CLI processes it started. It keeps no record of processes between runs.

### With Codex

A Codex mode is three things of Codex's own, which fat-g names each time it starts or resumes the session and with each prompt: a sandbox, an approval policy, and who answers what asks. fat-g checks that Codex's reply reports all three before your prompt is sent.

- **Read only + allowed MCP.** Codex's read-only sandbox, with approvals off. The agent reads files and runs nothing that changes them, and every request it makes for leave is declined at once. This is what every Codex session was before modes. **An MCP tool its server marks as safe still runs:** Codex runs a tool its server marks as read-only, or as neither destructive nor reaching outside, with no request, under this mode and every other, and such a tool may still change something. Codex refuses any other MCP tool itself under this mode.
- **Ask first.** Each command asks before it runs, unless Codex holds it safe or a rule of your own Codex configuration allows it, and so does each change to a file, a file in the project's folder included. On an account with a sandbox, a command you accept runs inside it, held to the project's folder and the temporary folders. **A file change you accept is written wherever it names, outside the project's folder too:** the sandbox holds commands, not accepted file changes. The card says when a path lies outside.
- **Sandbox ok.** Commands and file changes in the project's folder and the temporary folders run without asking. A file change outside them asks, and is written there once you accept it; a command that would write outside them is stopped by the sandbox.
- **Auto reviewed.** As Sandbox ok, with Codex's own reviewer answering in your place what would have asked you. **No card comes for what it decides,** and it can approve a change outside the project's folder. The chat shows the action; it does not show the reviewer's verdict.
- **Berserk.** Codex's own Full access: everything runs without asking, anywhere your user account can write, with no sandbox.
- **Where a sandbox mode can write is what Codex reports, not a list of fat-g's.** The project's first folder; the system's temporary folders, unless Codex's reply says it excludes them; and whatever your own Codex configuration adds — another writable folder, or access to the network — which the mode's menu then says, as your configuration, and which fat-g does not refuse. fat-g asks Codex for no exclusion and adds no folder.
- **An account whose sandbox is not set up has no sandbox.** On Windows, Codex's sandbox is set up per configuration folder, so an account you added starts without one. Codex then takes a sandboxed start with no error and reports its read-only sandbox in place of the one asked for. **Sandbox ok** and **Auto reviewed** are unavailable to that account, and say why. **Ask first** is available, and says what it then means: every write asks, and one you accept runs unconfined, outside any sandbox, wherever it names.
- **Setting up Codex's sandbox changes your machine, and happens only when you press Set up.** fat-g asks Codex whether its sandbox is ready, on Windows alone: when an account's modes are first listed, and after a setup. Where it is not, the modes that need it offer **Set up**. Its dialog says, before you press, what Codex's own setup does, by OpenAI's description: it creates dedicated sandbox user accounts on this machine and changes firewall rules and file permissions. Pressing it sends Codex that one request. Windows then asks for an administrator's approval by itself: fat-g asks for no password, and sees none. Codex writes its own files into its configuration folder, `config.toml` among them; fat-g reads and writes none of them, and **cannot undo the setup**. While it runs, nothing else of that account is sent. If fat-g does not hear how it ended, it says that the outcome is unknown and that the setup may still be changing the machine, asks Codex again whether the sandbox is ready, and shows the answer. Nothing is sent again without a new press, and fat-g keeps nothing of a setup once it is closed.
- **The first time Codex's sandbox works in a project's folder, Windows may ask for an administrator's approval.** The prompt is Codex's own: its setup helper, "Codex Windows sandbox setup", giving the sandbox's accounts access to that folder. fat-g sends nothing for it and sees nothing of it. Approving it changes that folder's permissions for Codex's sandbox accounts; declining it leaves Codex unable to write there in its sandbox. The three modes that use the sandbox, Ask first, Sandbox ok and Auto reviewed, say so where you choose them.
- **Under some modes Codex records the project's folder as trusted, in its own configuration.** Starting a session under **Berserk**, or under **Ask first**, **Sandbox ok** or **Auto reviewed** on an account whose sandbox is set up, makes Codex write that folder as trusted into its own `config.toml`, before any prompt. That is Codex's write, not fat-g's, and the mode says so where you choose it. **Read only + allowed MCP** writes nothing there, and neither does **Ask first** on an account with no sandbox. fat-g never reads or changes that file, and your answer to fat-g's own "Trust this folder?" stays in `records.json`.
- **Approve for this session, with Codex, covers the files of one change.** Codex offers it for a file change: a later change to the same file then runs without asking, until the session's process ends; a change to another file still asks. For a command Codex offers no such choice, and its other offer — a rule it would save for every project of the account — is told on the card as something the request would also grant, and is never among the choices.
- **A change of mode always closes a Codex session's process.** Codex keeps a policy with its thread once it is named, and reports it only when a session is started or resumed. So fat-g changes a mode in one way: the process is closed, the chat's choice is saved, and your next prompt resumes the session under the new mode, checked before the prompt is sent. The session's grants end with the process.
- **A Codex session asks for Codex's experimental API.** A plan turn's mode is an experimental field of Codex's, so fat-g's handshake for a session asks for it, whether or not you plan; fat-g sends no other experimental field or method. Where Codex refuses, the session is opened again without it, and plans are unavailable for that account until fat-g restarts. After a plan turn, every later turn of that chat names Codex's default mode, so that nothing goes on planning by itself.
- **No mode is "this folder only" for reading.** A Codex session, Read only + allowed MCP included, can read files outside the project's folder, wherever your user account can read. What it reads may be sent to the provider as part of the conversation.
- **Your own Codex configuration applies.** fat-g does not replace it. The MCP servers you set up in Codex start with each session, and run as Codex runs them.
- **An MCP tool Codex asks to run is a card.** Under **Ask first** and **Sandbox ok**, Codex asks before it runs an MCP tool its server does not mark as safe, and the card shows the server, the tool and the call's arguments whole. **Approve for this session** covers that tool of that server, until the session's process ends; another tool of the same server still asks. Codex also offers to remember the choice beyond the session: the card says so, and fat-g never sends that answer. Under **Auto reviewed** Codex's reviewer answers in your place. A form or a web address an MCP server asks you for is refused, with a notice.
- **One folder.** A Codex session is given the project's first folder. A project's other folders are not handed to it.
- **A side question runs on a copy of the conversation, read-only, and it may read files.** For each one fat-g asks the session's own Codex process for a temporary copy of the conversation as it stood at the last turn that ended, with the read-only sandbox and approvals off whatever the session's mode, checked before your question is sent, and with the instruction to answer briefly and act on nothing. Codex can still read a file, or list a folder, to answer you: what it read is shown in the question's tab and saved with it. The read-only sandbox prevents file changes by commands and file tools; the same allowed-MCP exception applies here, so an MCP tool its server marks as safe may still act. Codex starts your MCP servers again for each copy, which takes a few seconds and runs them as a session does. The copy is not written to Codex's own history, and is gone when the session's process ends; a follow-up asked after that is sent with your earlier questions and their answers before it.
- **The agent's task checklist is shown only where your own Codex configuration enables it.** Codex reports its running list of steps only when its `update_plan` tool is on in your Codex configuration (`[tools]`, `update_plan`, `enabled = true`). fat-g does not switch it on and sends Codex no configuration: with the tool off, a session shows no checklist, and its work is shown all the same.
- **An image goes to Codex as the path of its file in fat-g's data folder.** Codex reads the file itself and sends the image to the provider, and it keeps that path, which names your user folder, in its own session files, as it keeps your prompts. A message sent into a running turn goes as Codex's own `turn/steer`, on the session's own process.
- **A skill you choose from the menu goes as Codex's skill input.** When you type `/`, fat-g asks the instance's own Codex process which skills the session's folder has — their names, descriptions, scopes and paths — and keeps that list in memory alone; the menu shows names and descriptions, never a path. A skill you choose goes with your prompt by its name and its path, as Codex listed it just before the send; one no longer listed sends nothing. A command typed and not chosen is text.
- **Earlier turns are asked of the CLI once per start.** When you select a session, fat-g asks the CLI which turns the conversation has. A turn made in Codex's own app, which fat-g never saw, is then read and saved with the rest; a conversation with nothing missing is not read again. fat-g never reads the CLI's own session files.
- **How full a session's context is, as Codex counts it.** Codex reports, for each conversation it runs, how many tokens its last call used, how many all its calls used, and its model's context window. fat-g reads that report for the session's own conversation — never a sub-agent's or a side question's — and shows it beside the mode control, while fat-g runs; nothing of it is written to disk or logged ([decision 0033](docs/decisions/0033-context-readings.md)).

### With Claude

**Claude has no sandbox for fat-g to switch on, and fat-g never says it has.** Under every mode, what holds a Claude session back is the list of tools it is offered, the permission mode its process runs under, and your decisions on its cards. A Claude mode is those two things of Claude's own, which fat-g names when it starts the session's process: a permission mode, and a tool list.

- **Read only + allowed MCP.** Five of Claude's built-in tools: `Read`, `Glob`, `Grep`, `Agent`, which starts a sub-agent that is given the same list and no more, and `AskUserQuestion`, with which the model asks you a question in the chat. None of them edits a file, runs a command or reaches the web, and every request Claude makes for leave to act is refused. Its name says the rest: the MCP tools your settings allow, and your hooks, still act (see below). This is what every Claude session was before modes.
- **Ask first.** The same five tools, three that act — `Bash`, which runs a command, `Write`, which writes a whole file, and `Edit`, which replaces text in one — and two that reach the web: `WebFetch`, which reads a web page, and `WebSearch`, which searches the web (see below). Each command, each change to a file, each search and each fetch asks before it runs, and so does anything else Claude asks leave for — an MCP tool your settings do not already allow, a read outside the project's folders — unless a rule of your own Claude configuration allows it. **The exception is Claude's own: it fetches pages of its list of documentation sites without asking.** Reading inside the project's folders does not ask. **A change you allow is written wherever it names, outside the project's folders too:** an allow is all that stands before a write anywhere. The card says when a path lies outside.
- **Edits ok.** Claude's own `acceptEdits` mode: file changes run without asking, and so do the commands Claude holds safe and fetches of its documentation sites; other commands, searches and fetches ask.
- **Auto reviewed.** Claude's own `auto` mode: Claude decides by itself what would have asked you, outside the project's folders too. **No card comes for what it decides.**
- **Berserk.** Claude's own Bypass permissions: everything runs without asking. fat-g starts it by naming the mode alone. It never passes a flag that bypasses permissions, and if a version of Claude took this mode only with such a flag, the mode would be listed as unavailable.
- **A sub-agent runs under its session's mode.** What a mode lets the session do without a card, it lets a sub-agent do. Under Ask first a sub-agent's request is a card in the sub-agent's own tab, and the session shows that one is waiting. Claude's background tasks are switched off: a sub-agent ends with its turn.
- **Three changes of mode are made on the running process; the others close it.** Between Ask first, Edits ok and Auto reviewed, fat-g asks the running Claude process to change its permission mode, with nothing running, and saves your choice once Claude confirms it. Into and out of Read only + allowed MCP, and into and out of Berserk, the process is closed and your next prompt resumes the session under the new mode: the first is another list of tools, and a process started able to bypass permissions is never kept under another mode's name. The session's grants end with the process.
- **Under the four modes that act, Claude can search the web and read web pages.** The installed CLI does both, under your account; fat-g makes no network call of its own. **A search** goes to Anthropic, which runs it with its own search service and hands back the results' links with a short summary. **A fetch** is made from this computer: the CLI downloads the page at the address the model chose and has a small Claude model answer the session's question from it. The model chooses that address, and an address can carry words of the conversation or of your project to the site it names. Under Ask first and Edits ok the card shows the whole address before anything is fetched, or the whole query before a search — but for the documentation sites Claude fetches without asking. Under Auto reviewed Claude decides with no card, and under Berserk both run without asking, as a command does. What comes back is kept with the chat, as any tool's result is. A Claude account or backend without web search does not offer it, and fat-g does not ask for it.
- **Approve for this session, with Claude, is Claude's own rule.** Where Claude offers a rule with a request, as it does for a command, the card shows the rule's text: one exact command, in what fat-g has seen; for a fetch, the site (`domain:` and its name); for a search, every search (`WebSearch`). fat-g sends that rule back for the session alone, whatever Claude suggested: as Claude suggests it, the rule would be written into `.claude/settings.local.json` in your project's folder, which fat-g never asks for. For a change to a file Claude offers no such rule, only a change of mode: the card names the mode that would stop the question, and changes nothing.
- **Claude's own commands and your skills work as they do in Claude's terminal.** A prompt that begins with a command's name — `/compact`, a skill of yours, a command of a plugin — goes to the CLI as you wrote it, and the CLI runs it: `/compact` rewrites what the model holds of the conversation, and a skill does what you wrote it to do, with the tools of the session's mode. fat-g shows what the CLI answers and claims nothing about what the command did. The model itself is offered no way to start a skill: one runs only when you write its name. **Two commands fat-g answers itself and never sends,** because each would change what fat-g keeps track of: `/clear`, which would start another conversation in the same session, and `/model`, which would change the model a session was created with. The chat says so, in fat-g's words, and no model is called ([decision 0023](docs/decisions/0023-cli-commands-pass-through.md)).
- **An image goes to Claude as its bytes, in your message.** fat-g reads the image from `attachments/` and writes it into the message it hands the CLI; nothing of it comes back. A message sent into a running turn is written to the CLI as a message is, and Claude takes it at its next step or runs it as its next turn; **Stop** asks Claude to drop one it has not run yet, and fat-g ends the process where Claude does not confirm it. Send now is offered only where Claude says its Stop can do that.
- **The command menu lists Claude's own commands and your skills, as Claude reports them.** Claude tells fat-g its commands and skills when a session's process starts; fat-g keeps that list in memory alone, for the run, and shows its names, descriptions and hints. Choosing one puts its name in your message, which goes as you wrote it.
- **A side question is answered from the conversation alone.** fat-g sends it to the session's own Claude process, as a question beside the conversation. Claude answers it with no tool: it reads no file and runs nothing for it. Your hooks do not run for a side question, and Claude does not write it into its own record of the conversation. Claude keeps nothing of one either, so a follow-up is sent with your earlier side questions and their answers. Where another model than the session's answered, the tab says which.
- **fat-g asks Claude how full a session's context is.** When a turn starts on a process that has not been asked yet, and after each turn ends, fat-g asks the session's own Claude process for its context's summary, which Claude answers from what it already holds, with no request of its own to the provider. Of its answer fat-g reads only counts — the tokens used, the window, where Claude compacts by itself, and the parts of what is used under Claude's own names, such as System prompt or Messages — and between two answers the counts Claude reports with each reply. The answer also lists your memory files by path, your MCP tools and servers, agents and skills by name: fat-g reads none of them. The reading is shown beside the mode control while fat-g runs, and nothing of it is written to disk or logged ([decision 0033](docs/decisions/0033-context-readings.md)).
- **Reading outside the project asks.** Claude asks before it reads a file outside the folders the session was given. Under Read only + allowed MCP fat-g refuses every such request, so that read does not happen. Under any other mode such a request is a card like any other, and the read happens if you approve it; and a mode that lets Claude act without asking lets it reach outside the project's folders without asking too.
- **What Claude reports is checked against the chat's mode, at three points.** Before your prompt is sent, fat-g checks that Claude's reply reports the permission mode the process was started under; if not, nothing is sent. When a turn begins, Claude lists the tools the turn has: if that list holds a built-in tool outside the mode's own list, or reports another mode, fat-g ends the session's process at once and the chat says so. That second check can only be made after the prompt has been sent. And whenever Claude reports a change of its permission mode, fat-g holds it to the mode in force, or to the one a change it asked for is moving to: any other ends the process. After any of the three, nothing is sent until you choose a mode again.
- **Your own Claude configuration applies, and it can do more than the mode's tools.** fat-g does not replace it, and neither reads nor changes it: your own settings and the project's load through the CLI as they do in Claude's own app — instructions such as `CLAUDE.md`, hooks, MCP servers and sub-agent definitions. **A hook is a command of yours that Claude runs at set points of a session, and an MCP tool your settings already allow runs without asking. Both can change files and reach the network, and fat-g does not stand in their way.** A rule of your settings that allows a command lets it run with no card, under any mode that has the tool; one that denies it refuses it with no card either, and the action's line in the chat then reads "Declined by a rule of your configuration". A project's own configuration is read when the session's process starts, before any prompt: that is what your answer to "Trust this folder?" is about.
- **All of a project's trusted folders can be read.** The session runs in the project's first folder. The project's other folders that you trusted, and that are there, are handed to Claude as additional folders each time its process starts, and looked at again at each prompt: a folder you no longer trust, or that is gone, leaves the session at the next prompt. Their paths go to the CLI on its command line, as the session's model does, where other programs running under your account can read them; your prompt never goes there. On Windows, a folder whose path holds a character that cannot be passed safely to an npm-installed CLI is left out, and the chat says so without naming it. What Claude reads in any of these folders may be sent to the provider as part of the conversation.
- **A sub-agent can leave an empty folder in a git repository.** When the model asks for a sub-agent "in a worktree" and the project is a git repository, Claude itself makes a git worktree for it, with no request fat-g could refuse, and removes it afterwards: an empty `.claude/worktrees/` folder and a `.git/FETCH_HEAD` file can stay behind. That is the CLI's doing. fat-g writes nothing into your folders.
- **Which of your environment variables reach Claude.** The CLI inherits your environment as any program you start does, proxies and `ANTHROPIC_…` settings included. Of the variables named `CLAUDE_…`, only a reviewed list of standing settings passes: where the configuration is and how the CLI signs in, which backend it uses, certificates and network timeouts, what may leave the machine, which instructions load, and a conversation's limits. Whatever another Claude session exports for itself (its ids, its messaging socket and token), the debug-logging and telemetry switches, and anything that would change the model, the effort, the tools or the permission mode fat-g starts a session with, do not reach it. The list is [`src/main/providers/claude/environment.ts`](src/main/providers/claude/environment.ts).
- **Claude keeps its own record of the conversation, and fat-g never reads it.** Claude stores each conversation in files of its own, in its configuration folder — or, for an account you added, in the folder you picked for it. That record is what a resumed session continues from: what the model remembers of a conversation is Claude's, not fat-g's. What fat-g shows is its own copy in `conversations.sqlite`, written while the session ran. fat-g opens none of Claude's files, starts no process to read them, and Claude gives nothing of an earlier conversation back when a session is resumed. So a turn you made in the same conversation from Claude's own app is not shown in fat-g, though the model knows of it; and where fat-g's copy lacks a conversation's start, the chat says that earlier messages are not saved. If Claude can no longer reopen a conversation, the chat fat-g saved stays readable, and says so.
- **In a plan turn Claude saves its plan in its own configuration folder, and fat-g never reads it.** Before proposing a plan, the model writes it to a file under `plans/` in the account's configuration folder (`~/.claude/plans/` for your own account), which asks nothing. fat-g takes the plan's text from the proposal Claude sends over its stream, and neither reads nor deletes that file: remove it there yourself if you want it gone.
- **A first prompt that no model answered leaves a conversation in Claude that fat-g does not point to.** Claude saves a conversation as soon as it has a prompt. If a session's first turn failed, or you stopped it before a model spoke, fat-g has no reference for it yet: your prompt is in fat-g's saved chat, the next prompt starts a new conversation in Claude, and the unanswered one stays in Claude's own history until you delete it there.

## Session search

The search above the project list looks through session names and saved user and assistant messages, including Done and shelved sessions and hidden projects. It runs locally in memory, makes no network or provider call, and reads no project or CLI file. Side questions, sub-agent messages, tool activity, unsent drafts and queued messages are excluded. Plan files are not searched; a plan or review's text already sent as a message is searchable like other sent messages.

The index is built when message search is first used and is never written to disk. Results contain short plain-text excerpts for the Main window alone; the mini window cannot search or receive them. Queries and excerpts are never logged or saved. Closing the dialog clears its query and cached results; filter choices last only for the window's run. Removed messages and sessions are removed from the index, and closing or resetting the conversation store clears it. Search adds no file and changes no saved format ([decision 0035](docs/decisions/0035-session-search.md)).

## Files you open from a chat

An answer often names a file: `src/tides.js:12`, or a link to a README. In a session's chat such a reference is a control. Pressing it opens the file in a tab beside the chat, or, for a folder, has your system's file manager open that folder. This is the one way fat-g reads what is inside a project's folders, apart from images (see **Images an agent looks at, or an answer names**, below).

- **Opened by you, refreshed while visible.** fat-g reads a file when you press a reference to it, show its tab again, or choose **Reload**. While a Markdown or supported text file is displayed, it checks that exact file's modification time and size about every two seconds and rereads it when they change, after the same access checks. Checks pause while the main window is hidden or minimized, or you have text selected in the file, and stop when you leave its tab. Auto-refresh is best-effort: a failed check keeps the last displayed text and shows only `auto refresh failed` with a tooltip, then retries quietly. The toolbar gives the time and age of the last automatic text update; that timestamp lasts only for the open tab. Changes preserving both modification time and size may be missed; **Reload** always reads again. It reads nothing ahead and lists a folder only to find a file you pressed whose name was given without its folder.
- **Only inside the project's trusted folders, but for an image.** The file must lie in a folder of the session's project that you answered "Trust this folder?" with yes, and that is there. A reference that leads elsewhere — another folder, a link that points out of the project, a network share — is not read, and a line beside it says so. A share on another machine that is not one of your project's folders is never contacted.
- **Never the CLIs' own folders, nor fat-g's.** A file inside a provider's configuration folder (`~/.claude`, `~/.codex`, or the one its variable names), inside the folder of an account you added, or inside fat-g's data folder is never read by the general file reader, even where a project's folder is your home folder. A reference to an attachment already kept by fat-g can show that attachment through its owning store's checks, as described below. Any other file under a trusted folder can be opened this way, your other tools' files included: fat-g keeps no list of them.
- **Images an agent looks at, or an answer names.** An image the agent read — a picture Codex looked at with its image tool, a file Claude read with its Read tool — is drawn under that work's line in the chat, and an image a finished answer names is drawn under the answer, each as a thumbnail you can press to open in a tab beside the chat ([decision 0022](docs/decisions/0022-reading-project-files.md), item 15). For these fat-g reads the file when the chat draws it, without your pressing, and wherever it lies on this computer's own disks — in a temporary folder too, not only in your project's folders: the CLI has already read it and sent it to its model, and drawing it on your own screen sends it nowhere. Only a file whose name ends in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` is read so, and only a PNG, JPEG, GIF or WebP image by its own header, up to 5 MiB and 8,000 pixels a side. A path on a network share or a device, and a file inside a provider's configuration folder, an account's folder or fat-g's data folder, is never read by the general image reader, even through a link; already owned attachments follow the separate checks described next. Nothing of it is kept: not in `conversations.sqlite`, which keeps the path as the CLI wrote it, as it always did, nor in Chromium's cache, a log, the app state or the mini window. While fat-g runs it remembers the file's path, type, dimensions, modification time, byte size and a content fingerprint under an id the window draws it by, until you quit or remove the session. Each newly drawn thumbnail and each press to open it checks the original file again. Changed contents get a new preview id so an open tab can show the updated image; the fingerprint is never saved. **Copy image** and **Show in folder** on its tab act only when pressed, after the same checks.
- **A shown image artifact refreshes too.** Only the selected image tab checks its original file's modification time and size about every two seconds, after the same local-path and excluded-folder checks. Unchanged metadata reads no image bytes. Changed metadata settles before a bounded reread; the current image stays visible until its replacement loads successfully. Its toolbar then shows the update time and age, kept only until that tab closes or fat-g exits. Failures keep the previous image and retry quietly. Checks pause while Main is hidden or minimized and stop on leaving the image tab. Chat thumbnails and hidden artifacts are not polled. Immutable saved attachments need no polling read. Modification time and size may miss edits preserving both; clicking the reference or thumbnail reads again. No image copy or metadata history is saved, logged, sent to a provider or shared with the mini window.
- **An agent can look at an attachment you pasted.** When the agent's read or a file reference names an attachment in fat-g's data folder, main matches its exact stored path, hash and image type to the active conversation store, then checks its size, hash, header and owned location again. The chat's thumbnail and image tab reuse that attachment, with the same checks for Copy and Show in folder. Unknown files in the data folder, links and network locations remain refused. Nothing new is saved or sent.
- **Images Codex generates are kept with their chat.** fat-g takes image bytes already returned by the CLI, validates their encoding, size and image header, and saves them in the same hash-named `attachments/` files as pasted images. Their uses belong to assistant messages in `conversations.sqlite`; removing the conversation removes its uses and a file whose last use went. Identical images share one file. Thumbnails, the image tab, Copy and Show in folder use the existing attachment checks. A normal CLI history read can recover an earlier generated image if the CLI still returns its bytes; fat-g generates nothing again to recover it and never reads the CLI's saved-image path. Unusable or unsaved results have an explicit notice. No image bytes enter a log, the app state or the mini window.
- **Only text, up to 2 MiB.** A Markdown file is drawn as Markdown, with no image loaded. A text file on a fixed list of extensions and names — source and configuration files, `LICENSE`, `Makefile` — is shown as plain text. Any other file, `.env` among them, one larger than 2 MiB and one that is not text open a tab that says so: none of an unlisted file's content is read, and none of a file that is not text reaches the window. An image is drawn instead, as above.
- **Shown, never kept — but for a passage you send to a side question.** A file's text is in memory while its tab is shown, and nowhere else: not in `records.json`, `preferences.json` or any log, not in the mini window, and not put into `conversations.sqlite` by your opening it. One thing is kept, and only at your word: a passage you select in a file's tab and choose **Explain this** for is sent to the provider with your question, and saved with that question in `conversations.sqlite`, with the file's path and its lines, until you close that side question's tab or remove its session or its project ([decision 0025](docs/decisions/0025-asides.md)). What an agent read with one of its own tools is another matter: that is part of what the session did, and is kept with its chat (see [Sessions](#sessions)). Showing another tab drops it, and the file is read again when its tab is shown again. Your open file tabs are not saved either: they last until you quit, and a restart begins with none. Saved side questions reopen as tabs from their conversation metadata.
- **Show in folder** has your system's file manager show the file, selected. A reference to a folder has the file manager open it, after the same checks as a file; on macOS a folder whose name has an extension is shown selected instead, since an application or an installer is such a folder and the system would run it. fat-g never opens a file with another program: that would run whatever an answer names.
- **A reference's menu.** Right-clicking a reference, or pressing Shift+F10 or the Menu key on it, gives **Open**, **Show in folder** and **Copy path** — or, for a web address, **Open link** and **Copy link**. Copy path puts the full path fat-g found on your clipboard, after the same checks as opening it, and reads nothing of the file. Copy link copies the address as it was written.
- **Artifact controls act only when pressed.** Copy in a file or plan tab copies the entire shown source text to your system clipboard, including Markdown syntax. Copy image reads fat-g's stored attachment again, checks its size, hash and header, and converts its pixels to PNG in memory for the clipboard; an animated image copies its first frame. It saves no converted file. An image's folder button selects fat-g's stored attachment in the file manager, rather than the original dropped file. Plans have no folder button. A project file's full path is shown in its folder button's tooltip.
- **A web address opens in your browser.** A link to an `http:` or `https:` address, and such an address written by itself, is a control too: pressing it hands the address to your system's default browser, at once. The address is shown beside the link's text and in its tooltip before you press. fat-g itself requests nothing for it: no page, no title, no icon. An address with a user name or a password in it, and any other kind of address, is not handed over.
- **A chat without a session opens nothing.** Its links stay text: it has no project to hold a file to.

## The rules fat-g follows

- **No network of its own, and no credentials.** fat-g never reads the CLIs' credential files or your keychain, never calls a vendor's endpoints, and never asks you to sign in. The CLI you installed makes every authenticated call ([decision 0004](docs/decisions/0004-never-touch-credentials.md)). When you have Codex set up its sandbox, Windows asks for the administrator's approval itself: fat-g asks for no password, and sees none.
- **Account data stays in memory.** Your email, organization, plan and usage are shown while fat-g runs and never written to disk.
- **An account's folder is the CLI's.** When you add a second account of a provider you pick a folder for it, and its CLI keeps that account's login, settings and conversations there. fat-g stores the folder's path and your label for the account, and asks of the folder only whether it is there and what its real path is. It creates, reads, lists and writes nothing inside it, and removing an account leaves its folder as it is.
- **The model lists the CLIs report stay in memory.** They depend on your account's plan, so fat-g keeps them only while it runs, and writes none of them to disk.
- **Nothing is written into a project's folders.** fat-g creates no files there, provider files such as `AGENTS.md` or `CLAUDE.md` included, and changes no settings ([decision 0015](docs/decisions/0015-no-writes-into-project-folders.md)). It reads them for two things only: to check that a folder is there and what its real path is, and to show a file you open from a chat, as [Files you open from a chat](#files-you-open-from-a-chat) says ([decision 0022](docs/decisions/0022-reading-project-files.md)); the one text of a file it keeps is a passage you send to a side question. What a CLI writes during a session — a file the agent changes or a command it runs, at your approval or under the chat's mode; a hook or an MCP tool of your own configuration; a worktree Claude makes for a sub-agent — is that CLI's doing. fat-g never asks a CLI to save a permission rule, since Claude would write one into the project's folder.
- **Trust answers stay with fat-g.** fat-g asks "Trust this folder?" itself and keeps your answer in `records.json`. It never reads or changes the CLIs' own trust records (`~/.claude.json`, Codex's `config.toml`). Codex itself records a folder as trusted in its `config.toml` when a session starts under some modes ([With Codex](#with-codex)): that is Codex's write, which fat-g neither makes nor reads.
- **Conversations are in one file, and stay until you remove them.** Each query also keeps the speed tier requested for its turn (its id and name, or standard speed) in this conversation store, including side questions, so reply bars can retain their lightning bolts after a restart. This describes the request, not confirmed billing or speed served. No new file is written.  What you and the model said in fat-g's sessions, and what those sessions did between their messages — command lines, paths, command output, tool results, the provider's reasoning text and their sub-agents' work, each cut to a fixed size ([decision 0024](docs/decisions/0024-a-sessions-work.md)) — and the questions you asked beside a session, with their passages and their answers ([decision 0025](docs/decisions/0025-asides.md)), and the questions a session asked you, with your answers ([decision 0026](docs/decisions/0026-questions.md)), and what a session asked leave to do, with what you decided and what you granted, and each chat's mode ([decision 0027](docs/decisions/0027-execution-permissions.md)) — is in `conversations.sqlite` and nowhere else in fat-g's files: not in `records.json`, not in a log, and never in the mini window. Only your own Remove, or an explicit close of a side question's tab, deletes any of it; a missing or unreadable `records.json` never does ([decision 0019](docs/decisions/0019-conversation-store.md)). fat-g lists only the sessions it created, and it never reads the CLIs' own session stores: where a CLI can give a session's earlier turns back, as Codex's can, they come from the CLI itself, asked for by that session's reference.
- **A session's live status stays in memory.** Its status, its current action, its list of sub-agents, what it is waiting for and how full its context is are shown while fat-g runs and never written to disk. That a question is waiting for your answer, or a request for your decision, is held in memory too, so one that was waiting when fat-g closed is not waiting when it starts again: its card says that it was not answered. Which mode a session's process confirmed, whether a grant is still live, which modes an account can use, and where a sandbox setup stands are in memory as well: after a restart every grant reads as ended, and an account's sandbox is asked of Codex again. What it did is conversation content, and is saved with its chat as the rule above says; so are when a turn started and how it ended.
- **No permission rules of fat-g's own, and none saved in a CLI.** fat-g keeps no list of what is allowed, matches no request, and answers none you did not. What it remembers of a decision is the decision itself, in the chat. The one thing that outlives a request is the CLI's own grant for the session, which ends with the session's process; fat-g sends no rule a CLI would keep longer, passes no flag that bypasses a CLI's permissions, and sets up Codex's sandbox only when you press Set up ([decision 0027](docs/decisions/0027-execution-permissions.md)).
- **A file fat-g cannot read is left as it is.** fat-g says why, and changes it only when you choose **Start fresh** and confirm it — and then moves it aside, never deletes it ([decision 0005](docs/decisions/0005-preferences-compatibility.md), [decision 0011](docs/decisions/0011-records-store.md)). The same holds for the conversation store, whose files are moved aside together; while it cannot be read, your sessions stay listed and nothing is sent ([decision 0019](docs/decisions/0019-conversation-store.md)).
- **Logs hold counts and kinds.** fat-g writes no log file. What an installed fat-g prints to its console says, for example, "loaded 12 projects, 1 unreadable; 30 sessions, 0 unreadable, 0 without a project", "codex reported 9 models, 2 hidden", "turn ended (completed), 10 so far", "removed 1 conversation" or "override ignored (invalid)", or names an error's kind such as `EPERM` — never a prompt, a message, the CLI's own words in a chat, a project's or a session's name, a path, a session reference, what a session is doing, a command or a change a session asked leave for, what you decided of it, what a grant covers, a value from your files or an error's message. Of a line from a CLI that is too long to read, fat-g looks at its first bytes for two things alone — whether it is a request, and that request's id — and prints, keeps and shows nothing else of it. Of a file you open it prints only why one was not read, as a kind: "read refused (outside)" — never the file's path, the reference that named it, its text, or an address you opened. A development run prints errors in full, to the developer's own terminal.
- **Opt-in development lifecycle trace.** `npm run trace:live` starts a development build with `FATG_TRACE_LIFECYCLE=1`. Only an unpackaged app honors this switch. It prints timestamps, process IDs, request numbers, fixed operation/outcome names, numeric error codes and cleanup results. Codex's resume refusal text is inspected in memory only to classify the exact active-writer wording; the text and conversation ID are discarded, and the app's error handling is unchanged. The separate Windows launcher saves only these sanitized lines and observed process IDs, parent IDs, creation times and exit observation times in `spikes/output/m15/live-trace-*.jsonl` in the development checkout (gitignored, at most 8 MiB per run). It continues observing after fat-g exits and sends no prompts. It saves no ordinary console output, command lines, paths, model/account details, prompts, answers, thread references, tool output or raw error text. These developer-created diagnostic files are not part of installed fat-g's data folder; delete a trace file when finished with it.
- **The mini window sees the sessions running or waiting on you, and little else.** (fat-g's code and decision records call it the Pet.) It stays on top and shows in screen shares while visible. By default it hides while the main window has focus and returns when you switch away; you can turn this off beneath Show the mini window in Settings > General. This choice is saved in `preferences.json`; focus changes themselves are never saved. For each session whose turn runs, or that waits on your answer or decision, or that finished or failed and you have not looked at yet, it receives the session's name, its project's name, its state in fat-g's words — "Reading…", "2 Questions", "Error" — never the file or the command it works on, when its turn started, how many sub-agents run, its effort and speed, and the image files its avatar draws, by their ids ([decision 0010](docs/decisions/0010-pet-deferred.md)). Its status can describe a sub-agent wait using only a closed reason and known count, without child names or task text. Before Thinking, a previous generic status may remain visible for up to 400 ms; the mini window receives only its kind, safe waiting metadata and original deadline. These fields stay in memory and are never saved. It never receives your other sessions, your projects' folders, a prompt or a message of a conversation, a draft, a queued message or an image, an avatar's folder or family names or the avatars fat-g found, what a session asked leave to do, what you decided or granted, a chat's mode, which modes an account can use, how many chats are saved, your account identity, or the model lists and the path of your `catalog.json`. It can decide no card, change no mode and start no setup: a press on a session there opens it in the Main window, as a press on it there would. It can request rollover, click and right-click sounds by fixed cue names; the Main window alone plays them, and the mini window receives no audio filenames, catalog or preferences. It can read no file, show none in its folder and open no address.

## Automatic provider detection

fat-g checks for installed CLI executable files at launch and when you return to its Main window, at most once a minute; Accounts also offers **Check for providers**. These checks read file metadata at the configured executable path, its current PATH and the providers' known install locations. They open no account or credential file and make no network request. Focus checks start no CLI and do not refresh account, usage or model data. The existing shell PATH preparation is cached for the run; a PATH-only installation can require restarting fat-g.

A newly detected provider starts normally through its installed CLI unless you switched it off. A missing provider becomes inactive and loses its usage box; running sessions, workers and side questions can finish. Your saved provider/account choices and sessions stay in place. The first results and later changes appear only in the Main window. Only the acknowledged installation booleans above are saved, through the same atomic `.json.tmp` write as other JSON files. Inaccessible paths retain the previous result. Unreadable or incompatible detection history is left unchanged; discovery continues in memory and Accounts explains the problem.
