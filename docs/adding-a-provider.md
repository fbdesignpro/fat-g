# Adding a provider

A provider is an AI CLI fat-g works with — Claude and Codex today. Each is a **module**: one folder under `src/main/providers/`, holding everything fat-g knows about that CLI. Adding one means adding a folder and one line to the list of built-ins; nothing in fat-g's shared code names a provider.

This guide walks through the module in the order it is built, then lists the files outside it that change, and the rules every provider follows. The two built-in modules are the worked examples: `claude/` talks to its CLI through short control sessions and, for a chat, one process a session; `codex/` through one long-lived app-server connection, and an app-server of its own for each chat. A third provider, defined only in a test folder, proves the path: [`tests/support/example-provider.ts`](../tests/support/example-provider.ts).

## The module, step by step

Everything below lives in `src/main/providers/<id>/`. A module imports only `src/shared/` (the contracts and the provider kit) and its own folder: never another provider, never `src/main/` internals, never Electron, never `child_process`. ESLint enforces this, and [`tests/architecture/boundaries.test.ts`](../tests/architecture/boundaries.test.ts) proves the fence holds.

### 1. The folder and its `index.ts`

`index.ts` exports a `create<Name>Definition(options)` returning a `ProviderDefinition` ([`src/shared/provider-kit/provider.ts`](../src/shared/provider-kit/provider.ts)): the descriptor, the catalog defaults, the installation guide, the executable names and install-folder hints to look in, the child environment policy, and a `factory` that builds the runtime `AgentProvider` for one generation.

The `options` carry what tests and smoke runs need — a fixture script to run instead of the CLI, shorter deadlines. Production passes none of it.

Installation discovery ([decision 0037](decisions/0037-provider-discovery.md)) uses the definition's executable names and installation-directory hints automatically, once per provider for all its accounts. Keep them aligned with the adapter's own `detect`: the shared scan checks file availability only, never calls the factory, never reads a configuration folder, and never checks login or usage. In `detect`, resolve with `every: true` and pass the resolution's `candidatesOf` to `newestCandidate` (`src/shared/provider-kit/newest.ts`) with the CLI's version check and parser: it keeps the newest version found ([decision 0003](decisions/0003-detect-user-installed-clis.md)). Smoke definitions must name only fixture executables. No provider-specific discovery UI or shared branch is needed. For a versioned desktop runtime, an install hint may declare `versions: { children: 'version' | 'hash', nested?: 'version' | 'hash', suffix: [...], includeRoot?: true }`; the root comes from its usual `base` and `segments`, and `nested` names one build level inside each child. The process layer enumerates only that folder (and, with `nested`, its children's), bounded to 128 immediate entries each, after fixed install paths. Use `applications` for macOS `/Applications`, or `mac-applications` to check both `~/Applications` and `/Applications`, in that order. Keep every hint inside a known executable location, never an account/configuration folder, and record evidence for the layout.

### 2. The descriptor

`descriptor.ts` exports a `ProviderDescriptor` ([`src/shared/contracts/provider.ts`](../src/shared/contracts/provider.ts)): the id (lower case, stable forever — preferences and records key on it), the display name, the install guidance sentence, the login command a user runs in their own terminal, the minimum poll interval, and the capabilities: whether it reads an account, how it reads usage, whether it runs sessions, whether it can read a session's earlier conversation back (`history`), whether its sessions take a project's other folders (`otherFolders`), whether it reports its models, whether and how it answers a question asked beside a session (`asides`, §9), whether and how its sessions ask the user a question (`questions`, §9), the modes its sessions run under, or none (`permissions`, §9), and whether its sessions report how full their context is (`context`, §9).

The descriptor is plain data; it crosses into both windows. It holds no resolved user path, no address and no look. Its optional `executableHelp` supplies a CLI command name and static example folders per platform for Accounts' **How to find the CLI executable** disclosure; keep those examples in the provider module and use placeholders such as `%LOCALAPPDATA%` or `~`, never a path read from the user's machine. The renderer supplies the common selection and recovery instructions.

### 3. `catalog-defaults.json`

The module's defaults for the model catalog ([decision 0013](decisions/0013-catalog-format-and-layers.md)), imported by `index.ts` and passed on unparsed as `catalogDefaults`. They say how the provider looks and how its levels are shown — never which models it has: the models come from the user's own CLI (step 8), so no list goes stale in a release.

- **`presentation`** — the usage bars' colour (`#rrggbb`) and the provider's mark as SVG path data (`viewBox`, `path`: commands and numbers only). The mark is **original**, drawn for fat-g — never the vendor's logo.
- **`presentation.stream`**, optional — the provider's light stream in the status bar: `ground`, what a running bar's ground warms to, and `lights`, six tones, darkest first, all `#rrggbb`. The tones are composited with `plus-lighter`, so they **add** rather than cover: a blue or a green ramp wants noticeably less lightness than a warm one for the same field, since its luminance sits in the green channel, which has the headroom to clip overlapping rectangles to near-white. Which of the twelve rectangles takes which tone is the stylesheet's, not yours. A module that declares no stream leaves its running bar black with its word in white, as a provider this build does not have is drawn.
- **`canRequestSpeedTier`** — whether fat-g can ask this CLI for a faster tier at all.
- **`efforts`** — every effort level's id and label, and `"caution": true` for a level fat-g must never pick by itself. Their order is the order levels are shown in. A level the CLI reports that is not here is shown by its id.

The catalog checks the file against the contract when fat-g starts ([`src/main/catalog/defaults.ts`](../src/main/catalog/defaults.ts)): a file that fails stops the start, as a build defect, and so does a `models` field. A user may adjust the lists but never the look ([`catalog-override.md`](catalog-override.md)).

### 4. `installationGuide`

An `https:` address, set on the definition: where Settings' **Installation guide** button leads when the CLI is not found. It is checked at start. The page sends only the provider's id; main opens the address, so no address ever crosses to a window.

### 5. Several accounts: the instance declaration

A provider whose CLI keeps an account's login, settings and conversations in one configuration folder, and lets a documented variable move that folder, can run as several accounts ([decision 0017](decisions/0017-provider-instances.md)). The module says so with `instances` on its definition, an `InstanceSupport` ([`src/shared/provider-kit/provider.ts`](../src/shared/provider-kit/provider.ts)), kept in `descriptor.ts`:

- **`variable`** — the variable's name, such as `CODEX_HOME`.
- **`defaultFolder`** — the CLI's documented default folder, as segments under the home folder, such as `['.codex']`. The first account runs there unless the user's own environment moves it.
- **`withhold`** — the inherited variables an added account's children must not receive, by name and by prefix: whatever the CLI's documentation says is used before the folder's own login, such as an API key, a token, a backend selector or a base URL. Proxy and certificate variables stay. Read the vendor's page when writing the list, and say in a comment where each name comes from.

That is all the module does. fat-g's shared code gives each account its own runtime of the provider, sets the variable for an added account's processes and for nothing else, and offers **Add account** in Settings. Nothing outside the module names the variable. A module without the declaration has one account and no Add account.

Before relying on it, trace the CLI as M14b's spike did (`spikes/m14b/`): with the variable pointed at an empty folder beside the user's own, the empty one must read as signed out while the other reads its account. A CLI that keeps a login outside the folder cannot have several accounts this way.

### 6. Detection

`detect()` finds the installed CLI through `context.processes.resolve` (an explicit path from preferences, then `PATH`, then the install-folder hints) and runs one bounded version probe. It authenticates nothing and starts no session. fat-g only ever launches the CLI the user installed ([decision 0003](decisions/0003-detect-user-installed-clis.md)).

### 7. Account and usage

`getAccount()` asks the CLI who is signed in, and `getUsage()` reads the usage windows; both return the normalized results of the provider kit. Every child goes through `context.processes`, which bounds it, records it and confirms it gone. A provider whose CLI pushes changes implements `subscribe()` and sends `usage`, `invalidate` and `connection` events.

Normalize at the edge: parse replies with loose Zod schemas, take the fields you need by name, bound every string, and let nothing else of a reply leave the module. Account data stays in memory.

### 8. The model report

This is where a provider's models come from: without a report it lists none, and the user's `catalog.json` has nothing to adjust. A provider whose CLI lists its models without spending a turn reports them: set `capabilities.models`, and send a `models` event with a `ModelReport` — the rows mapped into the contract's shape, each id and string bounded, a row that cannot be read left out and counted, and no event at all when no row could be read. The catalog lays the user's override over the report and keeps the report in memory only.

Unless every usage read reports, also implement `reportModels(signal)`. The catalog calls it after a usage read during which no report arrived: the runtime's first, one that finds the account changed, one a Refresh caused, and otherwise once an hour. It sends only what the provider's usage reads may send, and a failed read changes nothing — not the status, not the account, not the usage. The two patterns: Codex asks `model/list` over the connection it holds and sends nothing while it is not connected (`codex/models.ts`, `codex/app-server.ts`); Claude runs the usage session's launch sending only `initialize`, for the accounts whose usage read runs no session (`claude/models.ts`, `claude/index.ts`).

### 9. Sessions

A provider whose CLI can run a conversation sets `capabilities.sessions` and gives its `AgentProvider` a `sessions` facet (`SessionFacet` in [`provider-kit/sessions.ts`](../src/shared/provider-kit/sessions.ts)). Without both, the New session popup offers it no tile and its sessions say so in place of the chat's input.

- **`start` and `resume`** return a `ProviderSession` at once and launch nothing: its first `send` starts the CLI, in the folder and the instance scope it was given, and resumes by the reference a `session-started` event reported. `stop` ends the turn; `closed` resolves once the process is confirmed gone, or says it could not be.
- **Events** are the normalized `AgentEvent` union of [`contracts/agent-events.ts`](../src/shared/contracts/agent-events.ts): whole messages by phase, a message's pieces while it is written, what the session does between them, the current action, workers, the values in force, notices by kind, and each turn's end. Every string is cut to its bound in the module; the CLI's own words leave it only as a notice's bounded detail. fat-g records what these events carry in its conversation store ([decision 0019](decisions/0019-conversation-store.md)), so nothing else of a frame may be put in them.
- **A message as it is written, or whole** (M19). A provider whose CLI tells a message while it is written sends `message-delta` events for it: one with an empty text when the message opens, with the message's phase or, where the CLI does not say it until later, none (the chat draws a text of no phase as it draws an answer), then one for each piece, all under the id the whole message will have. The whole `message` then completes it, and is the authority for its text: fat-g shows the pieces as they come, keeps what was received ([decision 0019](decisions/0019-conversation-store.md), item 14), and replaces it with the whole message's text. A turn that ends with a message still open leaves it as received, marked unfinished. A provider that sends no `message-delta` loses nothing: its whole messages are shown and stored as before. Streaming is no capability and nothing declares it; the facet's contract (`tests/sessions/facet-contract.ts`) runs against both forms and holds a module to the rules — a delta names an open message of the running turn, none follows the whole message, and the pieces put together are the whole message's text unless the provider itself says otherwise. A delta that breaks one is dropped in the module and counted by a reason, never logged with its text. Only an assistant's message streams.
- **What a session does, as it does it** (M20a; [decision 0024](decisions/0024-a-sessions-work.md)). Each thing the CLI reports the agent doing — a file read, a search, a command, an edit, a tool call, a web search, a wait — is an `activity-started` when it begins and an `activity-ended` when it ends, under the CLI's own id for it. The start says its type, from the closed list in [`contracts/activity.ts`](../src/shared/contracts/activity.ts), the CLI's name for it, one line of summary, its input and the files it names; the end says its status, as the CLI reports it, with its output, its exit code and its duration where the CLI gives them. A type the module does not know is `other`, with its name and nothing else read of it. Rules the facet's contract holds a module to (`workFaults` in `tests/sessions/facet-contract.ts`): an end follows a start of its id, under the same turn; no start follows an end; and an end with no start is dropped in the module, never sent.
  - **Cut in the module.** Every field is cut to its bound before the event is made: `cutParts` cuts a start's or an end's fields and answers what was cut, which the event carries. An output is kept as its first and last halves. fat-g records what these events carry, so nothing of a frame goes into one that the item's own fields do not name.
  - **As reported.** An edit's changes are what the CLI reported with the item; a module reads no file to fill one in, and a file an item names is a path as the CLI wrote it.
  - **A second start replaces.** An `activity-started` for an id that is still open replaces that item's fields and opens nothing: it is how a checklist, one item a turn, is told at each update. No event ends a checklist; fat-g completes it with its turn.
  - **An end may come late.** A completion the CLI sends after its turn's end is still sent, under that turn's id, and ends its item. An item whose end never comes is left as it is: fat-g reads it as unfinished once its turn has ended.
  - **Thinking** is an item of type `thinking`, with what text the CLI emits of it and none otherwise. It is kept, and the chat does not draw it.
- **A sub-agent's work, under its id** (M20a). A message, a message's pieces and an activity that are a worker's carry `workerId`, the id its `worker-started` gave, and the id of the turn of the session's that started it — also after that turn has ended. fat-g files them under the worker and shows them in the worker's tab, never in the session's own chat, and a worker's message is never the turn's answer. The item of the session's own that started the worker is an activity of type `worker`: its `pairedWorkerId` names the worker, on its start or on a second start once the CLI has said which worker it is, and the module ends it as the worker ends, just before `worker-ended`. A launch that failed before any worker started is that same item with no pairing, ended as failed with the CLI's error as its output.
- **A question beside a session** (M20b; [decision 0025](decisions/0025-asides.md)). A provider whose CLI can answer a question beside a conversation — against what the conversation holds, adding nothing to it — declares it in `capabilities.asides` and gives its sessions `ask` and `stopAside`; one that cannot declares `'none'`, has neither member, and is offered no Explain this and no Side question.
  - **The capability says what an aside is on this provider:** `streamed`, whether its answer arrives as it is written or whole, and `tools`, `none` or `read-only`. The aside's tab says the second in one line, and waits with a line of its own where the first is false. Declare what the route gives, never what it could.
  - **`ask(aside)`** takes the aside's id, the id of its own turn, the text to send, the id fat-g made for the message, `history` — the aside's earlier questions with their answers, oldest first, for a route that keeps nothing of an aside — `throughTurn`, the provider's own id of the session's newest turn whose end it reported, or none, and the session's effort. It starts the session's process if none is up, as a prompt would, with no turn of the session's. A second question of an aside whose turn runs is not taken: fat-g asks one at a time.
  - **Every outcome is an event that names the aside.** `turn-started`, `message`, `message-delta`, `activity-started`, `activity-ended`, `notice` and `turn-ended` each carry `asideId` and the aside's own turn id; nothing else is told for an aside — no reference, no action, no value in force. A reply that holds no answer ends the turn as failed with the `no-answer` notice, and is never sent as a message. A message whose reply names another model than the session's carries it as `model`.
  - **Beside the session's turn, never in it.** An ask is taken while a turn runs, and several at once; the session's own events are the same with an aside running as without, and the facet's contract holds that. Nothing of an aside is sent into the session's conversation.
  - **`stopAside` stops that aside alone.** It never ends the session's process, and `stop` never stops an aside. One the CLI does not confirm ends the aside's turn as the module's own, `reported: false`, with a `stop-unconfirmed` notice, and what still comes for it is dropped and counted. When the session closes or its process is lost, each open aside's turn is ended before the session's own.
  - **What it may be sent is in the module's one file.** Claude's side question and its cancel are the seventh and eighth sends of `chat-wire.ts`; Codex's fork is one more method of a session's set in `methods.ts`, sent from one place with fixed fields. A confinement test and a mutation hold each.
  - **A command of the CLI's own that fat-g must not send** is the facet's `intercepts`: a function that says, for a prompt, which notice answers it, or none ([decision 0023](decisions/0023-cli-commands-pass-through.md)). Main then answers the prompt as a turn of its own and never sends it. A provider with no such command leaves the member out.
- **A question the session asks the user** (M21; [decision 0026](decisions/0026-questions.md)). A provider declares in `capabilities.questions` how its CLI asks: `none`, `blocking` — a request the CLI makes and holds its turn on — `async` — a question asked in a message, the turn going on or ending — or `both`. fat-g draws each as a card in the chat and sends nothing until the user presses Submit.
  - **A blocking question is two events and one member.** `question-raised` carries the request's id as the CLI gave it, the id of what carried it (`sourceId`: the tool's use, or the request's item), the turn, the worker where a sub-agent asked, and the questions — bound them with `boundQuestions` of [`contracts/interaction.ts`](../src/shared/contracts/interaction.ts), which cuts each text to its bound and says what was cut. The module holds the request before it sends the event, since main may answer from inside it. `answer(requestId, answers)`, present exactly where the provider declares `blocking` or `both`, then takes the user's answers, one per question in the questions' order, each the places of the chosen options and the typed text; or `null`, where main could not place the request, which the module refuses as it refuses any request it grants nothing for, with the `request-refused` notice. `question-resolved` says what became of a request, by a reason: `confirmed` when the CLI says it took the answer, `withdrawn` when the CLI took the request back, `dropped` for one still held when its process was lost — sent before the ends the module makes for that loss.
  - **Encode from the request as it came.** The module keeps the raw request, in memory, until it is answered or abandoned, and writes the CLI's own keys and each option's whole label when it encodes: a label cut for display may no longer tell two options apart. A request the card could not ask whole — `canShow` says which — is refused on the wire, never cut.
  - **A Stop is left to the turn's end.** A request held when its turn is stopped is not said dropped by the module: the turn's end withdraws its card. An answer that comes for a request no longer held is nothing.
  - **An async question is a message's `questions`.** The message carries them, as Codex's does; fat-g makes the card with the message, and the user's answer is a prompt of the session's, in fat-g's words, sent as any prompt. Nothing more is asked of the module. A history page's message with questions makes a card too.
  - **Nothing of a question reaches a log.** Count kinds; never write a question, an option or an answer anywhere but the event. A secret question's answer is sent and kept nowhere.
  - **The contract** runs three tests for a provider that declares a blocking question (`{ questions: true }`, with a harness that names a prompt whose turn asks): an answer that completes its turn, a request main refuses, and one a Stop leaves to its turn's end. A provider that declares none is held to having no `answer` member.
- **What a session may do: its mode, approvals, and the CLI's own session grant** (M22; [decision 0027](decisions/0027-execution-permissions.md)). A provider whose CLI can be held to more than one policy declares its modes; fat-g resolves which one a chat has, hands it to the module at every start, and draws the CLI's requests for leave as cards. The CLI enforces the mode: a module names it, checks it, and never imitates one.
  - **Declare `permissions`.** `capabilities.permissions` is a `PermissionCapability` of [`contracts/permissions.ts`](../src/shared/contracts/permissions.ts), or `null` for a provider that declares none, whose sessions then run as they always did. `modes` lists each mode: an `id` of the provider's own, lower-case words joined by hyphens and stable for good, since a chat, a default and a turn store it; a `label`, fat-g's name for it and never the CLI's flag; a `description`, one line saying what runs without asking, by what a capture showed, and for a mode where nothing asks the CLI's own word for it; `asks`, whether it sends the CLI's requests to the user; `reading`, true for exactly one mode, which asks nothing and under which every request to act is refused; and `transitionsFrom`, the ids a change on the live process reaches it from. `fallback` is the mode a chat has where nothing chose one: one that asks, or the reading one, never one that acts unasked. `setup` is `null`, or — where an account may need a set-up step of the CLI's own — the three lines its dialog shows in the provider's words: what the setup `changes` on the machine, by the vendor's own description; whose `approval` it asks for, and how; and what may be happening while it is `waiting`. The page words nothing of a CLI or a system itself. `inherited` is the one line drawn under every list of the modes, saying what the user's own configuration lets act with no card, and `rules` the one line beside a session's grants on what is known of the CLI's own rules. No description promises a card before every action. The CLI's own words for a mode — a flag's value, a policy's name — stay in one file of the module (`claude/chat-modes.ts`, `codex/modes.ts`), and no shared file holds one.
  - **The facet's three members go together.** `modes()`, `transition(from, to)` and `onModesChanged(listener)` are present exactly when `permissions` is not null. `modes()` answers one `ModeAvailability` for each declared mode, for this account, as far as the module knows now: `available`, and a `reason` exactly where it is not — `unvalidated`, no capture shows a turn under it on this CLI version; `needs-setup`; `cli-refuses`, the CLI takes it only with a flag fat-g never passes; `platform`; `pending`, a check of the account whose answer has not come — with `setup`, whether a Set up control is offered for it; `records`, whether choosing it makes the CLI write into its own configuration; `unconfined`, whether the account has no sandbox for it; and `places`, where a sandbox mode can write beside the session's folder, read from what the CLI reported and never held as a constant. Asking may begin a read whose answer comes later: say so through `onModesChanged`. Keep one constant of the modes a capture shows a turn under, and list a mode left out of it as `unvalidated`. `transition` answers `idle` for a change the CLI makes on a live process and `restart` for every other, and agrees with the declared `transitionsFrom`.
  - **`SessionStart.mode` and `processKey`.** `start` and `resume` are handed the id of the mode main resolved for the chat and checked against the account. The module maps it to its CLI's fields, names it when the process starts, and checks what the CLI reports before any prompt goes. A start that names no mode, or one the module does not know, runs under the reading mode: never one that acts. Each confirmation — the start's check, a change's reply — is an `in-force` event whose `mode` is that id, never a native word. A start that reports another policy takes no prompt: the turn ends as the module's own, `failed`, with a `policy-mismatch` notice whose `detail` is what the CLI reported, bounded — or, for the reading mode, the notice a restricted start that was not taken has always had. `processKey` is main's key for the process, by which fat-g tells whether a grant is still live; a module keeps and reads nothing of it.
  - **`setMode(mode)`** is present exactly when some change of the provider's is `idle`. It is asked with nothing running on the process, resolves `{ confirmed: true }` once the CLI has confirmed the change and `{ confirmed: false, detail }` where it refused it or reported another, and never rejects. Hold the target while the request waits: a CLI that reports the change in a frame of its own may send that frame before its reply is read, and it is the change reported, not a violation. Every other change is main's to make: it closes the session and starts another under the new mode.
  - **A request for leave is two events and one member.** Under any mode but the reading one, a request the module can place is held, as a question is, and said as `approval-raised`: the turn, the worker where a sub-agent asked, `requestId` — the module's lossless key for the request, so that a number and a string of one spelling are two — `sourceId`, the CLI's id of what carried it, which the action's own activity shares, and `request`, an `ApprovalRequest` of [`contracts/interaction.ts`](../src/shared/contracts/interaction.ts): whether it is a command, a file change or a tool's use, the CLI's name for what asks, one line of summary, the working folder where the request names one, the paths, whether the CLI said one lies outside the folders the session was given, the model's own reason, what the CLI's own offers would grant beyond this action (`authority`, each a kind and, for a change of mode, fat-g's id of the mode), the whole action (`detail`), the `choices`, and `grant`. `decide(requestId, choice)` then takes one of `approve`, `approve-session` or `deny` and writes the CLI's reply from the request as it came; it returns a promise that resolves `true` once that write went and `false` where the process did not take it, in which case the module also says `approval-resolved` `dropped` and ends the process, and it never rejects. `null` in place of a choice refuses the request with the `request-refused` notice, as main asks for one it cannot place. `approval-resolved` says what became of a request: `confirmed`, the CLI's word that it took the decision, which says nothing of the action's success; `withdrawn`; `dropped`, for one still held when its process was lost or closed, sent before the ends the module makes; and `changed`. `decide` is present exactly when the descriptor declares a mode other than its reading one.
  - **Whole, or refused.** `approvalOverBound` says whether a request fits the card: 32 paths, 32 changes, 16 choices, a path of 2,048 units, a command or an input of 65,536, a file change of 1,048,576. One past a bound, one that lacks a field its action stands on, and one that names something the module does not hold are refused on the wire, with a `request-refused` notice that carries `bound` and `size` where a size is why, and no event. Cut the labels — the tool's name, the summary, the reason — and nothing else. Read no file to fill a change in.
  - **A repeated delivery is compared before it is counted.** A request that comes again under an id the module holds is the same request, counted and answered by the one reply, only where its whole payload equals the hold's. One that differs is refused on the wire, the hold is let go, and `approval-resolved` `changed` withdraws its card — `question-resolved` `changed` for a question, since the hold is one for both kinds. Nothing of the second payload is kept.
  - **A session grant: eligibility and reply.** `approve-session` is among the choices, and `grant.covers` set, only where the CLI's own request makes it eligible for a grant that lasts for the session's process and no longer; `covers` is the CLI's own words for what it covers. The reply is fixed by the choice, whatever the request offered: the CLI's own offer at the session's scope, and never another scope, a mode, a folder or a rule the CLI would save. An offer fat-g does not pass back is told in `authority`, to be said on the card. Where the CLI's only offer is a change of mode, `modeThatWouldStop` names fat-g's id of it, and the card changes none. The record of a grant is fat-g's, kept with the decision and keyed by `processKey`: a provider's session has no list of grants, and a module answers nothing from one.
  - **A declined action, and the notices.** An action that was refused leave ends its activity `declined`, with `declinedBy` where the module knows who refused it — `user`, or `rule` for a rule of the user's own configuration — and never `failed`. Two notice kinds are M22's: `policy-mismatch`, and `line-too-long`, with the line's `size`.
  - **A line over the session's limit** is handed to the module as its first bytes and its size. `peekLine` of [`provider-kit/ndjson.ts`](../src/shared/provider-kit/ndjson.ts) reads them for two things alone, given the kinds the module's protocol waits for a reply on: whether the line is a request, and its id. A request with an id is refused by that id, with the notice naming the line as its bound, and the turn goes on. One that is or may be a request and has no id stops everything the process runs — the turn and its workers by `stop`, each aside by `stopAside` — with `line-too-long`; with nothing running, and for any other line, it is skipped and counted. Keep, log and send nothing else of the line.
  - **`sandbox`** is the facet's member for a CLI that has a setup of its own, present exactly when the descriptor says `permissions.setup` and the system has one: `state()` answers where the account's setup stands and what the CLI last answered of its sandbox, and `act('start' | 'stop-waiting')` sends the CLI's one setup request, at the user's press alone, or lets go of one whose end has not come. A setup has an end the module always reaches, an end it did not hear being `unknown`, and nothing is sent again but at a new press. Its methods are a set of their own (`codex/methods.ts`).
  - **Nothing of a request reaches a log.** Count kinds; never write a command, a path, a change, a reason, a decision or what a grant covers anywhere but the event.
  - **The contract** runs ten tests for a provider that declares modes with one that asks (`{ permissions: true }`, with a `PermissionHarness`: the declared `capability`, the `mode` its other tests start under, an `asking` mode, a `prompt` whose turn asks leave for one action, a `session` pair — a prompt whose request can be granted for the session, and a later one the grant covers — an `idle` change where the provider declares one, and `mismatchNext`, which makes the next start report another mode): the declaration and the three members; a start under a declared mode, said confirmed before anything the model says; a start that reports another mode, which takes no prompt; a change on the live process, or no `setMode` where none is declared; an approval for once, a denial, a grant with the next request unasked on the same process, a request a Stop leaves to its turn's end, one main refuses, and one held when the session is closed, said dropped first. A provider that declares none is held to having neither `decide` nor `setMode`, and none of the three members. The example provider takes `modes: 'restart'` or `'idle'` for two modes under names no built-in has, its reading one among them.
- **A plan turn** (M22b; [decision 0029](decisions/0029-plans.md)). A provider whose CLI can be asked to plan before it acts declares it, and main does the rest: the plan's record, its line, its panel, its tab and its decisions are fat-g's, the same for every provider.
  - **Declare `plans`.** `capabilities.plans` is a `PlanCapability` of [`contracts/plans.ts`](../src/shared/contracts/plans.ts) — the modes a plan turn may start under, and the words the Plan toggle shows under the others — or `null`, and the toggle is disabled with its reason. List only the modes a capture shows a plan turn under.
  - **`plans()`** on the facet answers whether the account's CLI takes a plan turn now. Leave it out where it always does; a CLI that refused what a plan turn needs says so here until fat-g restarts, and nothing else of its sessions changes.
  - **`TurnRequest.plan`** asks for a plan turn, in the CLI's own plan mode, and the chat's mode is never changed for it. **`plannedBefore`** is set on every other turn of a session a plan turn ran on: where the CLI's plan mode stays with its conversation, as Codex's does, name its default mode then.
  - **A plan proposed in a request** — a tool's use the CLI holds its turn on, as Claude's `ExitPlanMode` — is `plan-raised`, with the request's id, its tool use's id, the turn and the plan's whole text, then the facet's `decidePlan(requestId, answer)`: feedback with the user's text, execute, or cancel, each the CLI's own answer, or `null` to refuse it. It resolves whether the reply's write went. A request the CLI takes back is `plan-resolved`.
  - **A plan written as an item** of the turn, as Codex's is, is `plan-delta` events — the first, which may be empty, opens it — and one `plan-completed` with the whole text, which is the version. No request waits on it: its decisions are turns main starts, whose prompts main composes with the plan's block.
  - **The text comes from the wire alone.** Never read a plan file the CLI writes, and never cut a plan: its bound is `MAX_PLAN_TEXT`, the line's, not a message's. A request over the session's line limit is told by `peekLine`'s tool name, and refused with the `plan-too-large` notice.
  - **Nothing of a plan reaches a log.** Count kinds; never write its text or its title anywhere but the event.
  - **The contract** runs its plan tests for a provider that declares `plans` (a `PlanHarness`: the capability, `request` or `item`, a prompt whose plan turn proposes a plan, the mode to start under): no plan turn where none is declared, a plan proposed and each decision taken, and `plannedBefore` on the turn after.
- **Images, a message during a turn, and commands** (M23; [decision 0030](decisions/0030-attachments.md)). Each is a field or a member a provider has or not; the composer, the store and the queue are fat-g's, the same for every provider.
  - **Images are `TurnRequest.attachments`**: each a `PromptAttachment` with its media type, the path of its file in fat-g's own folder and its bytes, read and checked by main. Send them in the CLI's own form — Claude's base64 image blocks, Codex's `localImage` path — in the one write the prompt is. A provider that cannot take an image leaves it to a refusal of its CLI's, said as any failed start; fat-g filters nothing by model. A history page's user message may name its images' paths (`HistoryMessage.images`); main matches a path to an image it holds by the hash in its name, and reads nothing.
  - **A message during a turn is `steerState()` and `steer(request)`**, present together or not at all. `steerState` says whether the session's own turn, past its prompt's write on this process, takes a message now; main checks it in the step that records the message. `steer` resolves with `taken` (the CLI named the turn), `handed` (written; the CLI says later), `turn-over` (refused because the turn had ended, nothing delivered — main sends it as the next prompt), `refused` with the CLI's bounded word, or `unknown`, and never rejects. Where the CLI says later, send `delivery` (`taken`, `cancelled`, `not-confirmed`) by the message's id, or `held-turn-started` with a turn id of the module's own where a held message runs as the CLI's next turn; a process that ends with a message unaccounted says `not-confirmed`. Offer it only where a Stop can take a held message back.
  - **Commands are rows.** A provider whose process lists its commands and skills gives its sessions `commands()` (null until the process said) and sets the facet's `commandsOnceStarted`; one whose instance lists them for a folder gives the facet `commands(folder, signal)`. Each row is a `ProviderCommand`: a single-token name, a description and a hint as given, `commands` or `skills`, and a selector — an opaque id the module made, never a path — for a skill that goes with the prompt as an input of its own (`TurnRequest.skill`, resolved by the module against its CLI's current list; one no longer listed fails the start). `interceptedCommands` names the facet's `intercepts` by name, first in the menu. A provider with none of these has no rows of its own in the menu, and needs no branch of the composer's.
  - **The contract** holds every provider to the three: a prompt with images completes as any prompt does; `steer` is present exactly with `steerState`, offers nothing with no turn and answers `turn-over`; and rows, where there are any, have single-token names.
- **A turn's answer, told either way** (M16). A provider that knows which message is the answer as it sends it gives that message the phase `final`. One that learns it only when the turn ends sends every text as `commentary` and names the answer on a completed `turn-ended`, as `answerItemId`: fat-g then settles that stored item as `final`, in the same write as the end. The facet's contract takes either, and never both for one turn.
- **A turn's two ids, and whose end it is** (M18). `turn-started` carries `providerTurnId`, the CLI's own id for the turn, when it has one: history is matched to recorded turns by it. A provider whose CLI names no turn leaves it out and bounds the turn itself, as Claude does by the id fat-g gave the prompt. `turn-ended` carries `reported`: `true` only for an end the provider itself gave. An end the module makes — the turn's end lost, the process gone, a Stop the CLI never confirmed, a failed start, the session closed — is `reported: false`: fat-g stores it as the session's end alone, the turn reads as unfinished, and the next history check reads it again. For a provider with no history nothing settles such a turn later: it stays unfinished, and the chat says so.
- **History is a capability of its own.** A provider that can read a session's earlier conversation back sets `capabilities.history` and gives its facet a `history` member (`HistoryFacet`); one that cannot leaves both out, is asked nothing, and its chats show what fat-g recorded — the store's contract tests run against both kinds (`tests/sessions/store-contract.ts`). `history.read` answers one page over a connection the instance already holds, starting nothing: the turns it covers, each with the provider's id, outcome and times, and their messages, each naming its turn and, for the user's own, the id it was sent with. Where the CLI's history holds what a turn did, a page read in full also gives its activities (M20a), each as its two events would have told it, as one, with its place among its turn's items (`order`, which its messages then carry too): an activity whose id fat-g already holds is completed in place, and one it lacks is added in that order. It is asked for the turns alone first (`detail: 'none'`), and for a turn's items only when fat-g's store lacks that turn; it tells a page that was too large from one that only timed out. `history.onAvailable` says when a read that failed can be tried again.
- **How full the context is** ([decision 0033](decisions/0033-context-readings.md)). A provider whose CLI counts a conversation's context window sets `capabilities.context`, and its sessions send a `context` event with a `ContextReading` ([`contracts/sessions.ts`](../src/shared/contracts/sessions.ts)) each time the count changes: the tokens used and the window, both required; where the CLI compacts by itself, `null` where it says it will not, and left out where it does not say; and what else the CLI counts — the used parts by its own labels, the messages by kind, the last call and every call so far. Only the CLI's own counts: never an estimate, and never a window shipped as a default. Read the session's own thread alone, never a sub-agent's or a side question's; read counts and plain labels alone, never a path or a configured name; and ask for nothing that makes a call of the CLI's own. The chat draws the meter beside the mode control from it, and nothing of it is stored. A provider without the capability draws no meter.
- **A project's other folders** (M16). A session starts in one folder. A provider whose sessions can be given more sets `capabilities.otherFolders`, and is then handed, in `SessionStart.otherFolders`, the project's other roots that are trusted and present, worked out again at each start and each resume; any other provider is handed an empty list. The module decides how they reach its CLI, and leaves out one its launch could not carry safely: `shimRefuses` in [`provider-kit/process.ts`](../src/shared/provider-kit/process.ts) is the rule the process layer applies, for the module to apply first, saying so with a `folder-not-passed` notice. When a folder that was handed over stops being eligible, fat-g closes the session's process before the next prompt, which resumes without it.
- **Held to its mode, checked, and nothing granted that the user did not grant.** A session starts under the mode main hands it and checks what the CLI reports before any prompt. Under its reading mode a request from the CLI for an approval is refused, as every such request was before M22; under any other it is held for the user's decision, and one fat-g cannot show whole or cannot place is refused. A question to the user is answered with the user's own answer, which grants nothing. What a mode is in the CLI's own terms differs, and each module's decision record says it: Codex has a sandbox, an approval policy and a reviewer ([decision 0018](decisions/0018-codex-sessions.md)); Claude has no sandbox, and is held to a permission mode and a list of tools, checked again at each turn ([decision 0020](decisions/0020-claude-chat-sessions.md)). Shared words hold no provider's word for a mode: a notice names the chat's mode by the label its provider declared, and says "restricted start" for a reading mode whose start was not taken. A provider that declares no mode asks the CLI for the most restricted start it has, and refuses every request.
- **One process per session, and one module that writes.** Both built-in facets start a process of the CLI for each session, in its instance's scope, and keep everything that process may be sent in one file a test reads: `codex/methods.ts` for a JSON-RPC connection (`context.processes.open`), `claude/chat-wire.ts` for a CLI that speaks its own line protocol. For the second kind the kit has `context.processes.openProcess`: the process's lines as they come, with no request and reply matched for the module, on the same ownership — an end that cannot be confirmed holds that session alone, and its scope goes on launching.
- **A new session's title, from its own account** (M26; [decision 0028](decisions/0028-secretary.md)). A provider whose CLI can answer one short request with no tool and nothing saved gives its facet a `secretary` member and sets `capabilities.titles`, which Settings reads to offer the model that writes titles. Given a task's instruction and text, a model key and a level, the member starts a process of its own in the instance's scope and fat-g's probe folder, sends the instruction in place of the CLI's own system prompt or base instructions and the text as one prompt, refuses whatever the CLI asks, and answers the final text or a failure, ending the process on every path. It never throws, keeps nothing and logs nothing of the text. Claude's (`claude/secretary.ts`, with its writer `secretary-wire.ts`) is a `claude` process with fixed arguments; Codex's (`codex/secretary.ts`) an app-server on a fourth method set with one ephemeral read-only thread. A provider without the member keeps the names fat-g gives it.
- **A replay fake** answers the session's side from the captures (`tests/fixtures/codex/replay.mjs`, `tests/fixtures/claude/replay.mjs`), sending nothing a capture does not hold, and the shared contract tests run against it: the facet's (`tests/sessions/facet-contract.ts`) and the conversation store's (`tests/sessions/store-contract.ts`). For a provider that declares asides, pass the facet's contract `{ asides: true }` and give its harness a question the fake answers and the two faults it needs — the next ask refused, and the next left unanswered until it is stopped: the contract then asks beside an idle session and beside a running turn, stops one, has one refused, and closes the session over one. `tests/sessions/parity.test.ts` runs the built-in providers side by side through the app's session side, and lists what each CLI says in its own way: a new provider's differences belong there. The fake's control file has a fault for each thing a module must survive of an activity — a tool or an item type it does not know, a completion withheld, an output past its bound, a result with its error flag, a line over the session's 4 MiB — each a captured frame with one named change. For a provider that declares modes (M22), the fake takes the mode a start names and answers with it, holds each request for leave until the reply comes and then plays the capture's frames after it, makes an accepted change in its own scratch project and nowhere else, and has faults for a request delivered twice, one that comes again changed, one over a bound and one over the line with and without its id, a start that reports another policy, and — where the CLI has a setup — a setup refused, never completed, and cut off.

### 10. Fixtures and tests

- **Captured replies**, redacted, under `tests/fixtures/<id>/` — never written from memory. The M10 spikes (`spikes/m10/`) show how captures are taken and redacted.
- **A fake CLI** in `tests/fixtures/`, answering from those captures, so tests and smoke runs never reach an installed CLI or a real account. With an instance declaration, the fake chooses its answers by the variable's value, from an accounts file it only reads, and opens nothing in the folder; a folder with no entry reads as not signed in.

## The rules every provider follows

- **The user's own CLI does everything.** fat-g launches only the CLI the user installed ([decision 0003](decisions/0003-detect-user-installed-clis.md)), never bundles one, and presents no login of its own: signing in is the CLI's command, which fat-g shows and can open the user's terminal with.
- **An account's folder is the CLI's.** Nothing in fat-g, a module included, opens, lists or writes anything in it ([decision 0017](decisions/0017-provider-instances.md)).
- **No credentials, no endpoints, no network.** A module never reads the CLI's credential files or the keychain, never calls a vendor's endpoint, and opens no connection of its own: the CLI makes every authenticated call ([decision 0004](decisions/0004-never-touch-credentials.md)).
- **Nothing written into a project's folders** — no files, no provider files such as `AGENTS.md` or `CLAUDE.md`, no settings ([decision 0015](decisions/0015-no-writes-into-project-folders.md)).
- **Layers and imports** as in [decision 0002](decisions/0002-single-package-layered-layout.md): `src/shared` and the module's own folder only.
- **An original mark.** Never a vendor's logo; the audit ships no image files, and the mark is path data.
- **Honest naming.** fat-g and its features are not named after a vendor's product, and a module identifies itself honestly to the CLI — never spoofing another client ([decision 0004](decisions/0004-never-touch-credentials.md), rules 2 and 7).

## Current action ownership (M105)

Normalize executing tools by provider id, independently for the parent turn and each sub-agent. The provider kit's `LiveActions` supplies stable start order, local-tool/response/wait precedence and duplicate suppression; durable activity is separate. Close only the matched use on success, failure, decline or cancellation, then emit what remains. End response Writing at message/block boundaries. With no specific work, emit Thinking; silence neither ends a tool nor establishes a wait.

An evidenced non-user wait carries `wait: { reason: 'provider' }`, or `reason: 'subagents'` with an optional known outstanding target count (1–256). Matching ids stay private. Active children, coordination notices and retry flags alone do not establish waiting. Returned launches release local ownership while child activity remains. Tool edits use `tool: true` with Writing so they receive the same visible-fallback grace as other tools. Clear live ownership at terminal boundaries and reject stale-turn frames. Main arbitrates requests and holds parent completion; adapters never reset work merely because a request resolved. Shared words, display deadlines and stream pacing need no provider branches. Persist none of this metadata and leave activity retention unchanged.
