# 0022 — fat-g reads a project's file only to show it, at the user's word

> **Rule:** fat-g opens a file of a project at the user's press and refreshes its visible text or image tab automatically (items 16 and 17), only inside that project's trusted folders, and only to show it: the text is drawn and never kept, written, logged or sent to the Pet — but for a passage the user selects in it and sends to an aside, which is kept with that aside as the question they asked ([0025](0025-asides.md)). A reference is a claim that main checks; the page resolves no path. fat-g never reads inside a provider's configuration folder, an added account's or its own data folder through the general file reader; an attachment already owned by fat-g goes through its store (item 15). It never opens a file with the system's application: Show in folder is the one fallback for a file, and a folder a reference names is opened in the system's file manager after the same checks. An external address is handed to the system's browser only as a parsed `http:` or `https:` URL with no credentials, and fat-g requests nothing for it. An image file — one an agent read, or one a reference names — is read without a press and wherever it lies on this machine's own disks, never on a share or a device nor in those folders, to be drawn by an id for the run and kept nowhere (item 15).

- **Status:** Accepted by the maintainer with M19b's final spec (C25–C35, C43–C45, C51, C55; maintainer decisions 5 and 8). Implemented in M19b. M20b, amended the rule and item 9 (C29, C63; [0025](0025-asides.md), item 10): the one exception. Amended at the maintainer's request: a folder a reference names opens in the file manager, and a reference has a menu (the rule, items 1, 6 and 11, item 14). Amended at the maintainer's request: images an agent reads or a reference names are drawn in the chat and the pane, wherever they lie on this machine's own disks (the rule, items 1, 3, 6 and 7, item 15).

> **Attachment exception:** a reference to an image the active conversation store already owns is resolved and read by that store, including within fat-g's data folder; item 15. The general file reader still enters none of the excluded folders.

- **Amendment:** accepted for quiet visible-file polling, the Rule and items 1, 10 and 16.
- **Applies to:** `src/main/files/`, the channels `files:read`, `files:refresh`, `files:refreshImage`, `files:showInFolder`, `files:locate`, `files:openFolder`, `files:readImageForCopy` and `shell:openAddress`, the media route's `files` source (`src/main/media/files.ts`), the chat's image thumbnails (`src/renderer/src/chat/ImageFileStrip.tsx`) and the `image` tab kind, a reference's control and its menu (`src/renderer/src/markdown/controls.tsx`), `src/shared/contracts/files.ts`, and every later place that shows a project's file or opens an address a text names: M20's activity items, M19c's viewer. Builds on [0004](0004-never-touch-credentials.md) (no network of fat-g's own, no credential file), [0015](0015-no-writes-into-project-folders.md) (nothing written into a project), [0017](0017-provider-instances.md) (an account's folder is its CLI's), [0019](0019-conversation-store.md) (what is kept, and where) and [0021](0021-drawing-conversation-text.md) (how a text is drawn).

## Context

- A model answers "where is this?" with a path. Until M19b the reader copied it into another program. M19b makes the reference a control that opens the file beside the chat.
- The text that names the file is not fat-g's. It comes from a model, and through it from whatever the model read. A reference can name anything: a file outside the project, a share on another machine, a credential file, an address that runs something.
- A project's root may be the user's home folder, which holds `~/.claude`, `~/.codex` and fat-g's own data.
- On Windows, asking the system anything about `\\host\share\…` connects to that host and offers it the user's sign-in.
- Before M19b main read nothing of a project's folders: it asked only whether a folder was there and what its real path was ([0015](0015-no-writes-into-project-folders.md), [0017](0017-provider-instances.md)).
- The two CLIs name a file differently: Codex writes a Markdown link with an absolute address, Claude a code span, twice by a bare name, and at another model in bold, with its line in words (chat protocols §11 (private research note)).

## Decision

1. **Only at the user's word** — but for an image (item 15). A file is read when the user presses a reference, when its tab is shown again, and at Reload. Where a reference leads is asked only at a press or a choice in its menu (item 14). Visible text and image tabs are checked and refreshed by items 16 and 17. Nothing is read ahead, and no folder is listed but to look up a name the user pressed (item 8).
2. **A reference is a claim.** The page sends the address as the message wrote it, with the session it belongs to and, for a reference inside a shown file, that file. It names no base folder. Main resolves the target, checks it and reads; what an address is, the page and main read with one function, and main reads it again.
3. **Inside the project's trusted folders, checked twice** — or, for an image, on this machine's own disks (item 15). The resolved path must lie in a root of the session's project that is trusted and not marked missing — first by its stored path, before the file system is asked anything, then by its real path. So a share's path or a `file:` URL with a host reaches no network, and a link inside a root that leads out of it is refused.
4. **Never a configuration folder, nor fat-g's own.** A path inside a registered provider's default configuration folder or the one its variable names, inside an added account's folder, or inside fat-g's data folder is refused, by its stored path and by its real one, whichever root holds it. The one exception is an attachment already owned by the active conversation store: item 15 routes its claim through that store's verified image source, never through the general file reader.
5. **Under a home-folder root, only those are refused.** fat-g keeps no list of other tools' folders, `.ssh` or `.aws`. The address is in the reference's tooltip before the press, a shown file leaves the machine by no path fat-g has, the session's model can read those files already, and such a list would be arbitrary and never complete.
6. **A regular file of 2 MiB at most, that is text** — or an image within 0030's bounds (item 15). A folder, a device or a pipe is not read: a folder is opened in the file manager instead (item 11). The size is asked before the file is opened. The bytes are text when they decode as UTF-8, or as UTF-16 where a byte-order mark says so, and hold no U+0000; otherwise none of them reaches the page.
7. **Only a name on the lists is read** — or an image's name, as an image (item 15). A file is shown as Markdown or as plain text by its name, from two lists in the shared contracts. Any other file opens a tab that says so, and none of its bytes is read.
8. **A bare name is looked up.** A name with no folder that is no file where it resolves is looked for in the project's trusted folders, nearest first, following no link, entering no dot folder, no `node_modules` and no folder of item 4, to 20,000 entries. One file found goes through items 3 to 7; several open none.
9. **Shown, never kept.** Main holds nothing of a file once it has answered. The page holds a file's text for the tab it shows and for no other. None of it is written to a stored file, a log, a session's summary or the app state, and none reaches the Pet. Open tabs last for the run: a restart begins with none. *(M20b, C29, C63:)* one exception, the user's own doing: a passage they select in a file's tab and send to an aside is kept with the aside in the conversation store — the passage, cut to 20,000 units, the file's real path and its lines — under [0019](0019-conversation-store.md)'s rules, until they remove the aside, its session or its project. Nothing else of the file is kept by it, and no file is read for an aside: the passage is what the page already showed.
10. **What main says of a read is a kind.** Its outcome is counted by kind and an explicit read's refusal is one log line with its kind — never a path, a target or a text. Automatic refresh outcomes are counted by fixed kind alone, with no repeated warning logs.
11. **Show in folder is the one fallback for a file, and a folder opens in the file manager.** The system's file manager shows a file selected, after items 3 and 4 passed for its path. A folder a reference names, placed by items 2 to 4 on its stored and its real path, is opened in the file manager (`files:openFolder`): a folder runs nothing when it is opened. On macOS one whose name has an extension is shown selected in its own folder instead, since an application, an installer or a workflow is such a folder, a bundle, and the system would run it. fat-g never opens a file with the system's application: that would run whatever a model's text names — a script, a shortcut, an installer — at a click.
12. **An external address goes to the browser as parsed, and fat-g asks nothing.** `shell:openAddress` is the one channel an address crosses. Main hands it over only when it parses as a URL of `http:` or `https:`, holds no user name or password and is at most 2,000 characters, in the parsed URL's own spelling. Nothing is fetched, previewed or resolved first: no title, no icon, no redirect followed.
13. **A control carries no address of its own.** A reference is a `button`, never an anchor ([0021](0021-drawing-conversation-text.md)): nothing can be navigated to, dragged out or opened in a window from it.
14. **A reference has a menu.** The right button, Shift+F10 and the Menu key open fat-g's own menu on a reference, drawn in the page as the selection's is: Open, Show in folder and Copy path for a local one, Open link and Copy link for an external one. Open is a press. For the other two main places where the reference leads by items 2 to 4 (`files:locate`), reading nothing of a file, and answers its real path: Show in folder hands that path back to `files:showInFolder`, which checks it again, and Copy path puts it on the clipboard. Copy link copies the address as written. On a selection the reference lies in, the selection's own menu opens instead.
15. **An image is drawn, wherever it lies on this machine.** *(at the maintainer's request:)* Images are more and more part of the work, and the CLIs' own apps draw them: a picture an agent looks at is shown to its model alone, which then writes of "the previews above". So a file by an image's name — `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp`, in any letter case — is read as an image, and drawn:
    - **under an activity group's line**, open or closed — the fold never opens by itself — for each finished read of one such file (Codex's `imageView` is a read of its file; Claude's `Read` of one already is);
    - **under a finished answer**, for each local reference its text names by such a name, at most 20, each once; an address main draws nothing of is left out, as the text is no claim that it was ever there;
    - **in the image tab**, at a press on either thumbnail or on a reference to one, by its real path.

    Each is read when the chat draws it, without a press: the thumbnail asks `files:read` as a press would at each mounting, and again at each press. Concurrent lookups of the same session and target share one request; completed lookups are not cached for the run. It is read wherever it lies on this machine's own disks, inside the project's folders or outside them — a temporary folder's preview among them — since the CLI read it already and sent it to its model, and drawing it on the user's own screen sends it nowhere. What still holds: no share's or device's path (`\\server\share`, `\\?\`, `\\.\` on Windows), checked on the stored path before the file system is asked anything and again on the real path, so that no read reaches another machine; none of item 4's folders, by stored and real path; a regular file of 5 MiB at most, its size asked before it is opened, and a PNG, JPEG, GIF or WebP by its own header of 8,000 pixels a side at most (0030's bounds). Outside the project's folders a file by any other name is refused as before, and so is one by an image's name that is too large or no such image (`not-image`); inside them, such a file opens the tab that says so.

    Main answers an image by an id for the run (`src/main/files/images.ts`): the same id for unchanged bytes of the same file of a session, a new id when its contents change, another for another session, 1,000 at most, the one named longest ago forgotten past that. The page draws it from `app://media/files/<id>` alone, never by its path; the route checks the file again at each request — the same real path, type, dimensions and SHA-256 content digest, its session still listed — and serves it with `no-store`, so Chromium keeps no copy. Copy (`files:readImageForCopy`) takes the session and the id, checks the file again and hands its bytes over once for the clipboard; Show in folder takes the real path through item 11's checks, which admit an image's path outside the project's folders by the same rule. What main holds between two readings is each id's session, real path, type, dimensions, modification time, byte size and content digest: never a byte. A new revision replaces the old run id, so reopening an existing image tab changes its media URL even when the file's name and dimensions stayed the same; nothing of that digest is stored. Every explicit opening also starts a fresh image load, allowing an unchanged file to recover from an earlier failed preview while preserving the tab's fit or actual-size choice. Nothing of it is stored, logged — a read is counted by its kind (`read:image`), a refusal by its kind — or sent to the Pet; `conversations.sqlite` keeps the path as the CLI wrote it, as 0024 always had it.

    *(attachment preview fix):* A path naming an active attachment directly under `attachments/`, with its exact hash and stored type's extension, is matched to the conversation store before the general data-folder refusal. Its owner's source checks the file's size, hash and header; main also checks its owned location, refusing links, redirected descendants and real paths on shares or devices. The same run id and image tab can draw it, copy it and reveal it, with those checks repeated each time. Nothing new is stored. An unknown hash, a mismatched extension, a nested path and every other file in fat-g's data folder remain refused. This lets an agent's read of an image the user pasted show the image the CLI was sent ([0030](0030-attachments.md), item 9).

    If an image cannot be drawn, its thumbnail and image tab say what the checked reader established: a file no longer found, a location not allowed, a read that failed, or an unsupported image or preview limit. A failed media request asks the checked reader again once for that reason; a successful header read alone says only that the preview could not be loaded, without retrying in a loop. A missing file explains that previews use the original file, that fat-g saves no copy and that temporary files may have been cleaned up; the app does not claim to know who removed it. An address named only in a message is still left out when no image can be drawn.


16. **A visible text file refreshes quietly.** *(at the maintainer's request:)* The selected Markdown or supported plain-text tab checks its exact absolute path's modification time and byte size about every two seconds through Main-only `files:refresh`. Every check repeats the session, trusted-root, excluded-folder and real-path checks, even for unchanged metadata; there is no name search or image exception. Changed metadata settles for 250 ms before a bounded checked read; a read whose path or metadata changes is retried. Only stable new text replaces the display, preserving scroll and focus. Checks pause while Main is hidden/minimized or a DOM selection touches the file, resume immediately on return or selection clearing, and stop on leaving the tab. Late results are discarded, including when manual Reload supersedes them. No native filesystem watcher or long-lived read handle is held.

    This is a convenience: every automatic failure keeps the last successfully displayed text and retries quietly. Its only visible failure feedback is small `auto refresh failed` text beside the toolbar title, with a tooltip explaining that the old text is still shown. A successful check clears it; nothing becomes a session error, dialog or notification. The toolbar shows the local time and age of the last successful automatic text change, never a metadata-only change, opening or manual Reload. Only that timestamp survives a tab switch, in the tab's in-memory view state; text and revisions stay with the visible body. A tab close or app exit drops the timestamp too. Modification time and size are a proxy and can miss changes preserving both; Reload always rereads. Nothing of this is stored, logged as content, sent to a provider or sent to the Pet.

17. **A visible image file refreshes by metadata first.** *(at the maintainer's request:)* The selected image artifact alone asks Main-only `files:refreshImage` about its exact previously admitted session and path, with the run id it currently draws, about every two seconds. Main keeps the admitted file's modification time and byte size with its run id; unchanged metadata repeats the local-path, excluded-folder, real-path and regular-file checks but reads and hashes no bytes. A changed file settles for 250 ms, then passes the bounded image reader and a stable metadata check again. The same content keeps its id and advances no update clock; changed contents get a new id. An immutable owned attachment needs no polling read through either reader, and a hash-referenced attachment starts no polling timer.

    Checks stop when another artifact or session is selected or the tab closes, pause while Main is hidden or minimized, and resume immediately on return. No chat thumbnail, hidden tab, folder, provider or model is polled. One request or candidate image load is held at a time, and late results after a hide, tab change or explicit reopening are discarded. The previous image stays visible until the replacement successfully loads; read or decode failures keep it, show the same small `auto refresh failed` status and retry quietly. Successful replacements preserve fit/actual size, focus and scroll, and show the text tab's same update time and age. That timestamp lives only in the open tab's view state and is dropped on close or exit. Metadata-only saves, opening and explicit reopening do not claim an automatic update. Modification time and size can miss edits preserving both; pressing the reference or thumbnail always rereads. No watcher, persistent handle, stored content, log text, provider call or Pet access is added.

## Consequences

- `src/main/files/` is the one place in main that reads a project's files, through an interface with three questions — what is at a path, a file's bytes up to a bound, a folder's entries — and writes nothing. The pinned list of file-system importers names it, and `tests/architecture/files-reach.test.ts` holds where main shows a file, opens a path and hands over an address.
- The reader's tests run on a file-system stand-in that records every call, for each system's path rules: a refusal of item 3 or 4 with a call made fails.
- A Codex session can read anywhere on the machine, so a file it names outside the project does not open here, and the reference says so. A Claude session is refused every read outside its project's folders, and fat-g's reader reads no wider.
- A file changed or gone, and a root no longer trusted, are found at the next showing and by visible-tab polling. A failed automatic refresh preserves the already displayed text; only a newly admitted read replaces it.
- `.env` is not on the lists: such a file opens the fallback tab, and none of it is read.
- `PRIVACY.md` says what is read and when, and its rule on project folders is exact: fat-g reads them to show a file the user opens, and to check that a folder is there.

## Revisit when

- A file is to be edited or saved from the pane: that would amend [0015](0015-no-writes-into-project-folders.md).
- Files beyond the selected visible text or image tab are to be watched, indexed or listed without a press: items 1, 16 and 17.
- Tabs are to be remembered across a restart: the references would be stored, and the records' version raised.
- A file is to be opened with the system's application, or in an editor: item 11.
- A folder is to be listed in the pane rather than opened in the file manager: items 1 and 11.
- Another address is to be loaded by the page: item 12 and [0021](0021-drawing-conversation-text.md). An image file is drawn by item 15; one a model's text names by a remote address is not.
- An image is to be kept, or read from a share, or past 0030's bounds: item 15.
- A list of other tools' folders is asked for under a home-folder root: item 5.
