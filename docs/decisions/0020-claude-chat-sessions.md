# 0020 — Claude chat sessions: one process each, four sends, four tools that read

> **Rule:** each Claude chat session runs on a `claude` process of its own, started in its instance's scope at its first prompt, with arguments fixed but for the two its chat's mode decides ([0027](0027-execution-permissions.md)). fat-g writes ten things to it and nothing else — `initialize`, a prompt with an id fat-g made, its images as base64 blocks where it has any ([0030](0030-attachments.md)), a message written while a turn runs, in a prompt's own frame under its own id (M23), `interrupt`, asking `cancel_queued` where a message the CLI holds could still run (M23), `apply_flag_settings` carrying `effortLevel` alone, the same carrying `fastMode` alone ([0016](0016-model-presets.md)), a side question and its cancel ([0025](0025-asides.md)), a change of permission mode between three of its modes, into `plan` for a plan turn and out of it to the process's own launch word ([0029](0029-plans.md)), and `get_context_usage` with its summary detail alone ([0033](0033-context-readings.md)) — and answers the CLI in six ways: `deny` to a tool's use, `allow` to the question tool's alone, with the user's answer ([0026](0026-questions.md)), `allow` to an action the user approved on its card or a plan they chose to execute, `deny` with the user's feedback on a plan, `deny` with `interrupt` for a plan they cancelled, and the error reply to anything else. The CLI is offered `Read`, `Glob`, `Grep`, `Agent` and `AskUserQuestion`, under a mode that acts `Bash`, `Write` and `Edit` beside them, and `WebFetch` and `WebSearch`, and `ExitPlanMode` under a mode that plans; the user's own configuration applies otherwise. What the CLI reports is checked against the chat's mode before a prompt, at every turn's `init` and at every status frame that names a mode. A Claude session is never described as sandboxed: its reading mode is named Read only + allowed MCP, and says what still acts.

## Context

- M16 is the live slice [0009](0009-live-session-data-first.md) asked for, for the second provider. Claude has no app-server: a session is the CLI itself, speaking stream-json over its input and output, the protocol [0006](0006-no-agent-sdk-at-runtime.md) already speaks for usage. 0006 closed that protocol to two requests and said a chat session would need a record of its own.
- Claude has no sandbox for fat-g to switch on, as Codex's read-only one is ([0018](0018-codex-sessions.md)). What holds a session back is the tool list the CLI is launched with and the answer to what it asks; the user's own hooks and MCP servers are outside both.
- The spikes K1 to K27 traced every point below against Claude Code 2.1.268 (the turn-tracing note (private), §8). Three findings shaped the decision: the CLI names no turn, but frames that name a prompt's id bound it; a worker started in the background outlives its turn, and the CLI then starts a turn by itself; and a session whose first turn no model answered is not one a later process can resume.
- Turns spend the user's subscription usage. The maintainer accepted the reviewed provider terms for the free, local, open-source release; the [release-policy assessment](../licensing.md#provider-policy-review) records that decision and the limits of the published guidance (0006).

## Decision

1. **One process per session.** A session's `claude` starts at its first prompt, in its instance's process scope ([0017](0017-provider-instances.md)), with the session's folder as its working folder. It closes by the runtime's idle rule, at once when the session is completed or removed, and at quit; it is never started again by itself. An end that cannot be confirmed holds that session alone: the instance's other sessions and its usage reads go on. The usage and models-only sessions stay short-lived and run beside it.
2. **Four sends, in one module.** [`chat-wire.ts`](../../src/main/providers/claude/chat-wire.ts) is the only writer to a chat session's process, behind a closed type:
   - `initialize`, with no system prompt, no hook and no MCP server of fat-g's: the CLI's own system prompt applies;
   - a `user` frame holding one prompt as one text, with an id fat-g made for it;
   - `interrupt`;
   - `apply_flag_settings` carrying `effortLevel` and no other key;
   - *([0016](0016-model-presets.md))* `apply_flag_settings` carrying `fastMode` and no other key: Claude's fast mode on for a turn whose speed tier is `fast`, off for standard speed. A process launches at standard speed — no argument names a speed — so a fast session sends it before its first turn's prompt, and a turn whose speed differs from the process's sends it first, after the effort's change and before a plan's; a refusal, or no reply in 15 s, fails the turn's start as the effort's does. It holds for the process, and no settings file changes. Flag settings that carry `fastMode: true` lift the CLI's `sdk_opt_in_required` block (Claude 2.1.302; confirmed on real turns, models research §6). What a fast turn was served is read beside the mapper, since only the session knows it asked: the turn's `result` carries `usage.speed` — `fast`, or `standard` where fast mode fell back — and `fast_mode_state` (`cooldown` while paused after a rate limit), and the last `rate_limit_event` says why extra usage was refused (`overageDisabledReason`, e.g. `out_of_credits`); the session says it as `in-force` `served`, with that reason id, before the turn's end. `usage.service_tier` is read for nothing: it says `standard` either way. An aside sends none: its side question runs at the speed the process has. The secretary's process can send none ([0028](0028-secretary.md)). Claude bills fast mode as extra usage;
   - *(M20b, C13; [0025](0025-asides.md), item 4)* `side_question`, a question asked beside the conversation: its text, and the aside's earlier exchanges as `history`, each its question and its answer and nothing else. It names no model and no tool;
   - *(M20b, C15)* `control_cancel_request`, carrying the id of the side question it takes back, and none of its own;
   - *(M22, C5, C74, C90; [0027](0027-execution-permissions.md), item 9)* `set_permission_mode`, carrying the CLI's word for one of three modes — Ask first's, Edits ok's or Auto reviewed's — sent with nothing running on the process, to move among those three. The module writes no other word: never the one that bypasses permissions, which is a launch's alone, and nothing for a move into or out of the reading mode, which is another tool list and so another process. It holds for the process, and no settings file changes.

   Six sends, then, from M20b on, and seven from M22. No login or OAuth subtype, no `set_model`, no `mcp_` subtype and no other request can be sent, on either kind of session; *(until M22)* no `set_permission_mode` either, which a chat session now sends for those three words and a usage session never does. A prompt never goes on a command line. *(M22b, C7, C51; [0029](0029-plans.md), item 2:)* `set_permission_mode` also names `plan`, before a plan turn's prompt, and at that turn's end, coming out of `plan` alone, may name the word the process was launched under, Berserk's `bypassPermissions` included — checked against that launch and never against a frame, so that no send raises a process above its launch. A move into Berserk from another mode stays a new process. Seven sends still. *([0033](0033-context-readings.md), item 2:)* the tenth, `get_context_usage` carrying `detail: 'summary'` and nothing else — the CLI answers it from the last response's usage and its own estimates, with no token-count call; the full detail, which makes them, is never written. It is sent at a turn's start while the process holds no reading and after each turn the CLI ended, one at a time, never for a process an aside launched; nothing waits on its reply, a refusal ends the asking on that process, and of the reply only counts and the used parts' labels are read. Ten sends.
3. **Two answers.** A `can_use_tool` request is answered `deny`, in fixed words of fat-g's; every other request the CLI makes gets the error reply. Each is counted under its subtype when that is one of a closed list, and as `other` otherwise; the chat shows one notice per turn. *(M21, C17–C19, C60:)* three: a `can_use_tool` request whose tool is `AskUserQuestion` is held, and answered when the user answers its card ([0026](0026-questions.md), item 8) with `allow` and `updatedInput` — the request's own `input` as it came, and `answers`, a map from each question's whole text to one string. The answer is in the module's closed type for that tool's name and no other: a request for any other tool is denied as before, whatever it carries, and so is a question fat-g cannot draw whole or cannot place. An answer approves nothing: the tool reads nothing, writes nothing and reaches nothing. *(M22, C8, C9, C11, C13, C21, C22, C68, C69, C91; [0027](0027-execution-permissions.md), items 11 to 17:)* four. Under the reading mode a `can_use_tool` request for any other tool is denied as before. Under any other mode such a request — for `Bash`, `Write`, `Edit`, an MCP tool or any other — is held as the question's is, under the session's turn or the worker its `agent_id` names, and answered when the user decides its card: `allow` with `updatedInput`, the request's own `input` as it came and changed by nothing; or `deny`, in the second of the module's two fixed messages, which tells the model that the user denied the action. With an `allow` may go the one thing that outlives the request, where the user chose Approve for this session: `updatedPermissions` holding exactly one entry, the request's own `addRules` suggestion that allows, its rules as the CLI wrote them and its destination set to `session`, whatever destination the CLI wrote on it. The entry is written field by field and never copied from the offer, so no reply can name another destination, a mode, a folder, or a rule that denies, replaces or removes. The CLI's other suggestions are read for their kind alone, to be said on the card. A request that cannot be shown whole, that lacks a field its action stands on, or that cannot be placed is denied on the wire with the notice. One that comes again under a held id is compared with the hold — its tool, its input, its tool use and its agent — before it is counted as a repeat, a question's too: one that differs is denied, the hold let go, and its card withdrawn as changed. The tool's result for a held request is the CLI's word that it took the decision. The `allow` for the question tool and the `allow` for an action are two members of the closed type: a question is never given leave as an action is, and an action is never answered with answers. *(M100b, C30, C31, K1:)* a question the user skipped is answered `deny` in their name, in the module's third fixed message, "The user declined to answer in fat-g": the CLI makes the tool's result an error holding those words, and the turn goes on, so that result is its word that it took the reply and counts as no failure. In an `allow`'s `answers`, a question the user left blank is given the words "No answer". *(M22b, C9–C11, C77; [0029](0029-plans.md), item 2:)* six: an `ExitPlanMode` request in a plan turn is held, and answered by the user's decision — Execute with `allow` and the request's input as it came, with no `updatedPermissions`; feedback with `deny` carrying the user's text, the one `deny` whose words are the user's; Cancel with `deny`, `interrupt: true` and fixed words, its turn reading stopped. A request with no plan in its input is denied with fixed words saying none reached fat-g, and one outside a plan turn, or after its Execute, is refused as any unknown request is. Each answer is in the module's closed type for that tool's name and no other.
4. **Fixed arguments.** Stream-json both ways with `--verbose`; `--setting-sources user,project,local`; `--permission-mode default`; `--permission-prompt-tool stdio`; `--tools Read,Glob,Grep,Agent` — *(M21, C16:)* `--tools Read,Glob,Grep,Agent,AskUserQuestion`; *(until M20b)* `--disable-slash-commands` — *(M20b, C54:)* no longer passed, by [0023](0023-cli-commands-pass-through.md): the CLI's commands and skills are on, fat-g answers `/clear` and `/model` — and `/fast` — itself and never sends them, and a side question is refused where the flag is set; *(M19, C9:)* `--include-partial-messages`, so that a reply's text arrives as it is written, in `stream_event` frames beside the whole messages. Per session: `--model` with the record's key, `--effort` with its effort where the model has levels, `--resume` with the reference for a started session, and `--add-dir` once for each other root (item 7). Never `--no-session-persistence`, `--session-id`, `--fork-session`, `--fallback-model`, `--strict-mcp-config`, or a flag that bypasses permissions. *(M22, C5, C45, C47; [0027](0027-execution-permissions.md), item 4:)* two of the arguments are the chat's mode's, from the module's one mode table (`chat-modes.ts`), in the places they had: `--permission-mode` with the mode's word — `default` for Read only + allowed MCP and for Ask first, `acceptEdits` for Edits ok, `auto` for Auto reviewed, `bypassPermissions` for Berserk — and `--tools` with the mode's list, the five for the reading mode and the five with `Bash`, `Write` and `Edit` for the other four. Nothing else of a launch differs by mode, and no flag is added for any of them: Berserk is its mode argument and nothing more, and the never-list stands, a flag that bypasses permissions on it. A start that names no mode, or one this build does not know, is the reading mode's. *(M22b, C8, C70:)* `--tools` lists `ExitPlanMode` under Ask first, Edits ok, Auto reviewed and Berserk, and never under Read only, which cannot save a plan; `EnterPlanMode` is listed under none.
5. **Four tools that read.** `Read`, `Glob`, `Grep`, and `Agent`, whose worker has the same list and no more: none changes a file, runs a command or reaches the network. `--tools` keeps every other built-in tool from being offered, and behind it the default permission mode with item 3's `deny` refuses whatever asks; both held under a configuration that allowed `Write`, `Edit` and `Bash` and set `acceptEdits`. One exception is the CLI's own: for a worker the model asks for in a worktree it makes a git worktree in a project that is a repository, with no request, and leaves an empty `.claude/worktrees/` folder and `.git/FETCH_HEAD` behind. *(M21, C16, C21:)* five: `AskUserQuestion` is the fifth, and asks the user a question through item 3's request — it changes no file, runs no command and reaches no network. The launch check and each turn's `init` are held to the five. A worker's list is the same five, and the CLI offers a worker no question tool (M21, K1): a worker's question is handled as the session's own would be, and none has been observed. *(M22, C5, C45, C97:)* the five are the reading mode's list, and what every mode starts from. The four modes that act add `Bash`, `Write` and `Edit`: a command, a whole file's content, an edit by match. Under Ask first each of their uses asks through item 3's request, unless a rule of the user's configuration allows it; under the others, what the mode lets run asks nothing ([0027](0027-execution-permissions.md), item 4). A worker has its session's list and runs under its session's mode. No other built-in tool is offered under any mode, the `Skill` tool among those left out. The launch check and each turn's `init` are held to the list of the mode in force. *(M22b, C8, C9, C70; [0029](0029-plans.md), item 2:)* `ExitPlanMode` is listed beside them under every mode that plans: it reads, writes and reaches nothing, and asks the user to decide on the plan through item 3's request. In a plan turn the model saves its plan with `Write`, which a mode that acts offers, to a file in the account's configuration folder, with no request; fat-g takes the text from the request's `input.plan` and never reads that file. the four modes that act add `WebFetch`, which the CLI runs on this computer — it downloads the page and has a small model answer the model's question from it — and `WebSearch`, which runs on the provider's side and returns links with a summary. Each asks through item 3's request as its mode has it, but the CLI fetches its own list of documentation sites with no request, under every mode, and the mode lines say so. A CLI that lists neither, such as one whose backend has no web search, passes the check, which holds `init` to a subset of the mode's list. The reading mode is offered neither.
6. **The user's configuration applies.** Instructions, hooks, MCP servers and agent definitions load through the CLI from the user's, the project's and the local settings; skills and slash commands do too *(from M20b, by [0023](0023-cli-commands-pass-through.md); until then the launch switched them off)*: the model is still offered no `Skill` tool, so a skill runs only at the user's word. fat-g reads and writes none of it. A hook runs as the user wrote it, and an MCP tool the user's settings already allow runs without a request: both can change files, and `PRIVACY.md` and the README say so. That is why the gate stands before every launch: a project's configuration is loaded when the process starts, before any prompt.
7. **Every trusted root of the project.** The working root is the process's folder; each other root of the project that is trusted and present is passed with `--add-dir`, worked out again at every launch and compared at every Send, where one that is no longer eligible closes the process so that the prompt resumes without it. A root whose path a shim launch would refuse is left out, by the provider kit's one rule, and the chat says so once without naming it. A read inside these roots runs without a request; one outside is asked for, and so refused. *(M22:)* refused under the reading mode; under any other it is a request as any is, and a card (item 3).
8. **Two checks, against the names the CLI reports.** Before any prompt, the `initialize` reply's permission mode is the launch's: a difference sends nothing and fails the turn. At every `init`, a turn's or one the CLI started by itself, the mode is the launch's and every built-in tool offered is one of item 5's: a difference ends the process at once. The names compared are the CLI's own, `default` or `manual` for the mode and `Task` or `Agent` for the worker's tool while they change; a name on neither list is a difference, whatever its cause. *(M22, C5, C7, C46, C90; [0027](0027-execution-permissions.md), items 9 and 10:)* three checks, each held to the mode in force and no longer to one fixed launch. Before any prompt, the `initialize` reply's permission mode is the mode's word: a difference sends nothing and fails the turn — for the reading mode as a restricted start that was not taken, for any other with a notice that carries the word the CLI reported. At every `init`, the mode is the mode in force and every built-in tool offered is one of that mode's list: a difference ends the process at once. And a `system/status` frame that names a permission mode is read for it: the mode in force, or the target of a change that waits for its reply — the frame can come beside that reply, or before the reply is read — is the change reported; any other word is a policy fat-g did not ask for, and the process is ended with a notice. A change whose reply does not name its target is not confirmed, and leaves the mode as it was. Each of these failures blocks Send until a mode is chosen again. *(M22b, C7, C61, C79; [0029](0029-plans.md), item 2:)* across a plan turn the mode in force is `plan` from its confirmed change, and the chat's mode again from the moment Execute's `allow` is written, its target armed before that write, the status frame naming it coming within the same chunk; the restoration at the turn's end is armed the same way. A report of any other word is a difference, as before.
9. **A prompt's id bounds its turn.** Each prompt's `user` frame carries the id the conversation store keeps for that message. The CLI's `command_lifecycle` frames that name it bound the turn: from `started` to the `result` that `completed` or `cancelled` follows. A turn whose `init` no `started` precedes is one the CLI started by itself: its frames are dropped and counted, and a prompt written meanwhile keeps its own.
10. **Background tasks off.** The process is started with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` set, so a worker ends with its turn. Of the user's exported `CLAUDE_` variables a reviewed list reaches the process, and none that decides what the launch fixes: the model, the effort, the tools, the permission mode, background tasks, session persistence.
11. **The reference is the session a model has answered in.** Claude saves a session by itself. Its id is reported, with the folder it started in, at the session's first frame from a model — not at `init`, and not for a turn the CLI answered alone or that failed or was interrupted before a model spoke. *(M19, C60:)* that is the start of the session's first reply from a model, its `message_start`, before any of the reply's text; the first `assistant` frame from a model stands in where no such start came. A worker's reply and one of the CLI's own establish none. A session whose first answer was cut while it was being written therefore has its reference, and is resumed; of the cut answer Claude keeps nothing, and what the chat shows of it is what fat-g received ([0019](0019-conversation-store.md), item 14). Until then the session has no reference, and a prompt written after its process ended starts a new conversation. A session with a reference is resumed at its next prompt by `--resume`, in its stored folder, a process ended during a turn included.
12. **Deadlines.** The launch to its `initialize` reply, 120 s, since a `SessionStart` hook of the user's holds that reply back; the prompt's `started` frame, 30 s; `apply_flag_settings`, 15 s, and *(M22)* `set_permission_mode` the same; a Stop, 10 s, after which the process is ended. A turn has none, and neither has the wait for its `init`.
13. **No history is read.** Claude's descriptor says it has none to give: fat-g opens no transcript, starts no process to read one, and a resumed session sends nothing of its earlier conversation. What the chat shows is what [0019](0019-conversation-store.md)'s store recorded. The answer of a turn is told at its end, which names the last text; the store then holds that item as `final`.
14. **A reply as it is written** *(M19, C10–C13)*. Of a `stream_event` frame of the session's own, fat-g reads its event's type, a block's index and type, a reply's id and model, and a text delta's text. Nothing of a thinking, of its signature or of a tool's input is read, and nothing of a worker's reply. A text block is one message from its start, under its reply's id with the block's index: the `assistant` frame that carries the block completes it, and is the authority for its text. A text whose reply or block no event opened is a whole message under its frame's own id, as before. A text is the turn's last from its first words, so a completed end names it as the answer though its frame never came. While it is written it says no phase *(C79)*: Claude names the answer at the turn's end, so a text that is still coming is neither commentary nor answer, and is drawn as an answer is; its frame makes it commentary, as before. A text whose frame comes after the turn's Stop was cut by it *(C80)*: the frame is taken for its text alone and does not complete the message, which the interrupted end leaves as it was received, unfinished and with no phase; where the turn completes after all, the frame completes it just before that end. Nothing more is sent for any of it. *(M20a, C16–C18, C20–C23:)* More of the same frames is read, and nothing new is sent. A `tool_use` block is an activity from its `assistant` frame — its tool's name, its input, the files it names — and the `tool_result` block of a `user` frame that names it ends it, with the result as its output and its error flag as a failure; of a `user` frame only its `tool_result` blocks and the tool use each names are read, never its `tool_use_result`. A `thinking` block is an item with what text it carries, which is none today. A frame that names an `Agent` tool use is its worker's: its tool uses, results and texts are the worker's items, under the worker's id, once `task_started` has paired that tool use with the worker — a frame that comes before the pairing is held for it, two seconds at most. The `Agent` tool use itself is the session's own item for the worker: an error result before any pairing fails it as any tool's does; once paired, its result ends nothing of it, and it ends as its worker ends, its notification's summary being its output. A line from the CLI may be 4 MiB, where it was 1.

## What is left out

- Approvals, answering the CLI's questions, a message during a turn, and any tool that writes, runs a command or reaches the network: later milestones, each with its own decision where it changes one of the above. *(Questions came with M21, [0026](0026-questions.md); approvals, and the three tools that write and run commands, with M22, [0027](0027-execution-permissions.md); the two that reach the network, item 5.)*
- *(M22)* A settings destination for a rule other than the session's; the CLI's other permission modes, `plan` among them (M22b); and a list of the CLI's own rules, which the CLI version traced does not give.
- Listing, naming, forking or deleting the user's Claude sessions; reading its transcripts or its settings; a session id of fat-g's own choosing.
- Starting a turn's process again by itself after a loss, and ending a descendant that outlives a forced end of fat-g.

## Consequences

- Each running session is one more `claude` process; an idle one closes after five minutes.
- *(M19)* The stream events are one more piece of that protocol. An event type this build does not know is passed over, uncounted; a CLI that stopped sending them would leave whole messages, as before M19.
- fat-g owns a second piece of an undocumented protocol. A CLI that changes it fails a check or a deadline, in fat-g's words, and never runs a turn fat-g did not bound.
- A session fat-g started shows in Claude's own history, where `claude --resume` lists it; removing the session in fat-g leaves it there. A conversation whose first prompt no model answered stays there too, unlinked.
- A turn made in the same conversation outside fat-g is not shown in fat-g, though the model knows of it.
- "Read-only" is Codex's word alone: a Claude session is held to tools that read, and the user's hooks and allowed MCP tools are not fat-g's to hold. *(M22, C45:)* no longer Codex's alone: Claude's reading mode is named Read only + allowed MCP, its name and its line saying that the MCP tools the user's settings allow, and the user's hooks, still act. What stays is that Claude is never described as sandboxed: under Ask first an allow is all that stands before a write anywhere, and under the modes that ask less, not that.
- Adding a send, an answer, an argument or a tool is a change to this decision.
- *(0023, from M20b)* A command of the CLI's that passes through does what it does in the terminal: `/compact` rewrites the context the model holds, a skill runs as the user wrote it. What fat-g tracks is kept by the intercept list, not by the launch.

## Revisit when

- The names the CLI reports change: its permission mode, the tools `init` lists, or the frames' own types. Item 8's lists follow, after a trace.
- `init`'s `capabilities` no longer lists `msg_lifecycle_v1`, or the `command_lifecycle` frames stop: every turn would then end at item 12's 30 s, and item 9 needs another bound.
- Approvals or write access are planned (M22): items 3, 4 and 5 change together, as they did for questions answered in the chat (M21). *(M22 changed them, with items 2 and 8: [0027](0027-execution-permissions.md).)*
- The CLI takes `bypassPermissions` only with a flag that bypasses permissions, or stops changing one of item 2's three modes on a live process: Berserk is then unavailable with its reason, and the change is a restart ([0027](0027-execution-permissions.md), items 4 and 9).
- The CLI's question tool changes its name, its input or what its answer must hold: items 3 and 5 follow, after a trace (M21, K1).
- Anthropic documents this protocol, or publishes a supported interface for sessions: prefer the documented one.
- Claude can give a session's earlier turns back without a file being read: item 13.
