# 0019 — Conversation store: what was said, in a SQLite file of its own, until the user removes it

> **Rule:** fat-g keeps the conversations of the sessions it ran in one SQLite database, `conversations.sqlite`, beside `records.json`, read and written only by the main process through `node:sqlite`. It holds what was said, what each session did between its messages and each turn's ends, never a frame or an account field. An accepted prompt is on disk before it is sent, and nothing sends one again. Only an explicit removal by the user deletes conversation data, and what it deletes is overwritten. *(M22b, [0029](0029-plans.md):)* a plan's text is conversation content kept beside it, in the plan store, and its line is an item here. *(The maintainer:)* a plan is deleted from the plan store once it is implemented or discarded; its lines and prompts stay here, and a conversation keeps where a plan it took part in was implemented. A store this build cannot read is left exactly as it is until the user chooses Start fresh, which moves its files aside together.

## Context

Format version 12: a user message accepted from the session's queue keeps `fromQueue: true` in its body, whether it starts a turn or enters a running one. The page labels it “(from queue)”, including after a restart. Both envelope versions rise together; no migration is added.

- M15 kept a session's messages in memory, 500 at most, and lost them at quit; what a restart showed was whatever Codex's history read gave back. Claude gives nothing back over its session protocol (M16, C49), and Codex leaves out what it does not keep. A chat fat-g showed could not be shown again.
- Conversations are large, are read a page at a time, and change one item at a time. `records.json` is rewritten whole at every change, and holds references only ([0011](0011-records-store.md)).
- Three spikes settled the driver and its settings on the Electron the app ships (conversation-store.md (private research note)): `node:sqlite` loads in the tests, the development build and the packaged build with nothing added to the package (K1); a store left by a killed writer is read, and a refused one keeps its bytes, in write-ahead mode with a read-only check (K2); and SQLite's defaults leave a deleted chat's text in the file, which two settings and a checkpoint remove (K3).

## Decision

1. **File:** `conversations.sqlite` in the user data folder, in SQLite's write-ahead mode, with the `-wal` and `-shm` files SQLite keeps beside it while it is open. The store is those files together: committed work can be in the log alone, so a move takes all of them.
2. **Driver:** `node:sqlite`, the module of Node itself and of Electron's Node. No dependency is added, nothing is built per system or unpacked, and the package's allowlist and fuses stay as they are. One module opens a connection (`conversations/open.ts`), and one touches the file system (`conversations/files.ts`).
3. **Envelope:** SQLite's application id marks the file as fat-g's, and the one row of `meta` holds `schemaVersion` and `minReaderVersion`. They are read on a read-only connection before anything is written. A file that is no database, has another id, or lacks the versions or a table or column this build needs is refused as damaged; one that needs a newer reader as newer; an earlier format as older, with no migration before the first release ([0014](0014-format-compatibility-starts-at-first-release.md)); one that cannot be opened as unreadable. *(M19:)* the versions are compared before the tables and columns, so that an earlier format, which lacks a later one's column, reads as older and not as damaged. A missing or zero-length file is a store not yet made. The check is bounded — never a scan — and nothing repairs, salvages or rebuilds a store.
4. **A refused store is left as it is,** its main file and its log byte for byte. Sessions stay listed and take no prompt, and no session, project or orphan removal is offered, until the user confirms Start fresh: the files are renamed together to `conversations.set-aside.<UTC date and time>.sqlite` and its sidecars, and a new store is opened. fat-g never reads a set-aside store again; the storage view lists them with their size and removes them when asked.
5. **What is kept:** per conversation, its id — its session's id — the provider's session reference with the folder and the configuration folder it started in; per turn, a stored place, the provider's own id for it, when it was accepted, whether the provider took it, the provider's end and the session's end, kept apart; per item, a stored place, its kind, where it came from, the provider's id for it, its times, and its content: role, phase, text, questions, a notice's kind and its bounded detail. *(M19, C14, C44:)* an item also says whether it is complete, and a turn how long it ran by fat-g's own steady clock. *(M20a, C28–C31:)* an item of the kind `activity` holds what the session did — its type, the provider's name for it, a summary, its input and its output, the files it names, an edit's changes, a checklist's steps, its status, its exit code, its duration and what was cut — each bounded as [0024](0024-a-sessions-work.md) says; and an item says whose it is, the session's own or a worker's by its id, a worker's being in no answer of the session's own and read by that id. *(M20b, C28–C30, C35:)* a conversation may name a parent: an aside's ([0025](0025-asides.md)) names its session's, with its source — what it was asked about, the item or the file's real path, the lines, the passage cut to its bound, and where the passage lies in what was drawn, as two offsets and a digest — and its title; its `reference` stays empty, a side thread's id living in the adapter alone. A message's content may name the model its reply said wrote it. A turn may be marked as one fat-g answered itself ([0023](0023-cli-commands-pass-through.md)): no provider took it or ended it, and it reads as ended. *(M21, C4, C32, C33, C61, C62:)* an item of the kind `interaction` holds a question the session asked ([0026](0026-questions.md)): its mode, its questions — each its text, its header, its options with their descriptions, whether several may be chosen, whether free text is taken and whether the answer is a secret — what was cut, its answers by the places of what was chosen with the text typed, its outcome, when it was settled and when the CLI confirmed it, the turn that answered it and what withdrew it. It is written when the question is raised, an asked message's with that message, and each later change sets its named fields alone, under the outcome it expects to find. A secret answer's text is never written: the item keeps that one was given. An outcome stored as pending reads as dropped once the run that raised it is over. *(M22, C12, C25, C48, C57, C77, C81, C83, C92:)* a conversation holds its chat's mode — the id of one of its provider's modes — and where it came from: the chat, the project's default, the user's, or the provider's fallback ([0027](0027-execution-permissions.md), item 7); an aside's holds neither. A turn holds the mode the chat had when its prompt was accepted, and none for an imported turn or an aside's. An item of the kind `interaction` may be an approval's, told from a question's by its body's own kind, a body that names none being a question's, so that no item kind is added. It holds the request as its adapter read it — whether it is a command, a file change or a tool's use, the CLI's name for what asks, a summary, the working folder, the paths, the model's reason, what the CLI would also grant, the choices, and the action itself: a command or a tool's input cut at 10,000 units, a change's text at 20,000 and the first 20 changes, said cut — its outcome, when it was decided or otherwise settled, whether its reply was delivered, when the CLI confirmed it, what withdrew it, and, for a decision that sent a session grant, what the grant covered and the key of the process it was written for ([0027](0027-execution-permissions.md), items 11 to 17). It is written when the request is raised; the decision is one write, before anything is sent; and each later change sets its named fields alone. Whether a grant is live is never stored: it is laid over at each read, from the session's current process. A stored pending outcome reads as dropped, as a question's does. *(M22b, C17, C27, C56, C69, C74, C76; [0029](0029-plans.md), items 5 and 8:)* an item of the kind `interaction` may be a plan's line, its body's kind `plan`: the plan and the version it stands for, whether it was made in the chat or brought into it, whether a provider's request holds it, its outcome — writing, pending, feedback, executed, cancelled, withdrawn, dropped or unfinished — and when it was decided and settled, and never the plan's text, which the plan store holds ([0029](0029-plans.md), item 4). A prompt item may name its plan, the version and whether it revises or executes it, and a turn whether it was a plan turn. *(M22e, C53:)* a prompt's plan fields may also read `review`: the prompt fat-g composes for a plan's review, which reads the plan it names, revising and carrying out nothing. A review's rounds, marks and integrations are the plan store's ([0029](0029-plans.md), item 14); the store holds only its prompts and answers. A brought plan's line stands in a turn of fat-g's own, never sent. A line a request held reads dropped once its run is over; one no request holds stays pending; one being written reads unfinished.
6. **Never kept:** a raw frame, account identity, credentials, usage readings. The store takes only what the agent events' schemas let through. *(M20a, C30:)* a command line and a tool's output were on this list while nothing recorded them; they are conversation content now, kept as an activity's input and output, in the store alone ([0024](0024-a-sessions-work.md)).
7. **A prompt is recorded before it is sent,** in one synchronous transaction inside the step that accepts it, with `synchronous=FULL`. A prompt that cannot be recorded is not sent. A turn the provider never confirmed, or never ended, reads as such after a restart; no end is invented, and nothing sends a prompt again.
8. **Two ends.** The provider's end of a turn is stored when the provider itself says the turn is over, and first *(round 3)*; the session's end when the session stops running for it, or a quit stops it. An end an adapter makes itself is the session's alone *(round 2)*. `records.json` holds the session's end only, and the two stores are reconciled by the session's id and its last turn's id each time a session becomes listed.
9. **Order is stored,** never derived from a time, a text or a list's position. History read from a provider is matched by the provider's turn id, else by the id a prompt was sent with, and is kept, paged and removed as recorded content is.
10. **Retention:** until the user removes it. Nothing ages out, and a missing, unreadable, refused or set-aside `records.json` deletes nothing: a conversation without a listed session is kept, counted, readable, and removed only when the user asks.
11. **Removal** of a session, a project or the sessions without a project takes their conversations: marked, the records removed, then the rows deleted, and a removal a crash cut short is finished in that order at the next open. What is deleted is overwritten and its space given back (`secure_delete`, `auto_vacuum`, a truncating checkpoint) *(round 2)*. Nothing in a provider is deleted. *(M20b, C32, C71:)* an aside is removed by itself, or with its parent: a session's removal marks and deletes its asides with it, in the one removal, and a conversation with a parent is never listed or counted as one without a session. *(M22:)* an approval, its decision and its grant are content of their item and go with it: a removal leaves nothing of them in the store's files, and a chat's mode goes with its conversation's row. *(M22b, C18, C62, C73:)* a session's removal leaves its plans, which are its project's; a project's removal settles the decisions waiting on its plans, then takes them from the plan store, marked once for its whole scope before the records' write ([0029](0029-plans.md), item 9).
    *([0025](0025-asides.md), item 9:)* explicitly closing a side question's tab is its removal; quitting or restarting is not. Saved side questions restore their tabs from existing conversation metadata, with no stored-format change.
12. **Unknown fields are kept:** a table or a column this build does not know is never touched, a row changes by an update of named columns, and no row is deleted and written again outside a removal.
13. **Access:** only the main process opens the store; the Main window reads pages over typed IPC channels, and the Pet gets none of it. Logs hold counts and error kinds, never a text, a detail, a name, a reference or a path.
14. **A message is kept while it is written** *(M19)*. At its first text an assistant's message is put in the store at a place reserved for it, marked incomplete. While it grows, its text is written again at most every two seconds, and once more when its turn ends and when fat-g quits, each in the same durable transaction as any other write, the flag that says it was cut to its bound together with the text. The provider's whole message completes it in one transaction: text, cut flag, phase, questions and the mark, and nothing else of the row. An end that brings no whole message — a Stop, a lost process, a quit, a kill — leaves it as it is: incomplete, with what was received, never deleted and never completed by fat-g. Where the provider's history holds the message, a history check that comes to its turn completes it, and the check's walk is not lengthened to look for one. Read back, it is `streaming` only while the turn that writes it runs in this process, and `partial` otherwise.

15. **Local session search** ([0035](0035-session-search.md)) reads bounded pages of normalized user and assistant messages through this store, excluding side questions, workers and conversations being removed. Successful text writes, history merges and removals notify the in-memory index by identifiers after commit; rollbacks notify nothing and close or Start fresh resets the index. No table, index, file or format version changes. Only the Main window receives bounded result excerpts; neither search text nor results reach logs, app-state snapshots or the Pet.

## Consequences

- A chat is there after a quit, a crash and a restart, whatever its provider can read back, and a conversation of any length loses nothing: the page holds a window, and the rest is read from disk.
- What was said to a provider is now on the user's disk in fat-g's folder, in clear. `PRIVACY.md` says so, names each file, and says what a removal cannot reach: a copy the system or the drive keeps.
- The driver comes with Electron's Node: an Electron upgrade can change it, and the three spikes are run again before one lands.
- Every commit waits for the disk, about a millisecond each. *(M19:)* a message that is being written is committed the same way, at most every two seconds: a kill loses at most the last two seconds of an answer, and never a prompt.
- *(M19)* The format is at version 2 — an item's complete mark, a turn's elapsed time — and an earlier store is refused as older.
- Records are at version 4, for the last turn's id: an earlier `records.json` is refused as older.
- *(M22)* The format is at version 6 — a conversation's mode and its source, a turn's mode, an approval's body — and an earlier store is refused as older. Records are at version 5, for a project's default modes ([0011](0011-records-store.md)).

## Revisit when

- Electron is upgraded: K1, K2 and K3 run again first.
- The two seconds between a growing message's writes prove too long, or too many writes: the chat protocols note (private) holds what each interval cost (M19, K4).
- M23 adds attachments: blobs are stored beside the database, with their own ownership and deletion rules; the store reserves the kind alone.
- The first public release is prepared: the format records its baseline ([0014](0014-format-compatibility-starts-at-first-release.md), item 4).
- A second process needs the store.

## Explicit full-data reset

[Decision 0038](0038-full-data-reset.md) adds a separate, twice-confirmed removal of all data in the current installation's data folder, followed by a normal quit and cleanup before the next startup. This explicit operation removes even unreadable files, backups, catalog overrides and user media; the ordinary read-only, retention and set-aside behavior in this record is unchanged outside that reset. No project or CLI folder is reached.
