# 0036 — Adding an avatar, and replacing its images, from an image

> **Rule:** an image the user drops on, or chooses at, the family editor's drop zone is decoded and scaled in the page alone. It is scaled by a Lanczos-3 filter over premultiplied colour, as fat-g's own art is made, to a PNG portrait of at most 512 px and a PNG small of 64 px. Main never decodes it: it checks both PNGs by their headers, creates the new avatar's folder in the family without overwriting anything, writes the two files there and the avatar's entry with its matches into `family.json` at once from the revision the editor holds, and scans again. An image dropped onto, or chosen for, an avatar's main image replaces it and its small version, and one for its small version that alone, the same way; the old files go to the system's trash. Browse is the system's chooser, opened by main at the folder the last image came from, chosen or dropped, which it holds in memory for the run. The dropped or chosen file itself is kept nowhere else. A new family started from an image uses the same preparation and checks, creating its required Default and an optional matched avatar in an exclusively reserved user family folder (item 7).

- **Status:** Implemented from the maintainer's approved plan; then, at the maintainer's word, an avatar's images replaced and Browse at the last folder (items 5, 6).
- **Applies to:** `src/shared/contracts/avatar-family.ts` (the new avatar's name, the two sides, the requests and their answers), `avatars:addAvatar`, `avatars:replaceImage`, `avatars:chooseImage`, `avatars:noteDropped` and the preload's byte bound and dropped file (`src/shared/ipc/channels.ts`, `src/shared/ipc/bridge.ts`, `src/preload/index.ts`), `src/main/avatars/add-avatar.ts`, `replace-image.ts` and `image-source.ts` with `authoring.ts` and the service, Electron's `shell.trashItem` and `dialog.showOpenDialog` in `src/main/index.ts`, and in Settings → Avatars the family editor's drop zone, `avatar-image.ts`, `lanczos.ts` and the Add avatar popup; `PRIVACY.md` and [`docs/avatars.md`](../avatars.md). Amends [0031](0031-avatars.md), whose editor created no file, and builds on [0030](0030-attachments.md)'s bytes from the page.

## Context

Before this, the family editor edited `family.json` alone: making an avatar meant making a folder by hand, placing a square image named `portrait.png` or `portrait.webp` in it, and choosing Rescan. Its size was the user's to get right, and a `small` was rarely made, so avatars at 36 px and less drew a scaled-down portrait. The maintainer asked for a drop zone under the family's avatar list that takes an image of any size and makes the files itself, filtered well, so that added art looks like the art fat-g ships.

0031 ruled out fat-g making derived copies, since that is a decode. Main runs with the user's rights, while Chromium's page is sandboxed: decoding an image the user hands over belongs in the page.

## Decision

1. **The image.** A PNG, JPEG or WebP, by its signature, within the one image bound (5 MiB, 8,000 px a side), square, and at least 64 px a side. Anything else is refused in words under the drop zone. A folder is refused unread. The page reads the file's bytes; no path crosses IPC.
2. **Decoded and scaled in the page.** Chromium decodes it, its colour profile converted to sRGB. A side past 4,096 px is first brought to 4,096 by Chromium (`resizeQuality: 'high'`), which bounds the memory the next step takes.
   - The **portrait** is 512 px. A larger image is scaled down to it. An image of 512 px or less keeps its side: a PNG of it keeps its very bytes, and any other is encoded as a PNG of its pixels. Nothing is scaled up.
   - The **small** is 64 px, scaled from the image itself, never from the portrait.
   - The **resampler** is a separable Lanczos filter of three lobes whose support widens with the reduction, over colour premultiplied by alpha, in the stored sRGB values. These are the coefficients of Pillow's `LANCZOS`, which [`maintaining-avatar-art.md`](../maintaining-avatar-art.md) uses for the built-in art; a test holds it to Pillow's output within its 8-bit rounding. It gives the page back its thread every few milliseconds.
3. **The popup.** It shows both images, the new avatar's **Name** and its **Matches**, with *Takes now* for the family as the draft makes it. The name is filled in from the file's. It is of 1 to 64 letters, digits, spaces and `. _ - ( ) +`, a letter or digit first and no space or dot last, not `Default` in any case and no Windows device name. It may be no name the family holds, folder or entry, in any case.
4. **Written at once.** Add avatar sends `avatars:addAvatar` the family's reference, the revision of `family.json` the editor holds, the name, the matches and both PNGs. It is the Main window's alone, and the preload measures each image's bytes before forwarding, as it does an attachment's. Main finds the family by its last scan, and then, in the one queue saves, copies and scans share:
   1. Main checks the family as a save does. The root must be writable, the folder no link and one name inside its root's real path, and the file no link. The file is read again, and a revision other than the editor's is a conflict. A refused file locks the family.
   2. It checks the name again, against every entry of the family's folder and every folder the file names, in any case, and `family.json` and `LICENSE.txt` too.
   3. It checks both images by their headers alone, with the one reader: the portrait a still square PNG of 64 to 512 px, the small a still PNG of 64 px.
   4. It reserves the folder exclusively and writes `portrait.png` and `small.png`, never overwriting anything.
   5. It writes `family.json` with the new entry last, as Save family writes it: the same writer, unknown fields and `defaultFor` kept, beside it as a temp file renamed over it. A failure after the folder is reserved removes that folder alone.
   6. It scans both roots, reads the family again and answers both: the editor takes the new revision, adds the entry to its draft beside the user's other unsaved changes, and selects it.

   A conflict, a lock or a family no longer listed is told in the editor's footer, as a save's would be.
5. **An avatar's images replaced.** The chosen avatar's detail — the Family default's too — shows its **Main image** at the model column's size and its **Small version** at the capsule's, near its own (the main image where it has none), each described at its left: what it is, its size, and how to replace it. An image dropped onto the main image, or chosen at its **Browse**, is made into a main image and a small version as Add avatar's is, and replaces both; one for the small version is made into a small alone, and replaces that. `avatars:replaceImage` names the family, the avatar's folder as the scan lists it and the PNGs. Main checks the family as a save does and the avatar's folder as one the scan lists, its real path unchanged; judges the PNGs by their headers as Add avatar does; writes each new file beside the old under a name of its own, never over anything; then, a role at a time, sends every file of that role — `portrait.webp` as well as `portrait.png`, in any case — to the system's trash, from where the user can restore it, and moves the new one into its place as `<role>.png`. A trash that will not take a file stops the replace there, the new files not yet in place removed. `family.json` is not touched, and both roots are scanned again before it answers. A smoke or stream run, whose data folder is scratch, removes the old files instead.
6. **Browse at the last folder.** Browse — the Add avatar zone's press, and each image's — is the system's file chooser, which main opens (`avatars:chooseImage`) at the folder the last image came from, held in memory for the run alone, never stored or logged; before any, wherever the system's own chooser remembers. Main reads the chosen file whole within the one image bound and answers its name and bytes, never its path. A dropped image's folder counts as well: the page hands the dropped file to the preload (`noteDroppedFile`), which reads its path with Electron's `webUtils` and tells main (`avatars:noteDropped`); the page never holds the path, and the preload refuses a page that names that channel itself.

7. **A new family from an image.** The drop zone under **Avatar families** uses the same drop/browse and sandboxed preparation as Add avatar. Its popup asks for the family name and previews both PNGs. Without matches, the image is the required `Default` avatar alone; optional matches add a named avatar with the same two images beside it. **Create family** sends the names, matches and PNGs through Main-only `avatars:createFamily`, with both image byte bounds enforced in the preload. Main validates the portable names and image headers, reserves a new folder exclusively under the user's avatar root (never a built-in root), and writes `Default/portrait.png`, `Default/small.png`, the optional named avatar's same files, and a current-version `family.json` with the default provider scope and look. Any existing root entry of the family name, in any case, is refused. A failure removes only the newly reserved folder after checking its real location again. Creation shares the service's scan/write queue, publishes the new listing and opens the family editor, without changing any provider's active family. Cancel and Escape before creation write nothing; Escape is held while writing. Logs contain a fixed operation and counts alone.

## Consequences

- An avatar can be made from any square image without leaving fat-g, and always has a small.
- Added art is filtered as the built-in art is, but encoded as PNG: an added family takes more room than a built-in one, which is WebP at quality 90.
- Add avatar writes before Save family does: cancelling the editor afterwards keeps the new avatar, as Make a copy's copy is kept. Removing one is still the file manager's.
- A JPEG's or a WebP's own bytes are never kept: an added avatar is always the PNGs the page encoded.
- The log says that an avatar was added, or an image replaced, never a name.
- Replacing an image cannot be undone in fat-g: the old file is in the system's trash, from where the user restores it. Replacing a main image replaces its small version too, a small made by hand among them.
- Browse forgets its folder when fat-g quits; the system's chooser remembers its own last folder, which is where the first Browse of a run opens.

## Revisit when

- An avatar's art needs cropping, or framing a non-square image: that is a choice of the user's, which this record leaves to them.
- Built-in art should be made by the app rather than by the art recipe.
- Added families grow large enough that WebP output is worth its encoder.
