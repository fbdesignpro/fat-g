# 0027 — Execution permissions: a chat's mode, approvals from the card, and the CLI's own session grant

> **Rule:** what a session may do is a mode of its chat: one of the modes its provider declares, named in fat-g's own words, resolved in main as the chat's saved mode, else the project's default, else the user's, else Auto reviewed (or the reading mode where unavailable), and kept in the conversation store alone. The installed CLI enforces it: fat-g names the mode at every start, checks what the CLI reports before any prompt, and sends nothing after a difference. Under a mode that asks, the CLI's request to run a command, change a file or use a tool is a card in the chat at its place, showing the whole action, with Approve once, Deny and Stop — and, where the CLI itself offers one, Approve for this session: the CLI's own session grant, passed back as the CLI wrote it, which lasts for the session's process and no longer. fat-g keeps no rule of its own, matches no request and answers none the user did not, sends no rule a CLI would save, passes no flag that bypasses permissions, and sets up Codex's sandbox only at the user's press.

- **Status:** Accepted by the maintainer with M22's final spec (spec sheet (private): S1–S9 and the items of C1–C109 that stand, C98–C114 being the amendments its implementation and its acceptance made), from the chat roadmap's M22 outline and chat decision P3 as the maintainer amended it (chat decisions (private)). Implemented in M22. The maintainer's acceptance with the installed CLIs (M22, V26) was made, with the visual review before it (V10), and is recorded in the milestone document. The amendments its implementation and its acceptance made are the spec sheet's rounds 4 and 5, C98–C114. M22b, amended items 8, 10, 15 and 22 (C1, C5, C7, C10, C56, C58, C61, C79; [0029](0029-plans.md)): a plan turn is a mode of one prompt, the chat's mode standing and held while a plan's decision waits; the checks follow a plan turn's three changes; the registry holds Claude's plan request; and a line over the limit is read for its tool's name too. Items 2 and 16, at the maintainer's word ([0018](0018-codex-sessions.md), item 7): Codex's leave to run an MCP tool is a card under Ask first and Sandbox ok, its session grant that tool's; and Codex's reading mode is named Read only + allowed MCP, as Claude's is, since an MCP tool its server marks as safe runs with no request under every mode. Item 4, at the maintainer's word ([0020](0020-claude-chat-sessions.md), item 5): Claude's four modes that act are offered `WebFetch` and `WebSearch`, a card for one headed by its address or its query, and the lines of Read only, Ask first and Edits ok say what of the web asks.

## Context

- Until M22 a session could read and ask, and nothing more. Codex ran in its read-only sandbox with approvals off ([0018](0018-codex-sessions.md)), Claude was offered five tools that read or ask ([0020](0020-claude-chat-sessions.md)), and every request either CLI made for an action was refused with a notice. The agent could not change a file or run a command, and the user could not let it. M14 had built the place for an approval — the session's attention, "1 APPROVAL" on its capsule — and M21's registry already named the kind.
- The two CLIs hold a session back by different means, traced under the app's own launches (chat-protocols.md §15 (private research note); M22's K1, K2, K4, K5 and K6). Codex pairs a sandbox with an approval policy and names who answers its requests; a policy once named stays with its thread, no frame reports it, and only the reply to a start or a resume that named a sandbox says which one a thread has. On Windows an account's sandbox may not be set up, and a start that asks for one is then taken with no error and answered read-only. Claude has no sandbox: it has permission modes, changed on a live process or at launch, and a tool list; one mode is taken at launch alone.
- Each CLI offers to remember an answer, and each would save it where fat-g must not go: Claude's suggestion, sent back as it came, is written into the project folder ([0015](0015-no-writes-into-project-folders.md)); Codex's amendment allows the command in every project of the account; and neither lists what it saved or takes it out. Each also has a grant that lasts for the session's process and no longer.
- Chat decision P3 had asked for remembered rules with review and revocation from the first approval release. With those findings the maintainer narrowed it: the CLI's own session grant, fat-g's record of what it sent, and the end of the process as what revokes.
- A user's own configuration acts beside all of this. An allow rule, an allowed MCP tool and a hook run with no request fat-g ever sees.

## Decision

1. **A mode is its provider's to declare, and the chat's to have.** A provider's descriptor declares its modes once, in `capabilities.permissions`: for each, an id of the provider's own, stable; fat-g's name for it; one line saying what runs without asking; whether it sends the CLI's requests to the user; whether it is the provider's reading mode; and which other modes reach it on a live process. With them it declares the fallback, and lines of its own: what the user's configuration lets act (item 5), what is known of the CLI's own rules, and — where an account may need a setup — what that setup changes on the machine and who asks for leave (item 20). A provider shows its own modes alone. An id is checked against the chat's own provider's list and never carried to another, and similarly named modes of two providers are never treated as one. No shared file, no channel and nothing in the page holds a CLI's word for a mode: each adapter maps an id to its CLI's fields in one file of its own folder.
2. **Codex's five are a sandbox, an approval policy, and who answers.**
   - **Read only + allowed MCP** *(formerly Read only)* — the read-only sandbox, `never`, no reviewer: nothing that changes a file runs, and every request for leave is declined at once, as before M22. An MCP tool its server marks as read-only, or as neither destructive nor reaching outside, still runs, with no request, under this mode and every other, and may act: its name and its line say so, as Claude's reading mode does. Codex refuses any other MCP tool itself under `never`.
   - **Ask first** — workspace-write, `untrusted`, the user: each command asks before it runs, unless Codex holds it safe or a rule of the user's own configuration allows it, and so does each file change, the session's folder included. An accepted command is held to the sandbox's places; an accepted file change is written wherever it names.
   - **Sandbox ok** — workspace-write, `on-request`, the user: what stays in the sandbox's places runs with no card; a file change outside them asks, and is written there once accepted; a command outside them is stopped by the sandbox.
   - Under Ask first and Sandbox ok, an MCP tool Codex asks leave for — one its server does not mark as safe — is a card ([0018](0018-codex-sessions.md), item 7).
   - **Auto reviewed** — the same sandbox and policy under Codex's own reviewer, which answers in the user's place what would have asked, a change outside the folder among it, an MCP tool's leave too. No card comes for what it decides; its frames are counted and not drawn, the reviewed action's own item being the chat's record.
   - **Berserk** — full access, `never`, no reviewer: everything runs without asking, outside the folder too. Its line names Codex's word for it, Full access.

   Every `thread/start` and `thread/resume` names the mode's three, a mode whose policy asks no one naming no reviewer; the reply is held to all three before any prompt; and every `turn/start` of the session's thread names again what that reply reported, and never another ([0018](0018-codex-sessions.md), items 2 and 3).
3. **Where a Codex sandbox mode can write is read from the reply,** and never held as a constant: the session's folder, which is the one folder Codex is given; the temporary folders, unless the reply excludes them; any other root the reply lists; and its word on the network. fat-g asks for no exclusion and adds no root. What the reply reports beyond the folder and the temporary ones is the user's own Codex configuration, shown as such and not refused. On an account with no sandbox Codex answers a workspace-write start with the read-only one: Ask first is available there and says so — every write asks, and an accepted one runs unconfined — and Sandbox ok and Auto reviewed are not.
4. **Claude's five are a permission mode and a tool list.**
   - **Read only + allowed MCP** — `default`, with the five tools that read or ask: every request to act is refused, as before M22. Its name and its line say that the MCP tools the user's settings allow, and the user's hooks, still act; its line says it searches the user's files, so that it is not taken for a web search.
   - **Ask first** — `default`, with those five, `Bash`, `Write` and `Edit`, and `WebFetch` and `WebSearch`: each command, file change, web search and fetch asks before it runs, and so does anything else Claude asks leave for, unless a rule of the user's configuration allows it. Its line says that Claude fetches its own list of documentation sites without asking, which the CLI does under every mode. A fetch's card is headed by its address and a search's by its query; its session grant is the CLI's rule, a fetch's site or every search.
   - **Edits ok** — `acceptEdits`: file changes run without asking, and so do the commands Claude holds safe and the fetches of its documentation sites; other commands, searches and fetches ask.
   - **Auto reviewed** — `auto`: Claude decides by itself what would ask, outside the project's folders too, with no card.
   - **Berserk** — `bypassPermissions`: everything runs without asking. Its line names Claude's word for it, Bypass permissions.

   A sub-agent runs under its session's mode, and the three lines that let a session act without a card say so. Claude has no sandbox and is never described as sandboxed: under Ask first an allow is all that stands before a write anywhere, and under the other three not that. The launch names the mode's word and its tool list, and the reply to the launch, each turn's `init` and each status frame that names a mode are held to the mode in force ([0020](0020-claude-chat-sessions.md), items 4, 5 and 8). Berserk is the launch's mode argument and nothing more: no flag that bypasses permissions is ever passed, and where a CLI would take the mode only with one, Berserk is listed unavailable with that reason.
5. **No line promises a card before every action.** A rule, an allowed MCP tool or a hook of the user's own configuration acts as that configuration lets it, with no request fat-g sees. Under every list of modes — the chat's menu, Settings, the project dialog — stands the provider's one line that says so. An execution mode does not approve every later request, and a CLI may act within its policy without asking. What is known of the CLI's own rules is one line beside a session's grants, with its actual limit: the Claude CLI traced lists none, and Codex lists its permission profiles and not its rules. fat-g reads no rule from a configuration file, asks for no general dump of one, and never claims to have revoked a rule of the user's.
6. **What an account can use is told per account, with its reason.** For each declared mode the adapter says whether the account can use it and, where it cannot, why: no capture shows a turn under it on this CLI version; the CLI's sandbox is not set up for the account; the CLI takes it only with a flag fat-g never passes; or the system has none. It also says whether a Set up control is offered, whether choosing the mode makes the CLI record the folder as trusted (item 21), whether the account has no sandbox for it, and a sandbox mode's writable places. A mode an account cannot use is still listed, with its reason. Each adapter holds one constant of the modes a capture shows a turn under, which is how a mode is held back for a later CLI version; each lists its five. An account's availability is on its snapshot for the Main window alone, since a writable place is a path: the Pet gets the descriptor's words, and nothing of an account or a chat.
7. **The hierarchy is resolved in main, in one place.** The chat's saved mode; else the project's default for the provider; else the user's default for the provider; else the provider's fallback, which is Auto reviewed on both — or its reading mode, where the account cannot use the fallback. This default was chosen by the maintainer, replacing Ask first. A new chat's mode is written to its conversation with where it came from — the project's default, the user's or the fallback, and the chat itself once it is changed there — when its session is first listed and has not started, and with its first prompt where that write could not be made: the snapshot, which a later change of a default never touches. A saved mode stands, whatever has become of the lists since: one its account cannot use blocks Send with its reason until the user chooses another, and nothing substitutes for it. The user's defaults are per provider in the preferences ([0005](0005-preferences-compatibility.md)) and a project's per provider in its record ([0011](0011-records-store.md)), "Use my default" being no entry. Changing a chat's mode writes its conversation alone; saving a default is the act of its own control.
8. **No mode for one prompt alone.** A chat's saved mode, changed from its header, is the one way to change what a session may do. Neither CLI's own application has a mode chosen for a single prompt. *(M22b, C1, C5, C58; [0029](0029-plans.md), item 1:)* one exception: a plan turn, which the Plan toggle sends with a prompt, is a mode of that prompt alone, and the chat's mode is not changed for it. While a plan's decision waits, the chat's mode cannot change. *([0029](0029-plans.md), item 21:)* but while the chat's plan is ready, by the user's word alone: a Claude request the chat holds on the plan is answered as Cancel answers it, its turn ended, and the mode then changes, the plan's decision standing on the same version. Under review or being revised, it still cannot.
9. **A change of mode is taken with nothing running, and the session is busy under it.** `chat:setMode` is refused while a turn, a worker, a pending request or an aside runs on the session, while another change is under way, and while a setup holds the account (item 20). It checks the mode asked for against the provider's list and the account, and never the mode it replaces. From the request until the choice is written or refused, a prompt, an aside's question, a decision and a second change are refused. How the change is made is the adapter's to say:
   - **On the live process,** where the provider declares it — Claude between Ask first, Edits ok and Auto reviewed, by `set_permission_mode`: confirmed by the CLI's reply, then written. A change the CLI does not confirm saves nothing, leaves the chat's mode as it was, and blocks Send.
   - **By a restart,** for every other change — Codex's always, and Claude's into and out of its reading mode and of Berserk: the choice is written at once, the live process is closed, and nothing is launched. The next start opens under the saved mode, and its check confirms it before anything is sent; until then the header says that the mode applies at the next prompt, so no choice is saved silently.

   A Codex thread's policy changes in that one way: the process closed, then a resume in a fresh process naming the new mode, its reply checked. A move into a reading mode is always a restart, so no grant is alive in a reading session; out of Berserk is a restart as into it, so no process launched able to bypass permissions lives under another mode's name.
10. **A start that reports another policy sends nothing more, and blocks Send.** Each adapter says which mode its process confirmed, by fat-g's id for it, and a session's summary shows that and nothing else. A start or a resume whose reply reports another policy than the mode's fails its turn with a notice — for a mode other than the reading one, a notice that carries what the CLI reported, in its own words — and a later report of another mode ends the process. Send is then blocked until the user chooses a mode again: another, or the same for another try. The two blocks, a mode not confirmed and a mode the account cannot use, are the last of the gate's order and hold a prompt and an aside's question alone — never the change that remedies them, nor a decision on a card the live process raised. A process started again after a loss, a crash, a forced end or a restart of fat-g is confirmed on the chat's saved mode the same way, and one found in force under another mode than the chat's is closed at the next Send. *(M22b, C7:)* a plan turn's change into `plan`, Execute's return to the chat's mode and the restoration at the turn's end are each checked as a change is: a reply or a report naming another word blocks Send.
11. **A request for leave is an item of the conversation.** Its kind is `interaction`, as a question's is ([0026](0026-questions.md), item 2), with a body that says `approval`. The adapter reads the CLI's request into one bounded, provider-neutral view: whether it is a command, a file change or a tool's use; the CLI's name for what asks; one line of summary; the working folder, where the request names one; the paths it names, and whether the CLI said one lies outside the folders the session was given; the model's own reason; what the CLI's own offers would grant beyond this action, each said by its kind and never passed back; the whole action; the choices; and what a session grant would cover. The adapter keeps the request as it came, in memory, and answers from that. The card stands at the action's place, a worker's in its worker's tab. It says who asks, for which account where the provider runs several, and exactly what would run or change, with the whole action behind a disclosure that is drawn only once opened; the model's reason is labelled as the model's and drawn as text ([0021](0021-drawing-conversation-text.md)); an edit by match says whether every matching passage is replaced or the first. No file is read to fill a change in ([0024](0024-a-sessions-work.md), item 2).
12. **Shown whole, or refused.** A card holds at most 32 paths, 32 changes and 16 choices, a path of 2,048 units, a command or a tool's input of 65,536, and a file change of 1,048,576 units, its parts counted together. A request past a bound, one that lacks a field its action stands on, and one that names a change its adapter does not hold are refused on the wire, with a notice that names the bound and the size where a size is why, and no card is made: leave is never given on a cut preview. The live card shows the action whole from the registry, which holds the view while the request lives. The store keeps it cut as an activity's is ([0024](0024-a-sessions-work.md), item 3) — a command or an input at 10,000 units, a change's text at 20,000, the first 20 changes — and a card read after its request is gone says so.
13. **Three choices, and a fourth where the CLI offers it.** Approve once; Deny, which refuses this request and lets the CLI go on; Stop, which is the session's own Stop; and Approve for this session where item 16 makes the request eligible, worded by what it covers and never the active choice. Nothing is active when a card arrives, the focus stays where it was, and closing a card, opening a tab or pressing Escape grants nothing. `chat:decide` names the session, the card's item and a choice — never a request's id, a tool's input or a scope — and main takes only a choice the request's own view lists, for a request held pending on the session's current process. Once settled a card is inert and stays.
14. **Written before it is sent; delivery, confirmation and success kept apart.** A decision is one durable write — the outcome, and the grant where the choice is the session's — and a failed write sends nothing. The session then writes the CLI's reply and says whether that write went. The CLI's own word that it took the decision is kept apart from that, and both apart from whether the action then succeeded, which is its activity's status and which the card never claims. A decision is final on fat-g's side once written, and nothing sends one again: one the process did not take says so, and one the CLI never confirmed says so once what carried it is over. Six outcomes, none inferred from time: pending; approved once; approved for the session; denied; withdrawn — the CLI took the request back, its turn or its worker ended, or it changed under its id; and dropped — its process was lost, or fat-g quit or started again, with it pending.
15. **One registry, [0026](0026-questions.md)'s.** It holds approvals as it holds questions, in memory, keyed by session, process generation and a lossless request identity, so that a number and a string of one spelling are two requests. A repeated delivery opens nothing. One that comes again under a held id with another payload is compared by its adapter before it is counted, refused on the wire, and its card withdrawn as changed; a question's the same. A request main cannot place is refused through the session; an owner's end withdraws; a loss drops. A pending approval raises the session's attention of the kind `approval`, and its own turn's action line reads "Waiting for your approval". Nothing pending survives a restart. *(M22b, C10, C27, C56:)* it holds Claude's `ExitPlanMode` request under the `plan` kind, which raises the attention `plan`, read "PLAN READY"; a plan no request holds is not in it ([0029](0029-plans.md), item 6).
16. **A session grant is the CLI's own, offered only where its request makes it eligible.** On Claude: a request that carries an `addRules` suggestion that allows, at whatever destination the CLI wrote on it, and that is not marked as one to keep no rule for. On Codex: a file change that asks for no root, which covers the files of that change; a command only where its own list of decisions holds `acceptForSession`; and ** an MCP tool where its `persist` offers `session`, which covers that tool of that server. Nothing else makes one: a change of mode, a folder, a rule that denies, replaces or removes, a file change that asks for a root, or Codex's amendment to its own rules. What is sent is fixed, whatever came in: on Claude the `allow` with the request's input as it came and exactly that one suggestion, its rules as the CLI wrote them and its destination set to `session`; on Codex `acceptForSession`, or for an MCP tool `accept` with `_meta.persist` `session` and never `always`. No reply of fat-g's names another destination, a mode, a folder or a rule a CLI would save. Where the CLI's only offer is a change of mode, the card names fat-g's mode that would stop the question, and changes none.
17. **A grant is fat-g's record of what it sent, and ends with its process.** With the decision are kept what the grant covered, in the CLI's own words, and the key of the process it was written for: a key main makes at each open of a session's process, unique across runs. A grant is live while that key is the session's current process's, and ended otherwise, which a restart of fat-g makes true of every stored grant. A provider's session holds no list of grants, and none is read from a CLI. A session's list shows the grants whose reply was delivered, each said confirmed or not by the CLI's word and live or ended, and says that it is fat-g's record and no reading of the CLI. One written and not delivered, or of unknown delivery, is told on its card alone. A grant ends with its process and with nothing else — a change of mode that restarts it, the idle close, a loss, a quit, a restart of fat-g. Nothing sends one again after a resume, and fat-g has no control that ends one. A grant answers nothing in fat-g: the CLI alone matches it, a provider's deny wins, and a request the CLI still sends is still asked.
18. **An aside is given neither the mode nor a grant.** Claude's side question takes no tool and Codex's fork is read-only with approvals off, whatever the session's mode ([0025](0025-asides.md), items 4 and 5). A request that names an aside's thread is no one's, and is refused.
19. **A declined action has a status of its own.** `declined`, beside [0024](0024-a-sessions-work.md)'s four, with who declined it where the adapter knows: the user, on the card, or a rule of the user's own configuration. An action that ran keeps the status its provider gave. A declined action's row says what was asked and never that it was done, gives no duration, and is counted apart in its group.
20. **Codex's sandbox is set up at the user's press, and never otherwise.** On Windows, an account whose Codex answers that its sandbox is not ready has the modes that need it unavailable, with a Set up control. Its dialog says before the press what Codex's setup changes on the machine — sandbox user accounts, firewall rules and file permissions, in the vendor's own description — that Windows asks for an administrator's approval by itself, that the setup belongs to this account's configuration, and that fat-g cannot undo it. The press sends Codex's one request, `windowsSandbox/setupStart` in the `elevated` mode, on a short-lived connection of the account's own that starts no thread ([0018](0018-codex-sessions.md), item 2). fat-g asks for, sees and keeps no credential. The outcome is Codex's own word, waited for with no clock of fat-g's, and a success is never taken from that word alone: the connection is closed, and a fresh process is asked whether the sandbox is ready. A setup holds its account: no prompt, aside's question, decision or change of mode of that account is taken meanwhile, and no setup starts while a turn or an aside of that account runs. It has an end fat-g always reaches — completed, failed with Codex's reason, or unknown, where fat-g did not hear its end or a fresh process does not confirm it, said as such with what Codex then answers. No request is sent again but at a new press, the `unelevated` mode is not offered, and nothing of a setup is kept across a restart. On another system nothing is asked, and the start reply alone decides.
21. **What a start makes Codex write is Codex's, and said.** A start under Berserk, and one under a workspace mode on an account whose sandbox is set up, makes Codex record the session's folder as trusted in its own `config.toml`; the mode says so where it is chosen. The setup writes there too. fat-g reads and writes nothing of that file ([0017](0017-provider-instances.md), item 7). And on Windows, the first time Codex's sandbox works in a project's folder, Codex's own setup helper may ask for an administrator's approval to give its sandbox accounts that folder: the three modes that use the sandbox say so, and fat-g sends nothing for it.
22. **A line over the limit is read for its kind and its request id alone.** Of a line over the 4 MiB a session may carry, the first 512 bytes are scanned, with no parse, for whether it is a request and for its id, and are then dropped. A request so read is refused on the wire by that id, with a notice naming the line's size, and its turn goes on. One that is or may be a request and whose id cannot be read would leave the CLI waiting on something fat-g cannot name: everything its process runs is stopped, each by its own Stop — the session's turn with its workers, and each aside — with a notice; with nothing running it is skipped and counted. Any other line is skipped and counted as before ([0024](0024-a-sessions-work.md), item 3). *(M22b, C61, C79:)* the scan reads the tool's name too, so that a request over the limit for `ExitPlanMode` brings the notice that the plan was too large to receive, and no other request does.
23. **In the store and the Main window alone.** The conversation store is at version 6: the chat's mode and its source on its conversation, the mode each turn ran under on the turn, and the approval's body — the request, cut; the outcome; when it was decided or otherwise settled; whether its reply was delivered and confirmed; what withdrew it; and the grant ([0019](0019-conversation-store.md), item 5). Preferences are at revision 6 and records at version 5, each for a default's id and nothing of a chat, a turn, a request or a grant. Each older file is refused, unchanged, with no migration ([0014](0014-format-compatibility-starts-at-first-release.md)). Three channels are new, `chat:setMode`, `chat:decide` and `instances:setupSandbox`, the Main window's only. A request's text, a command's arguments, a proposed change, a decision and a grant reach no log, no summary, no app state and never the Pet: main says kinds and counts.
24. **Every outcome is an event.** The agent events are at version 8: `approval-raised`, with the adapter's key for the request, the id of what carried it and the request, bounded; `approval-resolved`, by a reason — `withdrawn`, `dropped`, `confirmed`, or `changed`, which a question's resolution gains too; `in-force` naming the mode a process confirmed; an activity's end as `declined`; two notices, for a policy the provider reported that is not the mode's and for a line too long to read that may have been a request; and, on the notice of a refused request, which bound it was past and by how much. A session takes a decision through `decide`, which answers whether its reply's write went, and a change on a live process through `setMode`.
25. **What fat-g never does.** It keeps no rule of its own and matches no request. It answers no request the user did not. It sends no rule a CLI would save, and no destination but the session's. It passes no flag that bypasses permissions. It changes no mode from a card. It builds no reviewer, no sandbox and no imitation of a CLI's mode. It reads no rule from a CLI's configuration and edits none. And it sends Codex's setup request only at the press.

## What is left out

- Plan mode, a plan's presentation and its Execute and Revise (M22b), which take this approval path and this registry; MCP elicitation forms and address requests (M22c), refused as M21 leaves them, as an unknown dialog and a legacy approval method are; input while a turn runs, and attachments (M23); forks (M24).
- Rules of fat-g's own, with matching, a project scope and an inspector; a rule a CLI saves beyond the session; and one configuration shared by two accounts of a provider. Later work, if the session's scope proves too little.
- A mode for one prompt alone, and a control that ends a session's grants: neither CLI's own application has either. A user who wants a grant ended changes the chat's mode, or lets the idle close come.
- Codex's `unelevated` setup, its experimental policy fields, and drawing its reviewer's verdict on an action's row.
- A terminal, file editing by fat-g, and an editor of a CLI's configuration.

## Consequences

- A session can now change files and run commands, at the user's word or under a mode the user chose. Under Ask first on Claude, and on a Codex account with no sandbox, an allow is all that stands before a write anywhere; with a sandbox an accepted file change is still written wherever it names; and under the modes that ask less, less stands. The card shows the whole action and says where a path lies outside the project's folders, and each mode's line says what it lets act with no card.
- `conversations.sqlite` now holds what a session asked leave for and what was decided: commands, proposed changes, the model's reasons, decisions and grants, with the chat. [PRIVACY.md](../../PRIVACY.md) says so.
- Three stored formats change at once, with no migration: Start fresh, for each, sets aside what the earlier version held ([0014](0014-format-compatibility-starts-at-first-release.md)).
- A grant's liveness is fat-g's reading of its own process key. A CLI that kept a grant longer or shorter than its process would not be seen to; the list says it is no reading of the CLI, and a request the CLI still sends is still a card.
- fat-g now sends a request that changes the machine, at the user's press: Codex's sandbox setup. What a closed connection does to a setup past Windows' prompt is not known, so that end is said as unknown and never taken for a failure.
- Both CLIs' modes ship on what their captures show, one run each with small writes. What Codex's reviewer or Claude's `auto` refuses, and what either asks the client about, has not been seen: a request either still sends is a card, as under any mode but a reading one.
- The real CLIs' behaviour on macOS and Linux is a release gate for those systems, still open.
- A new provider declares `permissions`, gives its facet `modes`, `transition` and `onModesChanged`, takes `SessionStart.mode`, and — where a mode asks — sends `approval-raised` and `approval-resolved` and takes `decide`; `tests/sessions/facet-contract.ts` holds it to a start confirmed and one refused, a change on a live process where it declares one, and an approval approved, denied, granted for the session, left to a Stop, refused by main and lost with its process. Nothing in the shared code names a provider.

## Revisit when

- Either CLI's version differs from the captures': the spikes run again, and a mode a new version is not shown under leaves its adapter's constant until it is (item 6).
- Claude Code takes `bypassPermissions` only with a flag that bypasses permissions: Berserk is then unavailable on Claude, with its reason, and Auto reviewed stands for unattended runs (item 4).
- A CLI lists its rules, or takes one out, over its protocol: item 5's one line and item 17's "no reading of the CLI" can then say more.
- Codex offers a session choice for a command, changes a thread's policy on a live process, or reports a policy change in a frame: items 9 and 16.
- A CLI keeps a grant past its process, or ends one sooner: item 17's liveness needs another source.
- The session's scope proves too little, or a chat's mode too coarse: rules of fat-g's own, a saved rule, or a mode for one prompt, each a decision of its own.
- M22b sends plan turns and M22c elicitations: each takes item 15's registry, and a plan's Execute is an approval on this path.
- The `unelevated` setup is traced, or Codex's setup comes to another system: item 20.
