# 0018 — Codex sessions: one app-server each, read-only, a fixed set of methods

> **Rule:** each Codex session runs on an app-server process of its own, started in its instance's scope at its first prompt. fat-g sends each connection a fixed set of methods, enforced in one module; no set can sign in, change configuration, or list, name or delete the user's threads, and no handshake asks for the experimental API. Every thread starts and resumes under the sandbox, the approval policy and the reviewer of its chat's mode ([0027](0027-execution-permissions.md)) — Read only being the read-only sandbox with the `never` policy — no prompt is sent until Codex's reply says so, and every turn names again what that reply reported. A request for leave to act is answered from the user's decision on its card, and declined under Read only — Codex's leave to run an MCP tool, which it asks as an MCP elicitation, among them, never answered `always`; a question it asks the user is answered by the user, from its card ([0026](0026-questions.md)); anything else the CLI asks for is refused.

- **Status:** Accepted by the maintainer with M15's final spec (C12–C15, C20, C21, C33, C34, C36, C80; planning round 5, C130–C132). Implemented in M15. The acceptance with the installed CLI (M15, V49) is recorded in the milestone document. ## Context

- M15 is the read-only live slice [0009](0009-live-session-data-first.md) asked for, Codex first. Codex's `app-server` speaks JSON-RPC over stdio; M10 traced its turns, and M15's spike traced resume, history, interrupt, workers and the output cap (the turn-tracing note (private), §6).
- Each instance already holds one supervised app-server for its account, usage and model reads (M7, M14b). A thread run on it would share its fate: a lost process would end every session and the usage reads together, and one session's frames would interleave with another's.
- Read-only means the agent never has to ask for an approval, so the slice needs no approval UI. A user's own Codex configuration may ask for more; fat-g must notice, not trust.
- The traces showed that a thread given no turn is not kept and cannot be resumed, and that an interrupt sent before `turn/started` is refused (C130, C131).

## Decision

1. **One app-server per session.** A session's process starts at its first prompt, in its instance's process scope ([0017](0017-provider-instances.md)), and closes five minutes after its last turn and its last worker ended, at once when the session is completed or removed, and at quit. A lost process ends the turn as failed and starts nothing by itself; the next prompt resumes the thread in a new process. The instance's existing connection keeps the account, usage and model reads, and reads a session's earlier messages; it runs no thread. *(M18, C51:)* that read is a check: once per session after each start of fat-g, the turns are listed without their items, and only a turn fat-g's conversation store lacks, or holds unfinished, is read with them.
2. **Two fixed sets of methods,** *(three since M22, four since M26)* in [`codex/methods.ts`](../../src/main/providers/codex/methods.ts), the only senders in the adapter:
   - the existing connection: `initialize`, `initialized`, `account/read`, `account/rateLimits/read`, `model/list`, and `thread/turns/list` for history *(M18: the same method, asked for the turns alone before any turn's items)*;
   - a session's connection: `initialize`, `initialized`, `thread/start`, `thread/resume`, `turn/start`, `turn/interrupt`, and *(M20b, C19)* `thread/fork`;
   - *(M26; [0028](0028-secretary.md), item 3)* a secretary connection: `initialize`, `initialized`, `thread/start` and `turn/start`. It is a short-lived app-server of the account's own, in the instance's process scope and fat-g's probe folder, opened for one request and closed at its end: one ephemeral thread, started with the mode table's read-only policy, the task's instruction as its base instructions and overrides that switch its extras off (item 4), its reply held to Read only as a fork's is, and one turn. It can resume, fork, interrupt or read no thread, and sends no `config` (item 4).
   - *(M22, C60, C73; [0027](0027-execution-permissions.md), item 20)* a sandbox connection: `initialize`, `initialized`, `windowsSandbox/readiness` and `windowsSandbox/setupStart`. It is a short-lived app-server of the account's own, in the instance's process scope, opened for one request and closed at its end: what Codex answers of its Windows sandbox and, at the user's press alone, Codex's own setup of it, in the `elevated` mode and no other. It starts no thread, neither request can be sent on the existing connection or a session's, and `windowsSandbox/setupCompleted` is a notification that connection alone subscribes to, never a method fat-g calls. On a system other than Windows no such connection is opened.

   No login method, no `config/` method and no other `thread/` method can be sent on any of them. *(M22, C7, C64, C70:)* `thread/start`, `thread/resume` and `turn/start` now carry the mode's policy (item 3): fields of methods the session's set already held, so that set is as it was. *(M20b, C19; [0025](0025-asides.md), item 5:)* `thread/fork` is sent for one thing, an aside's side thread, from one place, with exactly these fields — the session's thread, the newest turn whose end Codex reported or none, `ephemeral: true`, `excludeTurns: true`, the session's folder, `sandbox: "read-only"`, `approvalPolicy: "never"`, fat-g's instructions to act on nothing, the record's model and ** the chat's speed tier as `serviceTier` — and never `config` or `baseInstructions`. A session's handshake opts out of the delta notifications, so the CLI sends whole items; no handshake sends `experimentalApi`. *(M19, C7, C8:)* it opts out of ten of them and keeps `item/agentMessage/delta`, so an agent's message arrives as it is written and is completed by its whole item, which stays the authority for its text; every other item still arrives whole. A delta is a notification the CLI sends, not a method fat-g calls: neither set grows. *(M22b, C13, C14, C80; [0029](0029-plans.md), item 3:)* a session's handshake asks for the experimental API, which a plan turn's `collaborationMode` needs, and keeps `item/plan/delta` beside the message's delta, opting out of the nine others: a plan arrives as it is written and is completed by its whole `plan` item, the authority for its text. Where Codex refuses that handshake, the process is opened again with the plain one, which asks for nothing experimental, and plans read unavailable for that account until fat-g restarts. The secretary's, the sandbox's and the existing connection's handshakes ask for nothing experimental, and `collaborationMode/list` is never sent: no set grows. *([0033](0033-context-readings.md), item 3:)* `thread/tokenUsage/updated`, which Codex sends unasked and the session dropped unparsed, is read beside the turn mapper for the session's own thread alone: its last call's count, its running total and its model's window are the chat's context reading. A sub-agent's and a side thread's are counted and left. No method is sent for it, and no set grows; where Codex compacts stays its configuration's, which no `config/` method reads.
3. **Read-only, checked.** `thread/start` and `thread/resume` carry `sandbox: "read-only"` and `approvalPolicy: "never"`, in the session's stored folder, or the project's first root for a new one. Before any prompt the adapter compares the reply: a read-only sandbox without network, and the `never` policy. On any difference it sends nothing, and the chat says so in fat-g's words. *(M20b, C19:)* a fork's reply is compared the same way before the side thread is sent any turn: a difference, a refusal, or a reply dropped for its size sends nothing, ends the aside's turn with its notice, and leaves the session as it is. *(M22, C4, C7, C46, C64, C65, C70, C84; [0027](0027-execution-permissions.md), items 2, 3, 9 and 10:)* the two fields are the chat's mode's, with a third. `thread/start` and `thread/resume` carry the mode's `sandbox`, its `approvalPolicy` and, for a mode whose policy asks someone, its `approvalsReviewer`: Read only is `read-only` and `never` as above, and names no reviewer; Ask first is `workspace-write`, `untrusted` and `user`; Sandbox ok is `workspace-write`, `on-request` and `user`; Auto reviewed is the same under `auto_review`; Berserk is `danger-full-access` and `never`, and names none. Those words are in one file of the module, `modes.ts`. Before any prompt the reply is held to all of them: the policy the mode's, the reviewer the mode's where it named one, the sandbox the mode's, and for Read only no network, as before. One exception: Ask first takes a reply that reports the read-only sandbox, which is what an account with no sandbox answers, and the mode is then said unconfined. On any other difference nothing is sent, the turn fails with its notice — for a mode other than Read only, one that carries what the reply reported — and Send is blocked until a mode is chosen again. The checked reply is kept, and every `turn/start` of the session's thread names again its `approvalPolicy`, its `sandbox` object as `sandboxPolicy`, and its reviewer where the mode named one: what that reply reported and never another, since a policy named on a turn stays with its thread and no frame reports it. Where a sandbox mode can write is read from the reply, never held as a constant. A thread's policy is changed in one way alone: the process closed, then `thread/resume` in a fresh process naming the new mode, its reply checked; a resume in a process that holds the thread loaded is never the means. A fork's fields and its reply's check are read-only and `never` whatever the session's mode, and a side thread's turns name no policy.
4. **The preset is what runs.** Every `turn/start` carries the record's model key and its effort; fat-g sends no `config` and writes no Codex configuration. *([0016](0016-model-presets.md):)* and its speed tier: `thread/start`, `thread/resume` and every `turn/start` carry `serviceTier`, the record's tier id or `default` for standard speed, so a `service_tier` in the user's `config.toml` applies to no chat of fat-g's, as it decides neither its model nor its effort. A turn's tier holds for that turn and those after it, so a change between turns needs no new process. An aside's `thread/fork` and its turns carry the chat's tier; the secretary's thread and turn always carry `default`. Codex 0.164.0's types take `serviceTier?: string | null` on all four; a `null` on a turn keeps the thread's tier, so standard speed is said by name: `default`, which a thread's start reply then reports (models research §6). A tier the model does not list is dropped with a `warning` notification, the reply reporting `null`; a turn's tier is not checked against the list. A start or resume that asked for a tier says, from its reply alone, whether the thread took it: `in-force` `served` `fast`, or `standard` with the reason `not-offered`. Codex's turns name no speed, so nothing more is known of a later change. The user's own configuration applies otherwise, their MCP servers included, and `PRIVACY.md` says so. *(M26, at the maintainer's word; [0028](0028-secretary.md), item 3:)* one thread is sent `baseInstructions`, the secretary's, whose instruction takes the place of Codex's own agent instructions, which a title needs none of: M26's K2 measured the request's input at about 9,600 tokens with it and 13,100 without. The same thread alone is sent a `config` too, at the maintainer's word: the overrides Codex's own IDE extension sends its title threads, each of which switches something off — sub-agents, hooks, plugins, the shell snapshot, tool suggestions, apps and their connectors, and web search — and none of which sets anything of the user's. K2 measured the request's input at about 5,500 tokens with both. A start Codex refuses with the overrides is asked once more without them. A session's thread and an aside's are sent neither, and keep Codex's own instructions and the user's configuration whole. fat-g still writes no Codex configuration. *(M22b, C13, C55; [0029](0029-plans.md), item 3:)* a plan turn's `turn/start` names `collaborationMode` with the mode `plan`, the record's model and effort and null instructions, and every later turn of a thread a plan turn of fat-g's ran on names it with `default`, read from the store's record of each turn, so that no turn inherits plan mode. A thread that never planned, an aside's fork and the secretary's thread name none. It sets no instruction of fat-g's and nothing of the user's configuration.
5. **The reference is the thread that holds a turn.** It is reported at the first turn's `turn/started` and stored then, with the folder it started in (C130).
6. **Stop waits for the turn to exist** (C131): an interrupt goes once `turn/started` has named the turn, and to each worker's own turn still open (C132). One not confirmed in ten seconds ends the session's process. *(M20b, C70:)* an aside's Stop is another matter: it interrupts the side thread's own turn, once that turn is named and started, on a clock of its own, and one not confirmed ends the aside's turn with a notice and leaves the process, since the session's turns run on it; what still comes for that side thread is dropped and counted. The session's own Stop sends no interrupt to a side thread.
7. **Nothing is granted.** A command or file-change approval is declined; any other request from the CLI gets "method not found". Each is counted by its method, and the chat shows one notice in fat-g's words. *(M21, C23, C27, C29, C65, C66:)* one request is neither: `item/tool/requestUserInput`, the question a plan turn asks, is held and answered when the user answers its card ([0026](0026-questions.md), item 9) — `answers` keyed by each question's id, the chosen labels and the typed text as separate strings. It is the reply to a request the CLI made, and no method of fat-g's: both sets and the handshake are as they were, and an answer approves nothing. A request fat-g cannot draw whole, or cannot place, is refused as before, with the notice. The connection's handler may answer later; the session writes that reply and learns whether its line went. A request still held when the turn is interrupted is resolved by Codex's `serverRequest/resolved`, and one held when the process is lost is said dropped before the session's own ends. *(M22, C8, C9, C11, C13, C21, C22, C68, C69, C76, C91, C96; [0027](0027-execution-permissions.md), items 11 to 17:)* nothing is granted that the user did not grant. Under Read only the two approval requests are declined at once, as above. Under every other mode `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` are held as the question is — under the session's turn, or the worker whose thread asked — and answered when the user decides the card: `{ decision: 'accept' }`, `{ decision: 'acceptForSession' }` or `{ decision: 'decline' }`, fixed by the choice whatever the request listed. A file change's request names no file: the session keeps each `fileChange` item's changes as they came, from the item's start to its end, and shows the request from that. A request that names an item the session does not hold, one that cannot be shown whole and one it cannot place — a side thread's among them — get "method not found", counted, with the notice. `acceptForSession` is offered for a file change that asks for no root, and for a command only where its own list of decisions holds it. Codex's amendment to its own rules is told on the card as something the request would also grant and is never among the choices: nothing in the module can write it. A request that comes again under a held id is compared with the hold, whole, before it is counted as a repeat, a question's too: one that differs is refused, the hold let go, and its card withdrawn as changed. `serverRequest/resolved` for a decided request is Codex's word that it took the decision; for an undecided one, that it took the request back. The holds are keyed by a lossless identity, so the ids `0` and `"0"` are two requests. A reply the process did not take is said dropped and ends the process, as an answer's does. The frames of Codex's own reviewer — `item/autoApprovalReview/started`, `item/autoApprovalReview/completed` and `guardianWarning` — are counted and mapped to nothing, and an item Codex reports as `declined` ends as declined, live and from history. Each reply is to a request the CLI made, and no method of fat-g's: the session's set is as it was. *(codex-cli 0.164.0, codex-mcp-approvals (private research note):)* a third request for leave: Codex asks to run an MCP tool by `mcpServer/elicitation/request` in form mode, its `_meta.codex_approval_kind` `mcp_tool_call`, naming its server and the call's arguments but no item, and the tool in its sentence alone, which is never read. The session keeps each open `mcpToolCall` item's server, tool and arguments, from its start to its end, and places the request on the one of its thread with that server and those arguments that nothing was asked for yet — the oldest where several are alike; one it cannot place, or whose alike calls name different tools, is refused with the notice. Its card is the tool card a Claude MCP tool's is: the server and tool as the activity names them, the arguments whole. It is answered `{ action: 'accept', content: null, _meta: null }`, with `_meta: { persist: 'session' }` for the session's grant where `_meta.persist` offers `session` — which covers that tool of that server and no other — or `{ action: 'decline', content: null, _meta: null }`. `always`, a rule Codex would keep, is told on the card as what the request would also grant, and nothing in the module can write it. Under Read only Codex asks none, refusing such a call itself under `never`, and one that came would be declined at once. A call the user denied, which Codex ends `failed` in its own words, ends declined by the user. Any other elicitation — an MCP server's own form or address — still gets "method not found", counted, with the notice.

   MCP calls are matched within their named, live turn, on the session or a worker; late or unowned starts are not kept, and a completion removes only the call of the same thread and turn. At most 16 open calls are kept across the process. If another would exceed that bound, its thread's cached calls are discarded and its further MCP approvals refused until that thread's turn or worker ends: losing a call must never make another tool appear to be its match. Calls and this refusal state are cleared with their owner, even without `item/completed`, and with the process. An elicitation delivered again under a held id is compared before it is classified, including one whose approval marker disappeared: the old card is withdrawn as changed before the new payload is refused.

8. **Codex's words stay Codex's.** A refusal's application behavior is determined by its code, never by its message; the CLI's text reaches the chat only as a notice's bounded detail, never a log. *(M18, C34:)* that detail is conversation content, and is kept with its notice in the conversation store ([0019](0019-conversation-store.md)); it still reaches no log, no summary and not the Pet. At the maintainer's request, an opt-in unpackaged-build diagnostic may classify the exact active-writer resume wording as `active-writer` or `other` before discarding it. Only that fixed classification reaches the trace; it never changes retries, errors or session state (M15 C139–C140).

## What is left out

- A message during a turn, approvals, answering the CLI's questions, and any write access: later milestones, each with its own decision where it changes one of the above. *(Questions came with M21, [0026](0026-questions.md); approvals and write access with M22, [0027](0027-execution-permissions.md).)*
- *(M22)* Codex's experimental policy fields — a named permission profile, a `granular` policy, runtime workspace roots — a `config` override, its amendment to its own rules, and the `unelevated` setup.
- Listing, renaming, archiving or deleting the user's Codex threads; reading Codex's own session files.
- Starting the turn's process again by itself after a loss.

## Consequences

- Each running session is one more Codex process; an idle one closes after five minutes.
- A thread fat-g started shows in Codex's own history, where its other apps show it; removing the session in fat-g leaves it there.
- A read-only session can read outside its project's folder, wherever the user's account can read (C135): `PRIVACY.md` says so.
- *(M22)* Under a mode other than Read only a session can run commands and change files, as [0027](0027-execution-permissions.md) says of each mode. A start under some of them makes Codex record the session's folder as trusted in its own `config.toml`, and the setup changes the machine: `PRIVACY.md` says both.
- Adding a method to any set is a change to this decision.

## Revisit when

- Write access or approvals are planned (M22): the sandbox, the policy and item 7 change together. Questions answered in the chat came with M21, and changed item 7 alone. *(M22 changed them together, with the rule and item 2: [0027](0027-execution-permissions.md).)*
- Codex changes a thread's policy on a live process, reports a policy in a frame, or offers a session choice for a command: item 3's one way of changing a policy, and item 7's choices.
- Codex names the item or the tool in its leave to run an MCP tool, or changes what `persist` offers: item 7's placing of the request, and its choices.
- A plan turn is sent, or the experimental API is asked for (M22b): item 7's question handler, tested against its capture alone, is then live.
- Codex changes its app-server's methods, its resume, or the meaning of the read-only sandbox, as the re-check before each milestone finds.
- Several sessions per process becomes worth its coupling.
