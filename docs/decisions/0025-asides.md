# 0025 — Asides: a question beside a session

> **Rule:** an aside is a question asked beside a session — Explain this on a selection, or one typed freely — answered against what the session already holds and adding nothing to it. It runs on the session's own process, by the route its provider gives: on Claude a `side_question` control request, which takes no tool; on Codex an ephemeral, read-only fork of the session's thread, told to act on nothing. It never waits for the session's turn, never interrupts one, and changes nothing of the session's status. Each aside is a conversation of its own in the conversation store, with its session as its parent and the passage it was asked about, kept until the user removes it, its session or its project. Nothing of it reaches a log, the app state, a summary or the Pet.

## Context

- A reader of a long answer wants to ask about one passage of it without that question, and its answer, becoming part of the conversation the agent is working in. A new prompt does: it is a turn, the model holds it from then on, and it waits for the turn in flight.
- Both CLIs have a route that answers beside a conversation, and they differ (chat-protocols.md §13 (private research note), M20b's K1 and K3). Claude Code takes a `side_question` control request on a session's process: answered whole in two to three seconds, with no tool, no hook of the user's and nothing written to Claude's own history, while a turn runs or not, and several at once. It keeps nothing of one: a follow-up carries the earlier exchanges as `history`. The request is refused under `--disable-slash-commands`, which [0023](0023-cli-commands-pass-through.md) had already decided to drop. The SDK's types do not list it. Codex's app-server takes `thread/fork`: an ephemeral thread that holds the session's history through a turn it names, on the same process, whose turns stream as a session's do; it starts the user's MCP servers again, and, told to act on nothing, still read a file a question invited it to.
- A side chat that can act — run a command, change a file — is a fork, a session of its own, and never a tab beside one (maintainer): M24's.
- A selection in a file fat-g shows is text of a project's file, which [0022](0022-reading-project-files.md) said is shown and never kept.

## Decision

1. **Beside the session, never in it.** Nothing of an aside is sent into the session's context. It neither waits for a turn in flight nor interrupts one; it changes neither the session's status, its attention, its action line nor its agent list. An aside running blocks no Send, and a turn running blocks no ask. There is no cap on asides running at once, and no queue of fat-g's. *(M22, C6, C62, C71, C84, C89, C90; [0027](0027-execution-permissions.md), items 9, 10, 18, 20 and 22:)* an aside is given neither its session's mode nor its grants. Claude's side question takes no tool whatever the session's mode; Codex's fork is read-only with approvals off whatever the session's mode, its fields and its reply's check as item 5 fixes them, and its turns name no policy. A request that names a side thread is no one's, and is refused: nothing asked from an aside can be approved through a session's card. An aside still runs on the session's process, so four things of that process reach it. A chat's mode is not changed while an aside's turn runs; a change that restarts the process closes it as the idle close does, and a Codex side thread is gone with it, a follow-up forking again. The two mode blocks hold an aside's question as they hold a prompt, since an ask may start the session's process, which starts under the chat's mode. A setup of the account's sandbox holds an ask as it holds a prompt. And a line too long to read that may have been a request stops each running aside by the aside's own Stop, with a notice of its own.
2. **Ways into one aside.** Explain this in a side chat on a selection, whose first question is fat-g's own words around the passage, naming where it came from; and a question typed freely. Send to new side chat opens a fresh, focused draft with the selected text between double quotation marks, preserving its line breaks; it sends nothing until the user submits it, and the submitted text is a freely typed question. This draft action also takes selections spanning several messages. standalone Explain buttons beside message blocks and review findings are hidden for now, with their implementation retained; saved asides' markers remain available. *(M22e, C34, C54:)* Explain on a finding of a plan's review, when its button is enabled, opens an aside of the reviewer's session whose source is of kind `message` — the round's answer, with the range and digest of the finding's row as drawn, and the finding's id, title, example, description and correction as its passage — and whose first question is fat-g's words naming the finding and ending "Explain this finding."; nothing is marked, and asking again for the same finding reopens its aside. From its first answer on an aside is the same whichever way it began. An explanation's question always carries the passage: a side thread may hold nothing of the turn it lies in.
3. **It needs a conversation the provider holds.** A session with no reference yet takes no aside. One whose process has closed has it started as a prompt would, through the same gate and the same checks, with no turn of the session's; the idle clock runs for an aside as for a turn.
4. **On Claude: a side question.** A fifth send, `side_question`, with the question and the aside's earlier exchanges as `history`, on the session's process; and a sixth, `control_cancel_request` with the request's id, for its Stop ([0020](0020-claude-chat-sessions.md), item 2). Of the reply, `response` is the answer, whole, or none; `synthetic` marks a placeholder that is never shown as the model's; `refusal_fallback` names the model that answered in the session's place, which the tab then says. Of the `control_request_progress` frame that names the request, its status alone. It has ten minutes; past them its turn fails and the process is left as it is. It names no model, takes no tool, and reports no usage, so fat-g shows nothing of its cost.
5. **On Codex: an ephemeral fork.** The session's method set grows by `thread/fork` and nothing else ([0018](0018-codex-sessions.md), item 2), sent on the session's own app-server with exactly these fields: the session's thread, the newest turn whose end Codex reported — or none while no turn has ended — `ephemeral: true`, `excludeTurns: true`, the session's folder, `sandbox: "read-only"`, `approvalPolicy: "never"`, fat-g's instructions to act on nothing, and the record's model. Never `config`, never `baseInstructions`. Its reply is checked as a start's is, before any turn. Its turns are `turn/start` on the side thread; its frames are the aside's alone; its Stop is `turn/interrupt` on its own turn, on a clock of its own. Once the process has ended a side thread cannot be resumed: a follow-up forks again, and carries the aside's earlier exchanges before its question.
6. **What an aside may do is its route's, declared and said.** A provider declares whether it answers asides, whether an answer arrives as it is written or whole, and whether an aside may read: Claude's reads nothing, Codex's may read and run a listing and changes nothing. The privacy document says which; the tab shows what a Codex side thread did as [0024](0024-a-sessions-work.md)'s items, without a separate capability line.
7. **A Stop of an aside holds the aside alone.** It never ends the session's process and never interrupts the session's turn. One not confirmed ends the aside's turn with a notice and leaves the process; what still comes for it is dropped and counted. The session's own Stop interrupts no aside; when the session's process ends, every open aside's turn ends with it, as a session's does.
8. **A conversation of its own, with a parent.** In the conversation store an aside is a conversation whose id is the aside's, which names its session as its parent, with its source — the kind of thing it was taken from, the item or the file's real path, the lines, the passage cut to 20,000 units, and where the passage lies in what was drawn, as two offsets and a short digest — and its title ([0019](0019-conversation-store.md), item 5). Its question is on disk before anything is sent. A message keeps the model its reply named. Its items are in no page of its session's conversation.
9. **Kept until explicitly closed; never detached by itself.** Only the user's removal deletes an aside: closing its tab, removing its session or removing its project, each leaving no text in the store's files ([0019](0019-conversation-store.md), item 11). At the maintainer's request, Side question always opens a fresh, focused draft directly, with no saved-question menu. An explicit tab close — X, middle click or Delete — stops its running answer and removes its saved conversation, source marker and draft without another confirmation. A failed removal keeps the tab open and says why it could not close. Switching tabs or sessions, quitting and restarting remove nothing: saved questions reopen as tabs when their session is read, without a provider call or a change to the selected tab. Unsent drafts remain in memory for the run. There is no separate Remove button. A session whose record is gone keeps its asides, unseen, counted with its chat and not beside it, and they go with that chat's removal.
10. **The one text of a project's file that is kept.** A passage the user selects in a file's tab and sends to an aside is kept with the aside, as the question they asked ([0022](0022-reading-project-files.md), its rule and item 9). A file's text is otherwise shown and never kept.
11. **A session's read lists markers, never text.** What a session's chat is told of its asides is, for each, its id, its title, where it came from and the two offsets and the digest: enough to draw a marker and to paint the passage, and none of its words. The passage is in the aside's own read alone. The page paints a passage only where the text drawn at those offsets still has that digest.
12. **In the store and the Main window alone.** Four channels, the Main window's only. An aside's pushes go out under its session's id and revision, each naming the aside, so every other window takes the revision and nothing else. No log, no summary, no app state and never the Pet: main says of an ask its outcome's kind, and counts.
13. **Every outcome is an event that names the aside.** The agent events are at version 6: a turn's start and end, a message and its delta, an activity's start and end and a notice may each name the aside whose event it is, and a message the model that wrote it. A reply with no answer ends the aside's turn as failed, with fat-g's own line that no answer was given.
14. **An explanation starts with its folded excerpt.** The pane's header says Explanation. Its source link stays visible above the scroll area, labelled "Explaining chat lines …" for a chat passage and naming the source for other kinds. A box labelled "Explained excerpt" uses the answered question's fold and holds the full saved excerpt, collapsed initially, then the model's speaker bar and answer. The excerpt shares the messages' scroll area. The generated opening question stays stored and sent as before, but the excerpt replaces it in presentation; freely typed questions and follow-ups stay visible. The fold's state lasts while its tab stays open.

## What is left out

- A side chat with tools that act: a fork is a session of its own (M24).
- Explain this on a plan's item (M22b), on media (M25), and on a selection that spans two messages or a message and a file.
- A cap on asides, an aside turned into a session, and asides anywhere but a tab.
- What an aside costs: neither route reports it per aside, and fat-g claims nothing of it.

## Consequences

- fat-g depends on a Claude control request the SDK's types do not list. The spike that found it runs again at each new CLI version (M20b, B1), the replay fake holds its capture, and a refusal ends the aside's turn with its notice and leaves the session untouched.
- `conversations.sqlite` now holds asides: their questions, the passage each was asked about — a file's own text among them, where the user sent it — their answers, and what a Codex side thread read. [PRIVACY.md](../../PRIVACY.md) says so. The leak scans take the side questions' captures as needles.
- The store is at version 4: `parentId`, `source` and `title` on a conversation, with an index by parent, and a mark on a turn fat-g answered itself ([0023](0023-cli-commands-pass-through.md)). No migration: a version-3 store is refused as older ([0014](0014-format-compatibility-starts-at-first-release.md)).
- Each Codex aside starts the user's MCP servers again, and takes some seconds to its first word; a Claude follow-up sends the aside's exchanges again, and grows with it.
- A new provider declares its asides and answers one through `ask` and `stopAside`; `tests/sessions/facet-contract.ts` holds it to an ask that completes, one stopped and one refused, and nothing in the shared code names a provider.

## Revisit when

- Claude Code documents the side question, changes its reply, or drops it: item 4, and the dependency.
- Codex's app-server offers a fork that starts no MCP server, or one that can be resumed: item 5's fork-again goes.
- Either route reports an aside's usage: the tab can then say it.
- M22 grants a tool that writes: an aside still acts on nothing, and item 6 says so again. *(M22 did, and an aside still acts on nothing: item 1 says so, and item 6 stands as it was.)*
- A highlight must survive a drawing that changed — a file edited above the passage: item 11's offsets would need an anchor that moves with the text.
